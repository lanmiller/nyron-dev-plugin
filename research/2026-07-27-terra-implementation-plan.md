## РЕВЬЮ: 5 ЗАМЕЧАНИЙ

1. QA-пилот противоречив: в VISION зафиксирован GLM Coding Plan Lite, а первый дайджест рекомендует начинать с Pro. До покупки нужно выбрать один тариф и задать измеримый exit-criterion: число UJM-прогонов, расход промптов за 5-часовое окно, доля успешных починок.

2. Не выбран единый формат связи Markdown ↔ Confluence: встречаются `confluence-page-id` и поле `публикация: <page id>`. Это создаст дубли при первой же миграции. Нужны одно имя поля, правила его записи CI и миграция существующих страниц.

3. Критерий этапа 1 про алерт на «застревание, видимое сенсорам» пока неоперационален. SQLite будки показывает сообщения/очередь, JSONL — прогресс конвейера, PID — лишь живость процесса; ни один источник сам по себе не означает «работа застряла». Нужен контракт наблюдения: `running/stalled/idle/unknown`, timestamp последнего прогресса, источник, порог и правило, что `unknown` тоже алертится отдельно.

4. Вышка этапа 1 не может создавать control-job с `--resume`: очереди job/lease и исполнитель появятся лишь на этапе 3–4а. На этапе 1 поле ввода должно быть скрыто или явно read-only («продолжение будет доступно после демона»), иначе UI обещает невозможное действие.

5. UJM-критерий «ночная регрессия идёт» не фиксирует контур исполнения: стенд, seed/test-data, секреты, владельца флаков, порог падений, место запуска и права Healer на MR. Без этого получится набор тестов, а не надёжный приёмочный гейт.

Остальная архитектура согласована: job-модель, переходный Desktop-контракт, границы будки/GitLab и DAG этапов не конфликтуют.

**Безопасный порядок выката H0:** H0-01 → H0-02 с тестами → H0-03 только для новых волн → по одной текущей волне: старт replacement, проверка `hubdir` и `alive`, затем остановка старого watcher.
