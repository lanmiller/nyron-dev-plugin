# STOVP — проект системы контролируемого создания продукта

Статус: проект, согласован на гриле с CTO 16.08.2026. Ничего из описанного не
выкачено; это карта, по которой строим. Источники: README плагина, задачи
STOVP-57 / STOVP-58 / STOVP-59 с комментами, замер docs/BASELINE-1210.md,
разборы docs/FLOW-MAP.md и docs/RULES-AUDIT.md.

Имя продукта — STOVP. Рабочее имя плагина nyron-dev сохраняется до шага
миграции имён (раздел 8, делается последним).

---

## 1. Суть

STOVP — система, в которой продукт создаётся контролируемо, качественно и
быстро силами флота ИИ-исполнителей под управлением людей. Главный принцип,
принятый на гриле: **контроль человека стоит в начале пути (проектирование и
согласование), а исполнение и проверка в конце пути — автоматика**. Человек
дорог там, где нужно суждение; автоматика надёжна там, где правило можно
проверить механически.

Цели числом (замер «до» — BASELINE-1210):

| Показатель | Сейчас | Цель |
|---|---|---|
| Параллельность эпика (сумма часов работы / календарный размах) | 1,7× | от 3× |
| Хвост доработок после первого ревью, медиана | 10,6 ч | ≤ 4 ч |
| Заходов в Ревью на тикет | 1,74 | ≤ 1,3 |
| Ответ человека доезжает до сессии | минуты–часы | секунды |

Стоимость токенов при выборе степени параллели аргументом не является —
у команды пул подписок. Аргументов ровно два: скорость и качество.

## 2. Три слоя (что можно настраивать, а что нельзя)

**Ядро — недоговариваемое.** Не отключается конфигом ни для какой команды:

- у работы есть DoD (определение готовности) и «Как тестировать»;
- проверяет не автор: код, написанный одной моделью, проверяет другая
  (предпочтительно другой поставщик; минимум — другой экземпляр; ослабленный
  вариант помечается при аттестации проекта);
- границы задачи расширяет только постановщик;
- секреты не живут в коде и в тикетах;
- находки разбираются, а не теряются (находка → тикет или строка долга).

**Флоу — конфигурируемое.** Имена статусов, роли и их носители, размеры задач,
потолок параллели, степень автоматики мержа — ключи конфига проекта. Скиллы
ходят по ключам, не по именам.

**Исполнение — свободное.** Кто закрывает роль — человек в Desktop, сессия в
CLI, контейнер в облаке — стандарту всё равно.

## 3. Единицы работы и план исполнения (из STOVP-57)

Три уровня, как у людей:

- **Эпик** — фича целиком; владелец — постановщик.
- **Задача** — целостное поведение с пользовательским DoD; ведёт
  диспетчер-синьор.
- **Подзадача** — технический кусок со своим DoD и красным тестом; единица
  работы исполнителя. Волна ведёт одну подзадачу; подзадачи заводятся только
  там, где есть реальная параллель.

**Новое (решение гриля): груминг обязан выдавать план исполнения.** Это
отдельный артефакт нарезки, в котором записано:

- сколько диспетчеров нужно фиче (или достаточно одного);
- по каждой подзадаче — механизм исполнения: диспетчер делает сам /
  субагенты внутри сессии / конвейер (workflow) / отдельная сессия-волна;
- число одновременных стартов.

Скорость проектируется здесь: если параллель возможна по коду, она должна
быть заложена в плане, а не открыта случайно по ходу. Очередь пульта
исполняет план автоматически; диспетчер может переметить кусок по ходу —
пометка живёт в трекере, и очередь читает её оттуда.

**Граница параллели — договорённость, а не файл.** Один файл можно вести
двумя исполнителями: git сливает правки в разных функциях сам. Ждать нужно в
двух случаях: одному физически нужен чужой код, которого ещё нет; либо обе
правки меняют один и тот же смысл (одну функцию, один инвариант). Такие
пересечения отмечаются на груминге и либо фиксируются одной строкой
договорённости, либо отдаются одному исполнителю.

**Дом фактов о зависимостях — связи трекера** («блокирует / блокируется»),
их ставит груминг. Бронь файлов в будке — сигнал «здесь работают», но не
источник истины: очередь читает только трекер.

**Мерж — по готовности, а не пачкой.** Каждая ветка уезжает в main сразу
после зелёных ворот (раздел 5), порядок держит очередь мержа в будке;
остальные подтягивают свежий main до сдачи.

## 4. Роли и права

Роль — это функция, а не человек. Пять функций обязательны в любом сценарии;
кто их закрывает — конфиг:

| Функция | Что делает | Кто может закрывать |
|---|---|---|
| Постановка | решает ЧТО делать и зачем; согласует нарезку; отвечает на эскалации; расширяет границы | человек (роль настраивается: конкретная роль, конкретный человек или «один за всех») |
| Порядок (диспетчер) | ведёт задачи, следит за конвейером, решает об эскалации, разруливает спорное | сессия ИИ; масштабируется — диспетчеров может быть несколько, число задаёт план исполнения |
| Исполнение | пишет код и тесты по DoD | сессии-волны, субагенты, конвейеры |
| Независимая проверка | проверяет код не-автор | другая модель (канон: GPT проверяет Claude); конфиг ревьюера |
| Приёмка | подтверждает, что фича работает для пользователя | QA-человек; в соло — тот же человек в роли QA (живой прогон) |

**Постановщик пишется всегда** — у каждого эпика и задачи он назначен явно.
Всё, что адресовано постановщику (второй гриль, эскалации), пишется простым
языком, понятным человеку без навыков разработки — даже если постановщик
формально разработчик или CTO.

**merge_rights — степень автоматики, которую проект себе разрешает:**

| Уровень | Что означает |
|---|---|
| `wave` | полный автомат: зелёные ворота (раздел 5) — исполнитель мержит сам |
| `dispatcher` | живой вердикт диспетчера на каждый мерж |
| `lead` | мержит только лид команды |
| `cto` | мержит только CTO |

Дефолт STOVP — `wave`. Консервативная команда ставит выше — и получает
прежнее поведение с вердиктами. Фраза «мержит диспетчер» в STOVP-57 — не
канон, а одно из положений этой ручки (противоречие снято).

**Кастомные роли** — по канону team-roles (0.9.2): карточка по единой сетке,
раздел «НЕ делает» обязателен.

## 5. Флоу от идеи до прода

```
 сырьё («прилетело»)      решённая фича (мандат)      гипотеза (ставка)
      intake-groom     →      feature-intake        →     product-flow
           └──────────────────────┬──────────────────────────┘
                        стандарт задачи (jira-task-standard)
                                  ↓
              ГРУМИНГ: нарезка + план исполнения + связи-зависимости
                                  ↓
              ВТОРОЙ ГРИЛЬ: постановщик проходит по задачам —
              «что делаем / как тестируем / зачем» простым языком;
              неподтверждённое в очередь не попадает (гейт механикой)
                                  ↓
              ОЧЕРЕДЬ ПУЛЬТА: свободен слот → запуск исполнителя
              по плану исполнения, без ручных кнопок
                                  ↓
              ИСПОЛНИТЕЛЬ: красный тест (чужой моделью) → код →
              проверка другой моделью (кросс-ревью) → сверка с DoD
                                  ↓
              ВОРОТА В MAIN (автомат при merge_rights=wave):
              код зелёный + DoD не нарушен → мерж по очереди будки
                                  ↓
              смоук предпрода → приёмка: живой прогон (live-epic-testing)
              и/или QA-тикет (qa-handoff) → Готово ставит приёмка
```

**Эскалация — единственная точка, где автоматика останавливается сама.**
Если по ходу работы видно, что DoD или канон не выдерживается, решение об
эскалации принимает диспетчер: постановщику прилетает карточка-вопрос
«получится вот так — ок или нет?» на простом языке. Ответ постановщика —
часть трекера, границы задачи меняет только он.

Вердикта диспетчера на каждый тикет больше нет — узкое горлышко убрано.
Контроль не исчез, а переехал в начало: второй гриль постановщика на
груминге дешевле и надёжнее, чем разбор готового кода в конце.

## 6. Оркестратор (пульт) — из STOVP-58

Пульт из смотрового окна становится владельцем исполнителей. Три шага строго
по порядку:

1. **Владение процессом.** Пульт запускает сессию CLI, читает её поток,
   пишет в неё, останавливает, перезапускает с контрольной точки. Одно поле
   ввода, два намерения: «хочу фичу X» и «закрой эпик N»; работает и с
   телефона. Диалоги согласий заменяются хук-забором на опасные операции —
   но полное снятие диалогов разрешено только после личности флота
   (раздел 7): забор на стороне сервера обойти нельзя, забор на маке — можно.
2. **Самотянущая очередь.** Очередь не выдаёт работу по одной — на старте
   эпика пульт запускает весь фронт сразу: все подзадачи плана исполнения,
   помеченные «флоту», у которых закрыты зависимости, — столько, на сколько
   хватает слотов. Ждать в системе можно только по двум причинам: нужен
   чужой код, которого ещё нет (зависимость), или кончились слоты. Как
   только причина исчезает — зависимость закрылась мержем, слот
   освободился — следующая готовая подзадача стартует немедленно, без
   человека. Очередь не выбирает, что делать (это решил план на груминге),
   она следит, чтобы готовое не лежало ни минуты. Параллельность перестаёт
   быть уговором и становится числом.
3. **Пул ресурсов.** Пульт знает аккаунты и слоты, паркует при исчерпании
   лимита и говорит об этом. Дом реестра аккаунтов на ступени 1 — машина
   владельца; для сервера команды (ступень 2) решение принимается при его
   строительстве — отдельный вопрос, не сейчас.

**Правило перезапуска.** «Зависшее лечится перезапуском» работает только при
условии: рабочий контекст диспетчера и волн живёт в трекере и будке (брифы,
план, вердикты, эскалации — комментами), а сессия после подъёма пересобирает
его оттуда. Память сессии — кэш, не дом. Это требование к каждому скиллу
флоу: всё решённое немедленно фиксируется наружу.

**Чего пульт не делает:** не пишет код, не принимает продуктовых решений,
не заменяет трекер и не заменяет диспетчера — тот остаётся сессией с
контекстом и суждением. Desktop-сессии остаются видимыми в пульте.

**Смотровой режим браузера** — после шага 1: пульт показывает последний
адрес и снимок экрана из браузера агента; клики из пульта — отдельным
заходом, с теми же правилами забора.

**Абстракция трекера.** Очередь и дерево пульта работают через единый
интерфейс единицы работы (id, родитель, зависимости, статус, метка
исполнителя, DoD) — чтобы хранилище jira/files из конфига оставалось
взаимозаменяемым. Прямые вызовы Jira из очереди — запрещены.

## 7. Конфигурация — паспорт проекта (из STOVP-59)

**Закон: у каждого факта один дом.**

| Дом | Хозяин | Едет | Что живёт |
|---|---|---|---|
| Канон команды | команда, через git | в репозиторий | статусы трекера, модели, правила, потолок параллели, merge_rights, реестр доступов «человек/флот → серверы» (публичные ключи) |
| Машина | владелец | никуда | ~/.ssh/, список проектов с корнями, подписки |
| Секреты проекта | разработчик | никуда (gitignored) | `<проект>/.secrets/` — токены и ключи; .env и .mcp.json — указатели, не значения |
| Живое состояние | пульт | никуда, не редактируется | кто запущен, остаток лимитов, очередь |

Переносимость: новая машина = скопировать `.secrets/` проекта и `~/.ssh/` —
проект живой.

**Подключение проекта — пять ступеней, каждая — ворота на следующую:**

1. **Анализ.** Аудитор проходит весь репозиторий: структура, стек, сервисы.
   Выход — карта проекта.
2. **Поиск секретов, включая захардкоженные.** Сканер с детекторами по всему
   дереву. Захардкоженный секрет — блокер ступени: сначала вынос и ротация.
3. **Сборка секретницы.** Всё по домам; смоук фактом по каждому ключу
   (Jira отвечает, SSH ходит, ревьюер жив).
4. **Правки CLAUDE.md — только по согласованию.** Аудитор различает четыре
   вещества (правила / факты в прозе / состояние на дату / инструкции
   установки), приносит разбор, человек подтверждает по пунктам.
5. **Аттестация.** Записанный факт с датой и чек-листом. Требования сверх
   конфигов: папка ai-docs по стандарту (доки фич, ресёрчей, тестирования);
   унификация тестирования (в DoD каждой задачи — как тестировать; API —
   unit/Postman, визуальное — e2e по путям клиента; QA сначала запускает
   автотесты). Неаттестованный проект в пульте — с плашкой, волны туда не
   запускаются.

Порядок включения запрета: сначала аттестуется ai-evolve (это и так DoD
STOVP-59), потом запрет включается — иначе правило остановит единственный
живой проект.

**Личность флота.** Отдельная пара ключей флота; на серверах — отдельный
пользователь с ограниченными правами (логи и чтение; без правки конфигов и
секретов). Даёт аудит «флот, не человек», отзыв одной строкой и забор,
который нельзя обойти с машины. Личность флота — предусловие снятия диалогов
разрешений (раздел 6, шаг 1) и автомержа. Ключи людей остаются для ручных
операций, флоту не положенных.

**Сканер требований — из проекта, не руками.** Список нужных ключей
выводится из конфигов и .env.example; каждый репозиторий держит актуальный
.env.example с комментарием к каждой переменной.

## 8. Фоновые процессы фабрики

Работа без тикета, которая не должна быть похоронена. Запускаются только в
свободные слоты (волны по задачам всегда приоритетнее); находки идут
тикетами в бэклог, никакой самодеятельной починки; расписание и
включённость — ключи конфига.

1. **Пассивный рефакторинг.** Флот свободен → оркестратор берёт строки из
   перечня долга (tech-debt.md): созревшее грумится в тикет, протухшее
   вычёркивается с причиной. Долг перестаёт быть свалкой.
2. **Регулярные e2e-прогоны.** По расписанию полный прогон на предпроде;
   красный прогон = тикет с воспроизведением автоматом. Ловит деградацию
   между релизами, а не только в момент сдачи.

Зависимость: фоновым процессам нужны очередь и пул ресурсов (шаги 2–3
оркестратора) — понятие «свободный слот» существует только там.

## 9. Проверка на трёх сценариях

**(а) Один человек, все роли его, merge_rights=wave.**
Человек — постановщик «один за всех»: приносит идею, подтверждает второй
гриль (карточки в пульте, можно с телефона), отвечает на эскалации,
принимает эпик живым прогоном. Диспетчеры — сессии, исполнители — флот из
его подписок, проверка — другой моделью (кодекс канона сохраняется без
второго человека). Всё остальное — автомат. Модель ложится без исключений;
это и есть ступень 1 продукта.

**(б) Команда ai-evolve сегодня.**
Постановщик — CTO, приёмка — QA (человек), merge_rights на старте —
`dispatcher` (как сейчас), после аттестации и личности флота — переключение
на `wave`. Роль ai-docs выполняет docs-репо — при аттестации сверяется со
стандартом. Ничего в модели менять не пришлось — только значения конфига.

**(в) Чужая команда из 5 человек, свой флоу, кастомная роль.**
Их статусы и колонки — маппинг в конфиге; их роль — карточка по канону
кастомной роли; их уровень доверия — merge_rights=lead. Два острых места:
- нет подписки на вторую модель → ядро «проверяет не автор» исполняется
  ослабленно (другой экземпляр той же модели), аттестация это помечает;
- их привычка «автор мержит сам без проверки» → аттестация отказывает:
  ядро не конфигурируется. Подключение — приведение к стандарту, не приём
  как есть.

## 10. Противоречия, найденные на стыках, и как сняты

| # | Противоречие | Решение |
|---|---|---|
| 1 | Кнопка «запустить»: суждение синьора (57) против автозапуска очереди (58) | план исполнения на груминге; очередь исполняет план; синьор перемечает по ходу |
| 2 | Кнопка «мерж»: «мержит диспетчер» (57) против лестницы merge_rights (59) | правилом владеет конфиг; лестница = степень автоматики; дефолт wave |
| 3 | Очередь не читает «контракты» из прозы груминга | дом зависимостей — связи трекера; бронь будки — сигнал |
| 4 | Снятие диалогов (58) раньше забора (59) | личность флота — предусловие снятия диалогов и автомержа |
| 5 | «Лечится перезапуском» против «диспетчер — живой контекст» | контекст живёт в трекере и будке; память сессии — кэш |
| 6 | У реестра аккаунтов нет дома | ступень 1 — машина; ступень 2 — решить при строительстве сервера |
| 7 | Аттестация останавливает единственный живой проект | сначала аттестация ai-evolve, потом включение запрета |
| 8 | В соло нет хозяина вердикта | вердикт как гейт упразднён; контроль — второй гриль + эскалации постановщику |

## 11. Порядок строительства

Логика очерёдности: каждый шаг стоит на предыдущем; эффект на главную
метрику (параллельность) — с первого шага.

**Шаг 1. Модель работы + усиленный груминг** *(минимальный работающий срез)*
Каноны и скиллы: три уровня, волна = одна подзадача, план исполнения как
обязательный артефакт, второй гриль постановщика, связи-зависимости в
трекере, эскалации простым языком. Дерево пульта из иерархии трекера.
Запуск пока чипами — но по плану исполнения. Замер параллельности на живом
эпике. Инфраструктуры — ноль, эффект — сразу.

**Шаг 2. Пульт владеет процессами** (58, шаг 1)
Запуск/чтение/запись/перезапуск сессий из пульта; чат-окно; правило
«контекст — в трекере» проверяется на перезапусках. Диалоги разрешений пока
остаются (allowlist), полное снятие — после шага 3.

**Шаг 3. Паспорт проекта и забор** (59)
Пять ступеней подключения, секретница, сканер секретов, аудит CLAUDE.md,
личность флота на серверах, аттестация ai-evolve. Открывает снятие диалогов
и автомерж.

**Шаг 4. Самотянущая очередь + пул ресурсов** (58, шаги 2–3)
Очередь исполняет план исполнения через абстракцию трекера; пул аккаунтов и
парковка при лимитах. Параллельность становится числом на экране.

**Шаг 5. Автомерж и фоновые процессы**
merge_rights=wave на аттестованных проектах: зелёный код + DoD не нарушен →
мерж без человека. Пассивный рефакторинг и регулярные e2e в свободные слоты.
Контрольный замер против целей раздела 1.

**Шаг 6. Миграция имён на STOVP** *(последним, решение CTO 16.08)*
Пока строим — два смягчения: в новых ключах, путях и компонентах не зашивать
слово «nyron» без нужды; вести чек-лист переименования (docs/MIGRATION-
NAMES.md) по ходу. Сама миграция:

1. объявление команде и фриз выкатов плагина;
2. смена пути репо в GitLab (Настройки → Общие → Дополнительно → Изменить
   путь); старый путь остаётся редиректом — но на него не полагаться;
3. обновление зеркала GitHub и ссылок установки;
4. переподключение у команды: marketplace remove/add по новому адресу,
   Desktop — удалить/добавить плагин;
5. перерегистрация будки (nyron-hub → stovp-hub) user-scope командой;
6. конфиг проекта: `.claude/nyron-dev.md` → `.claude/stovp.md`; на переходный
   период плагин читает оба имени, старое — с предупреждением; через один
   релиз чтение старого имени снимается;
7. смоук на каждой машине: hub_status отвечает, скиллы видны, волна
   запускается.

## 12. Что меряем после каждого шага

- параллельность эпика (история статусов) — цель от 3×;
- хвост доработок и заходы в Ревью — цели ≤ 4 ч и ≤ 1,3;
- время «вопрос человеку → ответ доехал до сессии» — цель секунды;
- доля мержей без эскалации (мера доверия автоматике);
- на шаге 3: аудитор находит на ai-evolve не меньше трёх реальных
  расхождений (столько нашли руками 15.08).
