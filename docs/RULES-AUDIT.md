# Правила фабрики: как сейчас и как надо

Разбор 12.08.2026 с CTO. Читается сверху вниз: сначала вывод, потом каждая
болезнь отдельной строкой — что записано в канонах сегодня, во что это
превращается на деле и как должно быть.

Задача на исполнение — [STOVP-51](https://nyron.atlassian.net/browse/STOVP-51).

---

## Вывод

Правил у нас **достаточно, и они верные**. Ломает не их отсутствие, а три
вещи: **каноны противоречат друг другу** (волна слушается ближнего),
**исполнитель не знает правил, которые к нему относятся** (принципы кода живут
только у ревьюера), и **часть правил лежит в файле, который никто не
открывает**.

Отсюда часы на простом тикете — при том что почти всё нужное уже написано.

## 1. Ревью: глубина и объём

| | |
|---|---|
| **Как записано** | Промт ревьюера прямо требует: «найди в коде call-sites изменённых функций и параллельные пути к тем же полям» |
| **Что выходит** | Ревьюер уходит во второй–четвёртый слой, приносит лавину находок; каждый круг рождает новые |
| **Как надо** | Смотреть дифф и **прямых потребителей** изменённого. Транзитивные зависимости, соседние подсистемы, архитектура проекта — вне зоны ревью |

## 2. Ревью: что блокирует сдачу

| | |
|---|---|
| **Как записано** | Правила волн: три корзины (ломает путь пользователя → тикет; поведения нет в каталоге → вопрос постановщику; ничего не ломает → долг) и потолок два круга. Правила ревью: «в Ревью тикет уходит только с ПРИНЯТО» |
| **Что выходит** | Прямое противоречие. Волна слушается ближнего документа и чинит всё подряд, включая то, что по канону должно уехать в долг |
| **Как надо** | Ревьюер помечает каждое замечание: **блокер / вопрос замысла / долг**. Вердикт «доработка» — только при блокерах. Долг уезжает списком в `tech-debt.md` и вердикт не двигает |

## 3. Ревью: внешний вид

| | |
|---|---|
| **Как записано** | Про интерфейс в промте ревьюера нет ничего |
| **Что выходит** | Ревьюер предлагает изменения внешнего вида, волна их исполняет — самодеятельность мимо постановщика |
| **Как надо** | Внешний вид и взаимодействие пользователя — **не зона ревьюера**, такие предложения не пишутся вовсе. Отдельно: субагент вообще не решает про интерфейс ([STOVP-48](https://nyron.atlassian.net/browse/STOVP-48)) |

## 4. Тесты: сколько гонять

| | |
|---|---|
| **Как записано** | Политика кода (приходит хуком в каждую сессию): «в цикле — точечно по затронутому; полный набор — один раз на финале тикета; **не гонять полный прогон на каждую итерацию**» |
| **Что выходит** | Правила волн — рабочий документ волны — дают голые команды полного прогона (`test-back-unit`, `npm run test`) без единой оговорки. Побеждает ближний документ: полный набор крутится каждый круг |
| **Как надо** | В правилах волн вместо голых команд — пара: **точечно в цикле** (примеры команд) и **полный набор на финале тикета** (примеры команд). Одна формулировка в обоих документах |

## 5. Принципы кода: DRY, KISS, SOLID

| | |
|---|---|
| **Как записано** | Только в промте ревьюера: дубль механизма — блокер; переусложнение — неблокирующее; KISS и SOLID — «блокер только если прячет баг» |
| **Что выходит** | У автора этих требований нет на входе; ревью ловит постфактум и почти никогда не блокирует. CTO: «не вижу, что применяется» |
| **Как надо** | Перенести в момент написания — в политику кода, тремя проверками вместо трёх аббревиатур: перед новым механизмом показать, почему не подходит существующий; не заводить слой без второго потребителя; правка требует трогать три места — сказать об этом, а не размазать молча |

## 6. Лестница до кода (ponytail)

| | |
|---|---|
| **Как записано** | Взята идея, не плагин: политика кода несёт лестницу дословно (нужен ли код → нет ли уже в базе с пруфом → нельзя ли параметризацией) плюс наш ограничитель — что минимизировать нельзя (дизайн-система, флаги, тесты, проверки доступа) |
| **Что выходит** | **Работает.** Приходит хуком в каждую сессию |
| **Как надо** | Оставить как есть. Причина ограничителя: независимая проверка показала, что «минимизируй всё» без стоп-ступеней режет дизайн-систему и защитный код |

## 7. Мёртвый документ

| | |
|---|---|
| **Как записано** | `nyron-dev/skills/nyron-waves/references/dev-best-practices.md` — 85 строк: лестница, TDD чужой моделью, режимы прогона тестов, матрица моделей |
| **Что выходит** | На него **не ссылается ни один документ плагина**. Волны его не открывают |
| **Как надо** | Живые правила перенести в политику кода и правила волн, файл удалить. Документ, который никто не открывает, устареет и начнёт врать |

## 8. Челлендж плана

| | |
|---|---|
| **Как записано** | Обязателен для каждой волны двумя прогонами (штурм замысла + сверка плана с кодом); мелкой волне — «одним слитым вызовом, но не скипать» |
| **Что выходит** | Ещё несколько минут и токенов на каждый тикет, включая тривиальные |
| **Как надо** | По размеру: S — без челленджа; M — один прогон; L и новый контур — два. Усилие модели ревьюера тоже по размеру |

## 9. Язык канонов

| | |
|---|---|
| **Как записано** | В правилах живут «адверсарный», «триаж», «MECE», «fan-out» |
| **Что выходит** | Читается как белиберда, люди буксуют на терминах |
| **Как надо** | «критика находок», «разбор находок», «без пересечений и без дыр», «веером». DoD и «скоуп» остаются — прижились |

## 10. Формат ответов и отчётов

| | |
|---|---|
| **Как записано** | Требований к форме ответа нет |
| **Что выходит** | Длинные путаные отчёты волн и диспетчеров: жгут токены и время читателя |
| **Как надо** | Вывод первой строкой; одно предложение — одна законченная мысль, понятная не-разработчику; без сленга и воды. На вопрос — контекст, варианты с последствиями и **всегда рекомендованный вариант** |

## 11. Расход шины

| | |
|---|---|
| **Как записано** | Чтение адресное и по курсору — механика верная |
| **Что выходит** | Замер за час: 51% трафика уходит веером (`all`) — 136 тысяч токенов, и это читает **каждая** сессия флота |
| **Как надо** | `all` — только то, что касается всех (смена базы, релизный стоп). Длинное — выжимкой со ссылкой на файл. Задача — [STOVP-47](https://nyron.atlassian.net/browse/STOVP-47) |

## Общий принцип, который вывели из всех двенадцати пунктов

**Правило, которое не проверяется механикой, не исполняется.** Дисциплина
модели ненадёжна по построению: канон про вотчер был написан давно и не
работал, пока не появился хук, который физически не отпускает сессию. Значит
каждое правило из этого разбора должно получить либо проверку в промте, либо
хук, либо стадию конвейера — иначе оно останется текстом.
