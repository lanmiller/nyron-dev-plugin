# Флоу работы по плагину nyron-dev — от идеи до прода

Ридми для постановщика (CTO). Сверено с фактическими скиллами 0.10.0 —
22.08.2026. Каждый этап = один скилл-владелец; этапы не пересекаются и
покрывают путь целиком (MECE).

## Карта одним взглядом

```
ВХОД (3 двери по типу сырья)
  гипотеза («верим, что X улучшит Y»)  → product-flow  (петля HADI)
  решённая фича («делаем X, решено»)   → feature-intake (требование → эпик)
  каша («прилетело от CEO/методолога») → intake-groom  (черновик до человека)
                 │
ПОСТАНОВКА       ▼
  jira-task-standard: форма тикета (7 разделов) и эпика (8), стиль McKinsey
                 │
ДИЗАЙН           ▼
  прототип собирает front-dev на этапе требования (feature-intake);
  новый кусок UI — сразу в дизайн-систему и на витрину (design-system)
                 │
ГРУМИНГ          ▼
  диспетчер (nyron-waves): волны по участкам кода, «паспорт конвейера»
  в каждом брифе; тикет без паспорта в волну НЕ идёт
                 │
РАЗРАБОТКА       ▼
  изолированные ветки/worktree; конвейер тикета = 2 workflow + сессионные
  решения; red-тесты пишет Sol/codex; политика кода (лестница, 3 проверки)
                 │
РЕВЬЮ            ▼
  cross-review (ДРУГАЯ модель, обязателен) + code-reviewer перед мержем
                 │
ИНТЕГРАЦИЯ       ▼
  hub_lock на файлы → мержевая очередь (мержит только голова) →
  «ок» человека на пачку → уборка за пачкой (ветки, локи, статусы)
                 │
QA               ▼
  qa-handoff (эпик → один QA-тикет приёмки) и/или live-epic-testing
  (живой прогон с пользователем, посекундная разметка, находка = тикет)
                 │
ЗАКРЫТИЕ         ▼
  эпик закрывается ТОЛЬКО после закрытия QA-тикета; вердикт гипотезы —
  обратно в канон (петля)
```

Сквозные шины: **Jira** — для людей и истории (брифы, отчёты, вердикты —
комменты); **будка** (nyron-hub) — быстрое общение агентов, локи, очередь
мержа, карточки решений человеку; **папка эпика** в docs-репо — всё, что
длиннее коммента; **память** — memory MCP (аккаунт) + авто-память проектов.

## 1. Вход — три двери (какой скилл открывать)

| Сырьё | Скилл | Что на выходе |
|---|---|---|
| Гипотеза, ставка | `product-flow` | карточка → челлендж другой моделью → эпик → замер → вердикт (Г1–Г5, HADI) |
| Решённая фича, мандат | `feature-intake` | Р1 файл-требование (+вопросы) → согласование → Р2 эпик + нарезка |
| Необработанная каша | `intake-groom` | черновик задачи дешёвой моделью — ДО того, как тратится человек |

Правило: шаги не склеиваются в одну кнопку — между ними живёт согласование.
Гипотезу обязана попытаться развалить другая модель (Г2) до того, как на
неё потратят разработку.

## 2. Постановка — стандарт тикета

`jira-task-standard`: тикет — 7 обязательных разделов, эпик — 8; стиль
McKinsey (вывод первым, одна мысль — одно предложение); конвенции трекера
(типы, статусы, лейблы) — из конфига проекта `.claude/nyron-dev.md`, не
хардкод. Тикеты заводят и люди, и скиллы — форма одна.

## 3. Дизайн

- Прототип фичи собирает агент `front-dev` на этапе требования — живой
  кликабельный, не макет; волна обязана переиспользовать его компоненты
  (STOVP-53), а не перерисовывать.
- Канон CTO: любой новый кусок UI — сразу компонент дизайн-системы
  (app.css) и на витрину /design (скилл `design-system`).
- Честная дыра: отдельного этапа «дизайнер в Figma» во флоу нет — при
  необходимости надевается роль `ux-designer` (team-roles).

## 4. Груминг под исполнение — диспетчер

`nyron-waves`, диспетчер ТОЛЬКО грумит и оркеструет (код не пишет):
- волны нарезаются **по участкам кода** — тикеты одной волны = один
  участок, чтобы волны не толкались в файлах;
- каждый бриф несёт **«паспорт конвейера»** (готовые args обоих workflow);
  паспорт не собирается без вопросов → тикет в волну не идёт, дорабатывается
  постановка;
- **масштаб исполнения выбирает диспетчер**: тривиальное — лайт-конвейер;
  среднее — субагенты/тимейты внутри сессии; большое — отдельные
  сессии-волны через пульт (можно на разных подписках — параллельные лимиты).

## 5. Разработка — принципы кода

- **Изоляция**: каждая волна — своя ветка + worktree от main.
- **Политика кода** (SessionStart-хук, всем сессиям): лестница до кода
  (нужен ли / нет ли уже с пруфом / нельзя ли параметризацией), три
  проверки при написании (не дублируй механизм; не заводи слой без второго
  потребителя; трогаешь три места — скажи вслух), легаси — три исхода,
  флаги — только новой флоу-фиче и сразу с тикетом на снос.
- **`quality_floor` не минимизируется**: компоненты дизайн-системы, флаги,
  тесты с регистрацией, проверки доступа.
- **Конвейер тикета** = 2 workflow (механика на дешёвых моделях) +
  сессионные интерлюдии (решения на дорогой); red-тесты по DoD пишет
  Sol/codex, не Claude; телеметрия стадий — в metrics.jsonl.
- **Багфикс — только через корень** (с 0.11.0, из superpowers:
  systematic-debugging): воспроизвести → локализовать → назвать причину;
  фикс без названного корня — блокер на вердикте диспетчера, корень —
  строкой в отчёт и в DoD тикета-бага.
- **Тесты**: точечно в цикле, полный сьют — один раз на финале.

## 6. Ревью — два слоя

1. `cross-review` — **обязательный**: написанное Claude проверяет ДРУГАЯ
   модель (codex/GPT) перед сдачей тикета в Ревью и на вердикте диспетчера.
   Находки разбираются протоколом «спор моделей»: проверить → принять или
   отвести с пруфом, поддавки запрещены (развёрнуто —
   superpowers:receiving-code-review).
   ⚠ Пока это уговор, не механика — 22.08 psylia его срезала (заменила
   своим адверсарным ревью). Кандидат в гейт: без отметки cross-review
   тикет не уходит в Готово.
2. `code-reviewer` (агент) — ревью перед мержем.

## 7. Интеграция — мержи и пуши

- `hub_lock` на свои файлы при старте волны → `hub_unlock` после пуша.
- **Мержевая очередь** (hub_merge_join): мержится только голова очереди,
  остальные ребейзятся, став головой. Никаких «десять веток разом».
- **Кто сливает в main — `merge_rights` конфига проекта**: лестница
  wave | dispatcher | lead | cto (нет поля → dispatcher).
- Пачка мержится только после **явного «ок» человека** — «ок» запрашивают
  напрямую, а не ждут молча.
- **Уборка за пачкой** — шаг жизненного цикла, не добрая воля: ветки,
  локи, статусы, worktree.
- Руками модели пульт не мержит никогда: кнопки git-панели — человек,
  ветки — сессии по правам.

## 8. QA

- `qa-handoff`: все тикеты эпика в «Готово», predprod смоукнут → эпик в
  «Готово к тестированию» + ОДИН понятный QA-тикет приёмки (путь
  пользователя целиком). Эпик закрывается только ПОСЛЕ закрытия QA-тикета.
- `live-epic-testing`: живой прогон с пользователем — карта флоу,
  посекундная разметка, находка = тикет сразу.

## 9. Надзор (сквозной, кодом + судья)

Пульт: гейт паспорта на старт, чек-ин по трём лентам, автосудья
(deepseek) при застревании + автопинок «сдал — передавай, нет — продолжай»,
толкач финала «ветка не влита», триаж мёртвых карточек, автовыбор подписки
по лимитам. Оркестратор — любое окно Claude Desktop (код-режим): тулы
`pult_*` + SessionStart-контекст.

## Роли (team-roles) и конфиг

Роль надевается первым ходом (`roles.<slug>` конфига → карточка роли);
реестр внешних участников (без плагина) — тоже в конфиге; любой скилл
сверяется с конфигом проекта (`project-config`) ДО работы.
