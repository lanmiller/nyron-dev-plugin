# SYSTEM: процесс разработки на плагине nyron-dev

Статус: черновик на ревью (CTO + Sol), собран 08.08.2026 из решений CTO.
Канон системы — этот файл в репе плагина. Проектная конкретика (имена
статусов доски, id переходов) — проекциями в доках проектов
(ai-evolve: `ai-evolve-docs-test/shared/work-route.md`). Детальная спека
инструмента — `docs/specs/2026-08-08-morda-pult.md`.

## Цель

Систематизировать и автоматизировать разработку — сначала nyron
(ai-evolve), затем psylia, дальше любой проект через конфиг плагина.

Целевой режим: **поставили задачу → агенты пошли сами** — приняли решения
уровня диспетчера, написали код, прогнали тесты, сдали на ревью — всё в
едином пошаговом процессе, где ничего не рассыпается. Человек нужен в
точках решения, а не для перетаскивания тикетов. Ресурс — пул подписок
(подход жрёт токены; масштабируемся не «умнее», а «шире» — параллелим в
десятки потоков).

Мера удобства: пользователю в морде так же удобно, как в Claude Desktop —
кинуть файл и картинку, увидеть браузер сессии и потыкать в него, залезть
в файлы, с которыми сессия работает.

## Роли

### Люди — владеют решениями

| Роль | Зона решения |
|---|---|
| Постановщик / CTO | что делаем, приоритет, go на мерж, разбор процесса |
| Продакт / методолог | зачем делаем, ценность, сценарий пользователя |
| Разработчик / техлид | как сделано; технический слой груминга |
| QA | принято или нет; единственный, кто ставит «Готово» |
| SRE | стенды, деплой, конфиги |
| UX | макет (штатного дизайнера нет — роль надевается) |

### Агенты — владеют работой

| Роль | Что делает | Где живёт |
|---|---|---|
| Сессия-исполнитель | ведёт один тикет от плана до сдачи | tmux (Мак / контейнер) |
| Сессия-диспетчер | координация эпика: пересечения зон, очередь мержа, релиз волн. НЕ гейт — тикеты двигаются без него | tmux, только при эпике волнами |
| Зональный субагент | пишет код (front-dev / backend-dev / langgraph-dev) | внутри исполнителя |
| Sol (codex/GPT) | челлендж плана, red-тесты, кросс-ревью | три шага конвейера |
| QA-борт | сверка DoD ↔ тест-кейсы, дописывает и гоняет | проект В (строится) |
| Интейк | сырьё → черновик тикета по стандарту | дешёвая модель |
| Надзиратель | состояния всех сессий, ловля молчунов, витрина | Haiku headless по расписанию |

Принцип: **человек владеет решением, агент владеет работой**. На каждом
шаге ровно один человек отвечает за исход и ровно одна сессия делает.

## Маршрут работы (канон; имена статусов — проекция проекта)

| # | Шаг | Assignee | Что происходит | Выход |
|---|---|---|---|---|
| 0 | вне трекера | — | интейк чистит сырьё | черновик + вопросы автору |
| 1 | Постановка | продакт/CEO/CTO | крутится гипотеза/фича, рождается дизайн | решение делать → Бэклог или сразу в работу |
| 2 | Бэклог | постановщик | решено, но не сейчас | — |
| 3 | К выполнению | пусто (очередь) | технический слой дотягивает разработка; владелец груминга — техлид/CTO (по ревью Sol: у шага должен быть владелец) | тикет готов к взятию |
| 4 | В работе | исполнитель | чекпойнт «план реализации» (Fable штурм + Sol челлендж) → red-тесты Sol → код субагентом | ветка запушена, тесты зелёные, `code:ветка` |
| 5 | Ревью | исполнитель | кросс-ревью Sol → вердикт ПРИНЯТО; E2E; отметка [AI-прогон]/[руками] | `ask` «мержить?» → go человека → мерж → CI предпрод → `code:предпрод` |
| 6 | Готово к тестированию | QA | QA-борт: DoD ↔ тест-кейсы, дописать, прогнать | очередь человека-QA |
| 7 | Тестирование | QA | человек по сценарию из тикета | пройдено / дефект |
| 8 | Доработка | исполнитель | фикс | обратно в Ревью (не в «В работе») |
| 9 | Готово | QA ставит | — | — |

Гейты-инварианты:

- assignee меняется вместе со статусом, без исключений;
- 5→6 только при вердикте Sol ПРИНЯТО И метке `code:предпрод` (QA нечего
  тестировать на невлитой ветке); **вердикт привязан к SHA головы ветки**
  и действителен только для него — после любого нового коммита нужен
  новый вердикт (по ревью Sol: иначе протухший ПРИНЯТО открывает гейт);
- возвраты — внутри того же тикета (7→8→5); тикеты «проверить фикс X» не
  заводятся;
- «Готово» ставит только QA; постановщик отпускает тикет на шаге 3 и
  обратно не получает — вопросы к нему идут через морду;
- эпик едет той же лестницей агрегатом; **сквозной сценарий эпика
  прогоняется ДО закрытия последнего дочернего тикета** (по ревью Sol:
  иначе провал сквозного прогона нечем возвращать — дети уже в Готово);
  провал → дефекты в ещё открытые тикеты либо новый тикет эпика.

Форма постановки — два слоя, два владельца:

- **продуктовый слой обязан дать автор** (кто угодно, кто добавляет
  функционал): что делаем / зачем (JTBD) / как работает / дизайн блоком /
  DoD / сценарий тестирования;
- **технический слой дотягивает разработка** на груминге: техконтекст,
  декомпозиция, где лежат тесты.

Оси не путать: статус работы ≠ состояние кода. Код — метками
`code:ветка → code:предпрод → code:прод`; журнал релизов в прод: что
влили, какие тикеты, какие ветки (для отката ветки волны).

Граница: не вся работа команды в трекере — методолог собирает плейбуки в
продукте, дизайнер правит макеты. Система показывает флот агентов, а не
занятость людей.

## Морда — как это выглядит для человека

Один слой доступа, три лица: **морда-сайт** (люди), **fleet-MCP**
(агенты: Desktop-Клод пользователя, локальные CLI, сами сессии), **гонец**
(Телеграм). Desktop не обязателен, но осмыслен — разговорный клиент
fleet-MCP.

Экран: вкладка на проект (nyron, psylia, …), в каждой две зоны —
**«ждут вас»** (карточки `ask`: вопрос одной строкой, варианты с
следствиями, контекст на экран, штамп базы, срочность; ответ — номером) и
**«идёт работа»** (строки сессий с состояниями от надзирателя).

У сессии три канала: **Окно** (рендер транскрипта: маркдаун, плашки
инструментов, дерево субагентов; ввод через tmux), **Терминал** (tmux как
есть, attach руками), **Экран** (фаза 2: общий Chromium контейнера через
noVNC — обе пары рук в одном браузере). Паритет с Desktop-чатом: вложения
падают в worktree сессии (в tmux уходит путь), рядом — обозреватель
файлов worktree (read-only + diff к origin/main).

Дисциплина и надзор: сессия, задавшая вопрос человеку, обязана оформить
`ask` в будке; Haiku-надзиратель по расписанию читает хвосты транскриптов
и будку, ставит состояния (работает / ждёт решения / ждёт молча /
замолчала / умерла), заводит `ask`-заглушки за молчунов, публикует
витрину-артефакт (read-only сводка для телефона). Гонец: карточка сразу →
Телеграм («блокирует» >30 мин, «может подождать» >2 ч) → повтор раз в час
одной сводкой; ночью молчит, кроме «горит».

Будильник: ответ живой сессии — `send-keys` в её tmux; мёртвой — новая
сессия с брифом = `ask` + решение + штамп базы; первое действие поднятой —
`git fetch` и сверка с origin/main (урок KAN-109: не писать отчёт про
мир, которого нет).

Запуск — только по **профилям** плагина (проект-cwd, модель, effort,
режим прав, MCP-набор, бриф, штамп) — наследник /goal-чипов; сессия не
может родиться не в той папке или без будки.

## Как это используется — сценарии по ролям

**CTO/постановщик:** утро — морда, зона «ждут вас»: 3 решения. Ответил
номерами за 5 минут. «Делаем DEV-1200» — профилем поднялась сессия в
нужном проекте. Днём Телеграм: «блокирует: мержить пачку Б?» — открыл
карточку, глянул окно сессии, ответил. Вечером витрина с телефона.

**Разработчик:** видит те же вкладки; поднимает исполнителей под свои
тикеты; в чужую спящую сессию заходит resume/fork (в живую пишут только
через морду — правило одного писателя); перехват руками — attach.

**QA:** очередь «Готово к тестированию» — тикеты с отметками
[AI-прогон]/[руками]; QA-борт уже сверил DoD и дописал тесты; дефект →
«Доработка» на исполнителя, тикет не плодится.

**Продакт:** заводит тикет с продуктовым слоем (6 блоков); дальше его
работа — «Постановка», реализация едет без него; вопросы приходят
карточками.

**Sol:** не двигает статусы, отвечает за три шага (челлендж плана,
red-тесты, кросс-ревью) — «кто писал, тот не проверяет».

## Инфраструктура

**Фаза 1 — локально (Мак CTO):** tmux + транскрипты + будка (hub.db на
проект) + Haiku-надзиратель + морда (SvelteKit, 127.0.0.1, без паролей) +
гонец. Даёт: один экран на 25 сессий, запросы решений, будильник,
Телеграм, подъём осиротевшей работы.

**Фаза 1.5 — телефон:** доступ к той же морде через Telegram Mini App:
бот один на всё (гонец шлёт уведомления, тап открывает мини-апп),
авторизация — криптографическая подпись initData + whitelist tg-id;
транспорт — туннель (tuna) к локальному серверу. Голый туннель без
авторизации запрещён: морда — руки, не глаза. Ограничение честно: Мак
спит — всё спит. Контейнеры с Claude, уже живущие на Маке (docker),
встают в схему как есть — tmux внутри, транскрипты томом наружу; это
локальная обкатка контейнерного образа до всякого сервера.

**Фаза 2 — сервер: ОТЛОЖЕНА до триггеров** (решение CTO 08.08 после
ревью Sol). Триггеры расконсервации — любой из двух: (а) ноутбук стал
узким местом — сессии должны переживать его сон и быть доступны команде;
(б) лимиты одной подписки регулярно упираются (сегодня неделя — 78%).
До тех пор — флот контейнеров (CLI+tmux+Chromium+noVNC, по
подписке на контейнер; логин живёт долго — смоук на первом). Хранение —
гибрид: общее на хосте (bare-зеркала реп, будка, реестры), своё у
контейнера (чекауты/worktree; HOME на именованном томе — носитель
«сессии — командный актив»). Реестры: сессий (тикет↔сессия↔контейнер↔
человек↔транскрипт↔штамп; история эпика = выборка) и контейнеров
(подписка, занятость, лимиты через `/usage` в tmux — точные проценты и
время сброса). Подбор контейнера — алгоритм над реестром. Правда — только
origin; контейнеры расходники. Морда — та же папка на сервере, за VPN.

Экономика: пул подписок; разбивка `/usage` (subagent-heavy, >150k
контекст, длинные сессии) складывается в реестр — видно, куда уходит
лимит.

## Почему не рассыпается — сквозные скрепы

1. Правда в долгоживущих хранилищах: origin (код), Jira (задачи), будка
   (решения), тома (сессии). Смертны только процессы.
2. Штамп базы в каждом сообщении — расхождение срезов видно сразу.
3. `git fetch` перед выводами у каждой поднятой сессии.
4. Машинные гейты вместо дисциплины: вердикт Sol комментом, метки кода,
   assignee-по-статусу, надзиратель против молчунов.
5. Профили запуска вместо ручного набора.
6. Один писатель в живую сессию; спящую поднимает любой.

## Порядок строительства (фаза 1, этапы сдаются по одному)

1. `ask`/`decision` в будке + штамп базы + правило дублирования вопроса.
2. Надзиратель (Haiku по расписанию) + витрина-артефакт.
3. Морда-список: вкладки, «ждут вас», ответ номером → будильник.
4. Окно: рендер транскрипта + ввод через tmux + вложения в worktree.
5. Терминал в браузере (мост: ttyd / node-pty — решить здесь).
6. Гонец: Телеграм.

Параллельно процессным треком: правки доски (проекция проекта), релиз
скиллов под новый маршрут, проект В (QA-борт и формы документов).
