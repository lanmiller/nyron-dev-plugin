# Разбор плагина и пульта от и до — под STOVP-узел

Дата: 07.09.2026. Статус: разбор на решение CTO. Кода нет.
Основание: разговор с CTO 07.09 (вайб как дефолт, «куча сессий на вайб»,
ветка всегда, пульт нужен для удалённого управления, «крутые штуки» —
ключница, конфиги, канон CLAUDE.md, перенос настроек — не выбрасывать);
спека `docs/specs/2026-09-07-vibe-first.md` (три редакции за день);
инвентаризация `nyron-dev/hub/` (26 файлов, ~3850 строк) и `morda/`
(15 серверных модулей, ~4500 строк) двумя агентами; все 11 скиллов
прочитаны целиком.

## 0. Рамка

**Целевой STOVP — не VISION 28.07, а то, что построено с августа плюс
вычитание.** VISION планировал демон `stovpd` с очередью job'ов, headless-флот
с лимит-планировщиком, Claudexor, консилиум трёх семей. Всё это решает задачу
«N автономных сессий координируются без человека». Под моделью «рабочая сессия
в worktree на выбранной подписке, Fable пишет, Astra проверяет, человек за
экраном или в пульте с телефона» координировать нечего. Этапы 3–5 VISION
снимаются с дорожной карты, не откладываются.

**STOVP = рабочее место + узел + канон.**

| Слой | Что это | Где живёт |
|---|---|---|
| Рабочее место | пульт в браузере: флот сессий, экран, ввод, карточки вопросов, git-панель; доступ снаружи | `morda/` |
| Узел | машина, на которой безопасно живут много сессий на разных подписках: слоты, ключница, паспорт, забор, конфигуратор, перенос настроек | `morda/` + хуки плагина |
| Канон | как ставить задачу и как её делать: продуктовый борт, стандарт тикета, рабочая сессия, ревью, приёмка | плагин `stovp` |

**Два плагина, не переименование.** Новый плагин `stovp` в том же маркетплейсе;
`nyron-dev` замораживается на 0.14.x без новых фич и доживает у проектов, что
не переехали. Переключатель — паспорт проекта: `plugin.name` в
`.claude/passport.json` говорит, какой контур у проекта; на проекте стоит ровно
один (два столкнутся SessionStart-хуками и именами скиллов). Переезд проекта =
прогон аудитора → паспорт → ключница → конфиг → канон CLAUDE.md (§6).

**Критерии вердиктов.** Каждому компоненту один из: ОСТАВИТЬ · УЖАТЬ ·
СЛИТЬ · ПЕРЕНЕСТИ · ПО КНОПКЕ (выключить из автомата, оставить вызов) ·
АРХИВ. Вопросы, которые задавались каждому: (1) он обслуживает одну рабочую
сессию с человеком или координацию многих сессий? (2) это механизм (хук,
скрипт, проверка фактом) или памятка? (3) им пользуются по факту?

## 2. Скиллы поштучно

### 2.1 `work` — новый, из `vibe` + `nyron-waves`

`nyron-waves` — 1478 слов тела плюс 1587 протокола плюс 2462 в шаблонах и
примере. Из них про координацию многих сессий (чипы, будка-вотчеры, бронь,
очередь мержа, ребаланс, Jira-шина ревью, паспорт конвейера, два Workflow) —
больше половины. Это уходит. Но в скилле лежат **уроки, оплаченные
инцидентами**, и они не про флот. В `work` они переезжают одной строкой
каждый:

| Урок (откуда) | Строка в `work` |
|---|---|
| пре-флайт human-гейтов (KAN-209, 6,5 ч простоя) | на старте эпика — список того, что машина не сделает (ключи, OAuth, DNS, оплаты) — постановщику одним вопросом ДО работы |
| «не нарезать на вырост» | в задачу не закладывать опции под несуществующее требование |
| багфикс только через корень (superpowers) | фикс без названного корня — блокер ревью |
| «ок не ждут — запрашивают» (07.08, пачка простояла) | готово к мержу → явный вопрос с составом и рисками, не строка «жду ок» |
| мандат на мерж вперёд (KAN-209, 2–3 ч на стыках) | при старте спросить: «зелёная Astra + зелёный CI ⇒ мержу сама?» |
| r1 полный, r2+ по диффу, раунд без новых находок — стоп (НБ-1, 20% времени) | правило повторного ревью |
| полный сьют один раз на финале (KAN-164/165/167) | как есть в `code-policy` |
| QA-блок в комменте сдачи (требование CTO 10.08) | форма сдачи: автотестами / руками / техническое |
| товарищи-агенты не возвращают результат (21.08, 45 мин) | параллель — обычными субагентами с отчётом; фоновые товарищи — только для работы, чей результат не нужен |
| фоновый долгий процесс — сказать человеку в том же ходе (21.08) | молчание при живом фоне неотличимо от смерти |
| уборка за собой (wave-cleanup) | финал: `git merge main` → тесты → Astra → мерж → `worktree remove` |
| спор с ревьюером — воспроизвести, сверить с границами, ответить письменно | как в `cross-review`, ссылкой |

Плюс из `vibe` целиком: роль и канал, что выключено, что несгораемо,
git-механика, финал «закругляемся». Плюс из agent-skills: шесть операционных
правил, таблица рационализаций, red flags, verification.

Структура `work` (≤600 слов): зачем → когда (и когда НЕ: §3 границы) → вход
(чип `/goal` из планирующей сессии с пятью снятиями, или мелочь без тикета)
→ первый ход (worktree, стенд, зона правки) → ход **без вопросов человеку:
сомневаешься — реши, запиши, покажи в сводке** → финал задачи →
рационализации (в первую очередь «спрошу человека — так надёжнее» и «срежу
проверку — так быстрее доеду») → red flags → verification.

Что НЕ переезжает: чипы `/goal`, `hub_lock`, очередь мержа, ребаланс волн,
`max_parallel_waves`, «паспорт конвейера» в брифе, два Workflow (тестген,
импл) как обязательная механика, телеметрия `metrics.jsonl` (замер §9 идёт по
вердиктам Astra и срабатываниям забора, не по JSONL стадий), роутинг
Fable-решения/Opus-код (в рабочей сессии одна модель — та, что выбрал человек).

### 2.2 `cross-review` — ОСТАВИТЬ как есть

Скрипты `cross-review.sh` / `plan-challenge.sh` / `engine.sh` — самая
инженерно чистая часть плагина: выбор ревьюера по окружению, read-only, размер
→ усилие, машиночитаемый вердикт, три метки с границами, потолок семь
замечаний, глубина один слой, отчёт об отказе в канал ошибок. Промт уже
содержит семь проверок по убыванию важности и явную «не зону» ревьюера. Пять
осей и severity-метки из agent-skills **не нужны** — они беднее (спека
`vibe-first` §2.4 п.3 в этой части снимается).

Правки: секция «Встраивание в конвейер волны» → короткая «Встраивание в
`work`» (когда до мержа, когда фоном — `review.gate`); упоминания диспетчера →
постановщик/сессия; второй контур (челлендж плана) остаётся для эпиков.

### 2.3 `jira-task-standard` — ОСТАВИТЬ

Форма задачи (7 разделов) и эпика (8), стиль, приём бизнес-задачи, чек перед
сохранением — всё нужно и в вайбе (CTO: «спека и эпик — факт нужно»). Правки
точечные: «паспорт конвейера собирается без вопросов» → «`work` берёт тикет без
вопросов»; «канон перехода — nyron-waves» → `work`; superpowers-секция остаётся
(мягкая деградация).

### 2.4 `feature-intake` — УЖАТЬ

839 слов, из них ~450 — механика прототипа: роут `/design-system/proto/`,
встроенный браузер, вьюпорт, перезагрузка вкладки, самопроверка, чистый вид,
мерж прото в main, варианты дизайна, ролевые линзы, предохранители гриля. Это
ценные уроки пилота 04.08, но они читаются только когда фича с интерфейсом.
Прогрессивное раскрытие: тело — Р1/Р2 с шагами и правилами, `references/
prototype.md` — механика прототипа и вариативность, `references/grill.md` —
предохранители гриля. Шаг Р2.6 «передать в доставку: nyron-waves» → `work`.

### 2.5 `product-flow`, `intake-groom`, `team-roles`, `live-epic-testing`, `qa-handoff` — ОСТАВИТЬ

Только ссылки: `nyron-waves` → `work`; «draft в волну не входит» → «`work`
не берёт draft»; в `qa-handoff` «диспетчер собирает» → «сессия собирает».
`team-roles` остаётся скиллом, не папкой референсов (спека `vibe-first` §5 в
этой части снимается): продуктовые скиллы зовут роли по протоколу надевания, и
это работает.

### 2.6 `project-config` — УЖАТЬ; `onboard` — новый

Тело `project-config` — на две трети перечень «какой ключ какой скилл читает».
Это схема, её место в `assets/config-template.md` (там она уже есть
комментариями). Остаётся: два файла, протокол чтения, мягкая деградация,
секреты. Новые ключи: `guard.prod` (хосты и строки подключения прода),
`review.gate: behavior | always | never`, `work.port_base`, `trace: jira |
changelog | none`, `intake: tasks | product`, `qa: model | human`. Секция
`models` становится **оверрайдом** карты машины `~/.stovp/models.yaml`
(спека §2.6): в проекте только отличия. Уходят: `max_parallel_waves`,
`models.dispatcher/wave`, `merge_rights: wave | dispatcher` → `session |
human`; клички моделей из скиллов (`Astra`, `Fable`) → роли (`review`,
`work`).

`references/setup.md` (одноразовые шаги) и аудитор проекта (§6) сливаются в
скилл **`onboard`**: подключение проекта к стандарту и переезд с `nyron-dev`.

## 3. Хуки

| Событие | Сейчас | Стало |
|---|---|---|
| SessionStart | `code-policy.md` + `version-check.sh` через `guard.sh` | то же; в политику — шесть операционных правил (допущения вслух, стоп при противоречии, scope, «кажется верным» не пруф, не поддакивать, evidence) |
| Stop | `hub-rearm.sh hook` — взвод вотчера, `decision:block` если не взвёлся | **снят**. Ответ на `hub_ask` доставляет пульт прямым вводом (`injectSend`), запаркованную поднимает резюмом. Сессия без вотчера ничего не теряет |
| PreToolUse | нет в плагине; `morda/guard/pretooluse-guard.mjs` только bypass-сессиям раннера | **в плагин**, для всех сессий проекта с паспортом. Пять правил: снос вне корня и `sudo`; силовой пуш; запись вне корня; ssh/scp/rsync на боевые алиасы; **данные прода** — обращение к хостам/URL/алиасам из `guard.prod` конфига (`psql`/`mongosh`/`supabase --project-ref` прода, миграции против прода) — deny. Плюс ключница `.secrets` как сейчас |

Раннер пульта продолжает подкладывать свой settings-файл с забором для
bypass — двойная страховка не мешает; источник кода забора один (плагин),
пульт ссылается на него.

`guard.sh` / `error-report.*` — ОСТАВИТЬ: канал ошибок инструментов в будку
читает пульт, это единственный способ увидеть «скрипт упал» не из жалобы.

## 8. Требования к скиллам `stovp`

- фронтматтер `name` + `description` ≤ 600 знаков без пересказа метода
  (`skills-lint.py`);
- секции: зачем → когда и когда НЕ → процесс → рационализации → red flags →
  verification (анатомия agent-skills);
- тело ≤ 600 слов; справочники отдельными файлами;
- `evals/cases/<skill>.json`: три позитивных, два негативных промпта;
  прогон — `skills-lint.py --evals` лексически (описания короткие, TF-IDF
  под кириллицу не нужен — достаточно «каждый позитивный промпт ранжирует
  свой скилл первым по пересечению слов»).

1. **Манифест как единый источник** — не новый формат, а два уже
   существующих файла с расширением: `.claude/passport.json` (проект:
   плагин, скиллы, MCP, ключи) и `morda/canon.json` (машина: что стоит у
   всех). Из них рендерить конфиги **всех** харнессов, не только Claude:
   `render codex` → `.codex/config.toml` с MCP через тот же загрузчик
   ключницы. Bridle — кандидат в зависимость для трансляции skills/agents/MCP
   между харнессами (принцип VISION «готовое вместо своего»); ключи и
   правила он не носит — это наше.
2. **Doctor** (§6): сверка «стоит ↔ требуется» по манифесту для каждого
   харнесса, report-only, кнопка в пульте. Сегодня матрица конфигуратора
   делает это для Claude.
3. **Хост**: пульт уже веб-сервис; образ Debian + Claude Code собран 11.08;
   с worktree на сессию контейнер ничего не ломает. Открыт с роадмапа один
   вопрос — переносится ли авторизация Codex (`~/.codex/auth.json`) в
   контейнер; проверяется за час. Э3 «узел в контейнере» возвращается в план
   как «хост», не как «ферма».

### 11.3 Продукт или инструмент — порядок

Строить для других дороже втрое: мультипользователь, вход, упаковка,
онбординг без нас рядом. Порядок, при котором ничего не выбрасывается:

1. **Узел для себя на хосте** (релизы `stovp` 0.1–0.4 из §9 плюс п.1–3
   выше): команда кодит удалённо через пульт, Codex и Claude с одного
   манифеста. Это dogfood и одновременно «убийца» BridgeMind для своих.
2. **Замер**: сколько сессий в день, сколько проектов, сколько раз
   пригодился doctor, сколько людей команды вошли без нас.
3. **Решение о продукте** — по замеру, с формой: open-source узел
   (Conductor/Bridle живут так) плюс платный hosted-пульт, либо закрытый
   десктоп как BridgeMind. Сейчас не решать.

Что не менять ради продукта: канон разработки (продуктовый борт, стандарт
тикета, `work`, кросс-ревью) остаётся плагином и опцией, а не ядром продукта —
у чужой команды свой флоу, узел им нужен и без нашего канона.
