# Аудит проекта — промт сессии-аудитора (STOVP-59, ступени 1–5)

Статус: драфт на согласование CTO, 18.08.2026. Это «что, где и зачем»
человеческим языком + сам промт в конце. Аудит — то, чем собирается
паспорт проекта: сессия запускается из пульта кнопкой у проекта
(«подключить проект» / «аудит»), проходит пять ступеней, каждая — ворота
на следующую. Выход — паспорт, ключница, чистые правила и зелёный прогон
«проверить готовность».

## Принципы (короче некуда)

1. **Аудитор читает всё — не правит ничего молча.** Любая правка канона
   (CLAUDE.md, AGENTS.md, перенос файлов) — списком предложений, человек
   подтверждает по пунктам. Машина канон не меняет.
2. **У каждого факта один дом**: канон команды (git) / машина / ключница
   проекта `.secrets/` (gitignored) / живое состояние (пульт).
3. **Проверка — фактом, не галочкой**: MCP отвечает вызовом, SSH ходит,
   тест запускается, ключ лежит. «Настроено» без вызова не считается.
4. **Секреты в отчётах не показываются никогда** — только имена
   переменных и статус «задано / не задано».
5. **Вопросы человеку — пачкой на развилках**, формами в пульте (HITL),
   а не по одному в час. Аудитор сначала собирает факты, потом спрашивает.

## Ступень 1 — карта проекта

Что делает: проходит весь репозиторий, не только конфиги.

- **Структура**: монорепо / мультирепо-чекаут (как ai-evolve: субрепо в
  подпапках), где чьи `.git` и `.gitignore`. От этого зависит, где живут
  паспорт и ключница (дефолт: в корне рабочего чекаута, один на проект).
- **Стек и сервисы**: фронт, бек, агенты, воркеры — и КАК ОНИ СВЯЗАНЫ
  (кто кого зовёт, по каким портам/каналам). Схема связей — обязательная
  часть карты: без неё правила «как у нас фронт говорит с беком» негде
  проверять.
- **Как запускается / собирается / тестируется**: команды dev-сервера,
  билда, тестов (unit / integration / e2e), докер. Команды идут в паспорт
  как проверяемые фактом (запустил — работает), а не как проза.
- **Документация**: есть ли отдельная папка доков (у нас — docs-репо,
  стандарт ai-docs), где лежат тесты, юз-кейсы, e2e, Postman-коллекции.
  Нет структуры — кандидат в предложения ступени 4.
- **Агенты для LLM**: `.claude/agents/`, AGENTS.md, промты в коде — что
  есть, чем пользуются, что протухло.

Выход: **карта проекта** (файл в доках проекта) + черновой список того,
что поедет в паспорт. Ворота: карта есть — идём искать секреты.

## Ступень 2 — секреты, включая захардкоженные

- Сканер по всему дереву: паттерны токенов (Atlassian, OpenAI, GitHub,
  GitLab, AWS…), приватные ключи, пароли в URL — в коде, docker-compose,
  фикстурах, старых скриптах, конфигах агентов.
- **И по git-истории**, не только по рабочему дереву: секрет, который
  когда-то коммитили, уже скомпрометирован.
- Инвентарь env-файлов: все `.env*` по подпапкам + прямые значения
  подключений (базы, серверы, ключи) в коде.

Выход: список «где лежит, что это, живой ли». **Захардкоженный секрет —
блокер ступени**: сначала вынос в ключницу и ротация, потом дальше.

## Ступень 3 — сборка: ключница, конфиги, инструменты, доступы

**Ключница.** `.secrets/` в корне, gitignored фактом (`git check-ignore`).
Env-стратегия — вопрос человеку (форма):

- одно место (`.secrets/` + указатели из подпапок), или
- по env-файлу на подпапку/сервис (мультирепо так живёт естественнее), или
- оставить готовые как есть и только описать их в паспорте.

Каждому env — `.env.example` с комментарием к КАЖДОЙ переменной;
расхождение example ↔ реальный env дальше видно механически.

**Инструменты проекта** — в паспорт: MCP-серверы (со смоук-вызовами),
плагины (+мин. версии), скиллы, агенты. `.mcp.json` — указатель без
значений, ключи через загрузчик ключницы.

**Глобальное vs проектное** (вопрос «джира глобальная и в проекте»):
правило — **нужен проекту → объявлен в паспорте и стоит project-scope с
ключами из ключницы ЭТОГО проекта**. Глобальная копия на машине может
жить для сессий вне проектов; при совпадении имён project-scope
перекрывает глобальный — конфликта нет. Аудитор флажит одно: проект
МОЛЧА полагается на глобальный инструмент (работает у тебя, падает у
новичка) — это и есть «как получится на машине», паспорт это запрещает.

**Инструменты с машинной половиной — Обсидиан и граф кода.** У обоих
дом двойной, аудитор разделяет:

- **Обсидиан** (поиск знаний по докам): приложение и его плагины —
  дом «машина» (аудитор проверяет «установлен/нет» и говорит, что
  поставить); а вот КАКОЙ вольт и на какие папки проекта он смотрит —
  проектный факт, едет в паспорт. Смоук фактом: `smart-connections`
  отвечает lookup-ом по докам проекта, `obsidian-mcp-tools` читает
  заметку. Обсидиан не установлен/вольт не тот — карточка починки, а не
  молчаливый фолбэк на grep.
- **codebase-memory** (граф кода: кто вызывает, где дубль): сервер стоит
  user-scope, но проект в паспорте объявляет, КАКИЕ репозитории обязаны
  быть в индексе. Смоук фактом: `list_projects` отвечает, репо проекта в
  списке, и `head_sha` индекса не старше последнего мержа (протух —
  карточка «переиндексируй», это секунды). Так «граф отстал» перестаёт
  быть сюрпризом посреди волны.

**Базовые правила разработки** не вшиваются в CLAUDE.md каждого проекта:
в проект ставится плагин (nyron-dev), в CLAUDE.md остаётся одна сноска
«работа по плагину, конфиг `.claude/nyron-dev.md`». Правила живут и
обновляются в одном месте.

**Роли.** Источник людей — трекер: аудитор берёт пользователей проекта
Jira (почта, имя) и предлагает сопоставление «человек → роль конфига»
(постановщик, техлид, QA…; merge_rights — кто сливает). Человек
подтверждает формой. Нет Jira — роли заполняются вручную или
пропускаются.

**SSH.** Инвентарь `~/.ssh` и алиасов config; проект называет свои
серверы (топология) → проверка фактом `ssh -o BatchMode <alias> exit`
(read-only, ничего не выполняем). Нет доступа — карточка «положи ключ /
добавь алиас». Схема одинаковая для мака, линукс-сервера и винды: папка
ключей + config подключений; если проект разворачивается на новой машине
или серваке — аудитор говорит, ЧТО скопировать (ключницу и ssh-папку) и
куда. Личность флота (отдельный пользователь с урезанными правами на
серверах) — следующий шаг STOVP-59, аудитор её пока только помечает.

Выход: паспорт + ключница собраны, **смоук фактом по каждому пункту** —
это тот же верификатор «проверить готовность» из пульта.

## Ступень 4 — правки CLAUDE.md / AGENTS.md (только по согласованию)

Аудитор различает **четыре вещества** в тексте:

| Вещество | Что с ним делать |
|---|---|
| Правила поведения | оставить; проверить на дубли и противоречия |
| Факты в прозе (серверы, порты, домены, карта деплоя) | вытащить в структуру (паспорт/конфиг/топологию), в тексте — ссылка |
| Состояние на дату («установлено, проверено N-го», версии) | выкинуть: протухает за день; истину показывает верификатор |
| Инструкции установки | в setup-справочник, из канона убрать |

Плюс проверки: дублирование правил (в т.ч. между корнем и подпапками),
противоречия между источниками (CLAUDE.md ↔ конфиг ↔ доки), прямые
значения подключений в тексте, битые ссылки на файлы/пути.

Стандарт минимального CLAUDE.md после переписания: что это за проект и
схема связей (1 экран) → как запустить/тестировать (команды) → правила,
которые НЕЛЬЗЯ проверить фактом (их и остаётся мало) → сноска на плагин
и паспорт. **AGENTS.md** — тот же канон для не-Claude инструментов
(codex и др.): не второй свод правил, а тот же (общий файл или ссылка);
нет CLAUDE.md — правила живут в AGENTS.md.

Выход: разбор списком предложений по каждому уровню (корень, подпапки) →
человек подтверждает по пунктам → аудитор применяет подтверждённое.

## Ступень 5 — аттестация

Записанный факт с датой и чек-листом: паспорт зелёный (верификатор),
секретов в git нет, канон переписан, ai-docs структура есть, у задач в
DoD написано как тестировать. Неаттестованный проект в пульте — с
плашкой; правило «волны не запускаются» включается только после
аттестации первого живого проекта (ai-evolve).

Повторный прогон аудита — легален и дешевле первого: сравнение факта с
паспортом, отчёт о дрейфе (что разъехалось с прошлого раза).

## Чего аудитор НЕ делает

- не чинит код и не рефакторит «раз уж зашёл» — только находки в отчёт;
- не правит канон и не переносит файлы без подтверждения по пунктам;
- не выполняет на серверах ничего, кроме проверки входа;
- не показывает значения секретов ни в отчётах, ни в вопросах;
- не изобретает правила проекту — базовые правила приносит плагин.

## Восемь дополнений — решения гриля с постановщиком 18.08

1. **Ключница закрыта от сессий.** Значение секрета едет из ключницы
   напрямую в процесс: MCP — через загрузчик, локальный стек — через
   `env_file` докера, запросы к базе — через обвязку, которая сама берёт
   креды. Агенту не нужно знать ни одного значения. Поэтому: забор-хук
   дополняется запретом чтения `.secrets/*` (попытка = красный флаг в
   логе, не тихий успех), а pre-commit хук с тем же детектором секретов
   не даёт закоммитить значение — ловим ДО, а не ротируем ПОСЛЕ.
   Прод-база, доступная просто по адресу, — тоже ключ проекта, плюс
   усиление: в самой базе отдельная учётка флота только на чтение
   (запись — человеку; отзыв одной строкой; в логах видно «флот, не
   человек»). Карта проекта обязана показывать, какие сервисы вообще
   торчат в интернет напрямую.
2. **Два ритма проверки.** Быстрый: верификатор — это скрипт (кнопка в
   пульте — лишь один из входов); дешёвые проверки — перед каждым
   стартом волны (красный паспорт → волна не стартует), дорогие
   MCP-смоуки — раз в день. Медленный: в паспорте дата последней
   ревизии; вышел интервал (напр. неделя) — пульт вешает карточку «пора
   ревизия» → аудитор-лайт: дрейф факт↔паспорт, мусор в CLAUDE.md
   (датированные пометки, прожитые запреты «тогда-то решили — больше не
   делаем», дубли, битые пути), сверка правил с живой практикой волн.
   Выход — список предложений с подтверждением. Сквозное правило:
   сессия, добавившая проекту инструмент или ключ, дописывает паспорт
   тем же коммитом — иначе верификатор о новом не узнает.
3. **Аудит проводит скрипт на той машине, где всё запущено** — там
   реальные env, докер и ssh; проверка фактом чего-то стоит только там.
   На сервере команды станет проще: один дом, все подключаются к нему.
   Топология серверов — файл в каноне команды (НЕ память сессии — она
   кэш). Бутстрап серверного дома: человек ставит проект и панель,
   дефолтный логин панели сносится при первом входе, дальше всё
   конфигурирование — через пульт.
4. **Ключи с паспортом на перевыпуск.** У каждого ключа в паспорте
   обязательны «как перевыпустить» и «владелец», плюс срок жизни, где он
   есть, — верификатор предупреждает «протухнет через неделю», а не
   констатирует труп посреди волны.
5. **Командные копии ключей — отложено осознанно** до сервера команды со
   входом по паспорту (аутентификацию пока не строим). Схема уже
   совместима: паспорт описывает имена, значения у каждого свои.
6. **Данные для запуска — часть карты проекта.** Первый пользователь
   (сид/миграция/регистрация), осмысленные данные (сид-скрипт, дамп,
   тестовые учётки), фикстуры e2e, создающиеся сами. Смоук: прогнал
   сид → вошёл тестовой учёткой → главный экран не пустой. Иначе «стек
   поднялся» ≠ «в проекте можно работать».
7. **Права токена — рекомендация, не ворота** (решение постановщика:
   не разводить дотошность). Верификатор может делать безопасные
   read-проверки прав (например «покажи доступные переходы») и честно
   писать «вход проверен, права — нет»; красным это не красится и
   ничего не блокирует.
8. **Выкат плагина = пересборка, а не тихое расхождение.** Пульт видит
   новую версию → обновляет установленную копию, поднимает минимальную
   версию в паспортах проектов и пересоздаёт сессии: простаивающие —
   перезапуск резюмом без вопросов; активно работающим — оповещение в
   пульте («доработай и перезапустись»), посреди работы никого не
   убиваем.

## Развилки — приняты дефолты (18.08; меняются словом постановщика)

1. Env-стратегия по умолчанию: аудитор предлагает по структуре —
   монорепо → одно место, мультирепо → по подпапкам; финальный выбор
   всё равно формой у человека.
2. Роли из Jira: тянуть assignable-пользователей проекта и предлагать
   сопоставление; человек правит формой.
3. Карта проекта: отдельный файл в доках проекта; в паспорте — только
