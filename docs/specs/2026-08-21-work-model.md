# Модель работы: эпик → задача → подзадача. Как режем, где граница, что держит пульт

Статус: проект спеки по STOVP-57, на согласование CTO. Кода нет — только модель.
Источники: STOVP-57 с комментом гриля 16.08, docs/SYSTEM-DESIGN.md (§3–6),
docs/BASELINE-1210.md, wave-protocol.md (груминг, шаги 6–8), факты 21.08 по
аудитору psylia.

## Суть одним абзацем

Работа режется на три уровня (эпик → задача → подзадача), параллель
ограничивается контрактами кода, а не нашей нарезкой, и — главное новое этой
спеки — **видимость сессий в пульте превращается в ограничения**: чек-ин по
пульсу, лимит времени шага и гейты запуска становятся механикой пульта, а
всё, что требует суждения (сама нарезка, границы контрактов, выбор «сам или
волной»), остаётся правилом канона. Критерий сортировки один: **механикой
становится только то, что проверяется по данным (трекер, пульс, паспорт) без
чтения кода и смысла; всё остальное — канон.**

## Зачем: два факта

1. **Замер DEV-1210 (12.08):** параллельность 1,7× — 209 часов работы
   растянулись на 5,2 суток; 71 час из 98 активных в работе был ровно один
   тикет. Причина — единица работы (тикет), исполнитель (волна) и поток
   ответственности (блок) лежали в одном списке, и волна везла пачку тикетов
   — спрятанную очередь.
2. **Аудитор psylia (21.08):** сессия простояла в тупике на фоновых
   агентах-товарищах 45 минут — при часе полезной работы. То есть почти
   половина календарного времени сессии — простой. Пульт всё это **видел**
   (пульс, фоновые команды, состояния агентов — уже в интерфейсе), но ничто
   не **ограничивало**: видимость без порогов не спасает. Точечный фикс уже
   сделан (аудитору фоновые товарищи запрещены, коммит 7431bef; тишина 30
   минут снимает статус «работает», коммит 197e5ae) — спека обобщает его в
   систему.

Вывод: полутора-кратная параллельность и 45-минутные тупики — одна болезнь
в двух проявлениях. Лечится в двух местах: нарезкой (проектируем параллель
на груминге) и пультом (готовое не лежит, застрявшее не молчит).

## 1. Три уровня работы

| Уровень | Что это | Владелец | В трекере |
|---|---|---|---|
| Эпик | фича целиком | постановщик | Epic |
| Задача | целостное поведение с пользовательским DoD и «Как тестировать» | диспетчер-синьор | Задание/Баг, parent = эпик |
| Подзадача | технический кусок со своим DoD и красным тестом | исполнитель (волна / субагент / конвейер / сам синьор) | Subtask (тип в конфиге уже объявлен) |

Правила уровней:

- **Волна ведёт ровно одну подзадачу.** Пачка внутри волны — спрятанная
  очередь; именно она дала 1,7×.
- **Подзадачи заводятся только при реальной параллели**: есть два и больше
  независимых кусков. Один кусок = задача без подзадач, её ведёт синьор сам.
- **«Блок» как обязательный уровень нарезки упраздняется.** Несколько
  диспетчеров на фичу — можно (число задаёт план исполнения), но это
  распределение задач по синьорам, а не отдельный слой в трекере.

## 2. Кто режет и когда

Нарезка происходит в две руки, в два момента:

**Груминг (сессия постановки, до старта работ):**

1. режет эпик на **задачи без взаимных зависимостей** — каждая задача
   закрываема и проверяема сама по себе;
2. внутри задачи размечает **подзадачи там, где видит параллель**;
3. ставит **связи трекера «блокирует / блокируется»** — это единственный дом
   фактов о зависимостях; проза плана и бронь будки источником истины не
   являются;
4. отмечает **общие контракты** (раздел 3): пересечение либо фиксируется
   одной строкой договорённости, либо два куска сливаются в один;
5. выдаёт **план исполнения** — обязательный артефакт: сколько диспетчеров
   нужно фиче; по каждой подзадаче механизм (синьор сам / субагенты в сессии
   / конвейер / отдельная волна); число одновременных стартов. Стоимость
   токенов при выборе степени параллели — не аргумент; аргументы — скорость
   и качество.

**Диспетчер-синьор (по ходу задачи):**

- решает по каждому куску «мелочь и связное — сам, независимое и объёмное —
  волне»; может **дорезать** подзадачу или **переметить** механизм — пометка
  живёт в трекере, откуда её читает очередь пульта;
- мержит готовые ветки по очереди будки (до merge_rights=wave), верифицирует
  фактом, ведёт эскалации к постановщику.

После нарезки — **второй гриль постановщика**: «что делаем / как тестируем /
зачем» простым языком по каждой задаче; неподтверждённое в очередь не
попадает.

## 3. Граница параллели — контракт, а не файл

Один файл можно вести двумя исполнителями: git сливает правки в разных
функциях сам. Ждать нужно ровно в двух случаях:

1. **Нужен чужой код, которого ещё нет** — физическая зависимость; ставится
   связью «блокируется» в трекере.
2. **Обе правки меняют один смысл** — одну функцию, один инвариант, один
   протокол: слияние проходит чисто, а поведение ломается (случай К-2: джоба
   закрывалась в одном месте, конвейер продолжался в другом).

Контракт — это то, о чём договорились поверх кода: сигнатура функции, формат
сообщения, схема данных, инвариант «кто закрывает джобу». На груминге
отмечаются **общие контракты, а не общие файлы**. Следствия:

- нарезка «один файл — ровно одна волна» (wave-protocol, шаг 6.2) в каноне
  заменяется на «один контракт — ровно один исполнитель»;
- **бронь файла в будке — сигнал** «здесь работает волна Б2, участок
  такой-то», а не замок; очередь пульта броню не читает;
- типовая ложная зависимость «фронт ждёт бек» решается контрактом:
  согласовали формат — фронт пишется против него сразу, не после мержа.

## 4. Мерж — по готовности, а не пачкой

Каждая ветка уезжает в main сразу после зелёных ворот (кросс-ревью другой
моделью + сверка с DoD; до merge_rights=wave — вердикт диспетчера). Порядок
держит **очередь мержа в будке**: кто первый готов — первый в main, остальные
подтягивают свежий main до сдачи. Анти-пример зафиксирован: на Блоке 2 три
ветки копились, и диспетчер руками ребейзил стек 1225→1226→1227.

## 5. Что при этом делает пульт

| Момент | Что делает пульт |
|---|---|
| Груминг | показывает сессию с ролью «постановка» (роль известна при запуске, не угадывается по имени) |
| Второй гриль | карточки «что делаем / как тестируем / зачем» в ленте «ждут человека», ответ доезжает до сессии за секунды |
| Старт исполнителя | запускает сессию с привязкой «сессия → подзадача»; дерево эпик → задача → подзадача → сессии строится из **иерархии трекера**, не из имён сессий |
| Ход работы | пульс: чем занята, сколько идёт, фоновые команды, состояния агентов (уже есть); поверх — пороги из раздела 6 |
| Застревание / просрочка | карточка диспетчеру или человеку, не молчаливое ожидание |
| Готовность | очередь мержа будки; после зависимости-мержа стартует следующая готовая подзадача (самотянущая очередь — шаг 4 стройки) |

## 6. Механика пульта против правила канона (отдельный раздел по заданию)

Критерий: **механика — то, что проверяется по данным без суждения** (трекер,
пульс процесса, паспорт проекта). Требуется читать код или понимать смысл —
это канон, и пульт может лишь подать материал.

### Включается механикой

| Ручка | Как работает | Что уже есть фактом |
|---|---|---|
| **Гейт паспорта** | волна не стартует на красном паспорте проекта; неаттестованный проект — с плашкой, волны туда не идут (запрет включается после аттестации ai-evolve). Уточнение по челленджу Sol 21.08: сегодня гейт проверяется только для bypass-режима, а отсутствие паспорта считается зелёным (`runner.js:292`, `passport.js:121`) — целевая механика проверяет паспорт при **любом** старте волны, независимо от режима разрешений, и «паспорта нет» = красный | `passportQuick`: bypass-сессия не стартует по красному паспорту (STATE-2026-08-20) |
| **Обязательный чек-ин (пульс)** | тишина сессии дольше порога → статус «застряла» + карточка в ленту «ждут человека». Тишина считается по совокупности: главный поток **и** фоновые агенты — «жду товарищей» тишиной не прикрывается (урок psylia: 45 минут тупика при видимом пульсе). Уточнение по челленджу Sol: живость процесса ≠ работа — сегодня живой tmux/CLI оставляет статус «working» (`fleet.js:704`, `fleet.js:455`), кейс psylia может повториться как «CLI жив, значит работает»; тишина меряется по активности лент (транскрипт + агенты + фоновые команды), не по живости процесса. Порог — ключ конфига; для рабочих ролей предлагается 15 минут (втрое меньше потери, чем 45) | «тишина 30 минут сильнее вердикта сторожа» (коммит 197e5ae); пульс, фоновые команды и состояния агентов видны (6b698db, 3e3701c, 7976bcb) |
| **Лимит времени шага** | подзадаче на груминге пишется грубая оценка (S/M/L → часы, поле трекера); пульт меряет от старта сессии; превышение ×2 → карточка-эскалация с кнопкой «перезапустить с контрольной точки» (правило перезапуска работает: контекст — в трекере и будке, память сессии — кэш). Автоматически не убивает — только сигналит и предлагает. Уточнение по челленджу Sol: сегодня resume восстанавливает разговор, а не рабочую точку (реестр хранит sessionId/workdir, без ветки/SHA — `runner.js:309`, `runner.js:345`); кнопка перезапуска показывается только при валидной контрольной точке — ветка, коммит, статус подзадачи в трекере | замер времени сессии в шапке уже есть (6b698db) |
| **Гейт «волна = одна подзадача»** | пульт привязывает сессию к подзадаче при запуске; запуск волны без подзадачи или на вторую живую подзадачу — отказ механикой | привязка «сессия → подзадача» заложена в дерево пульта (SYSTEM-DESIGN §6) |
| **Гейт второго гриля** | подзадача без подтверждения постановщика в очередь не попадает (проверка по отметке в трекере). До появления самотянущей очереди (шаг 4) — проверка при выдаче чипа | ленты «ждут человека» и карточки — в замысле пульта (STOVP-58) |
| **Запрет фоновых товарищей по роли** | ключ роли в конфиге: каким ролям фоновые агенты-товарищи запрещены (аудитор — уже), каким разрешены с учётом их пульса в тишине | сделано для аудитора точечно (коммит 7431bef) |
| **Очередь мержа** | будка держит очередь; готовая ветка встаёт в хвост, мерж по порядку готовности. Сегодня очередь — советующая (SQLite в будке, `hub-db.mjs:548`), жёсткими воротами она становится на шаге автомержа: мерж вне очереди отклоняется механикой | тулы `hub_merge_join` / `hub_merge_leave` существуют |

**Порядок включения (по челленджу Sol 21.08).** Гейты «зависимости закрыты»,
«второй гриль подтверждён» и дерево эпик → задача → подзадача висят на данных
трекера, которых пульт сегодня не читает: `/api/tree` отдаёт только
`project → sessions`, эпик угадывается по будке и заголовкам
(`fleet.js:336`). Поэтому первым строится **адаптер трекера** (единый
интерфейс единицы работы — SYSTEM-DESIGN §6 «Абстракция трекера», шаг 4
стройки), и только на нём включаются эти гейты; до адаптера они действуют
правилом канона при выдаче чипов. Аналогично «запрет фоновых товарищей по
роли» сегодня держится промтом аудитора, роли в реестре запуска нет
(`runner.js:309`) — механикой он становится вместе с launch-профилем
(роль + подзадача + оценка в записи запуска).

### Остаётся правилом канона

| Правило | Почему не механика |
|---|---|
| **Нарезка (в т.ч. «авто-нарезка»)** | решить, независимы ли два куска, — значит понять код и смысл. Пульт **не режет**; он может подать материал (карту «тикет → файлы», связи трекера), но границы задач и подзадач ставят груминг и второй гриль. Авто-нарезка механикой отклоняется |
| **Граница параллели / контракты** | увидеть общий инвариант в двух правках одного файла машина по данным не может — это суждение груминга; после фиксации контракт живёт строкой в плане и связью в трекере (и вот их наличие механика проверить может) |
| **«Мелочь — сам, объёмное — волне»** | выбор механизма исполнения — суждение синьора о связности и объёме; пульт лишь исполняет пометку из плана |
| **Содержание DoD, вердикты кросс-ревью, эскалации** | что считать блокером и как сформулировать вопрос постановщику — смысл, не данные. Механика проверяет только факт: DoD заполнен, ревью было, ответ получен |

Дальний ориентир: правило канона, которое научились проверять по данным,
переезжает в механику (так уже случилось с «молчащая сессия ≠ работает»).
Обратного хода нет — механика в канон не разжимается.

## 7. Что поменять в каноне волн (заход отдельной волной, плагин здесь не трогаем)

По правилу CTO правки nyron-dev/ в этой ветке не делаются. Список — диффом
на будущий заход по wave-protocol.md и wave-rules-template.md:

1. Груминг: три уровня и Subtask как единица волны; «блок» из обязательных
   уровней убрать; план исполнения — обязательный артефакт (шаг 6).
2. Шаг 6.2 «один файл — ровно одна волна» → «один контракт — ровно один
   исполнитель»; карта «тикет → файлы» остаётся материалом, решение — по
   контрактам.
3. Зависимости — связями трекера, не прозой; проверка на ложность (шаг 6.4)
   остаётся.
4. Правила волн: волна = одна подзадача; бронь — сигнал; мерж по готовности
   через очередь будки; свежий main подтягивается до сдачи.
5. Чип волны получает ключ подзадачи (не список тикетов) — иначе гейт
   «одна подзадача» пульту не по чему проверять.

## 8. Три вопроса постановщика (дополнение 21.08)

### 8.1. Как разные задачи распределяются между сессиями и копиями подписок

Ответ: **никто не раздаёт работу руками, потому что решение разнесено на два
момента.** ЧТО делать и каким механизмом — решает план исполнения на груминге
(суждение). КОГДА и НА КАКОМ слоте — решает очередь пульта по двум спискам:
готовые подзадачи (зависимости в трекере закрыты, второй гриль подтверждён)
и свободные слоты пула. Совпали — старт, без человека и без выбора.

Слот (копия подписки в `~/.stovp-slots/<id>`) — взаимозаменяемый ресурс:
подзадаче всё равно, какая копия её везёт, потому что конфиги розданы
(`slot_sync` — «взять конфиг основного», факт 20.08). Привязка «подзадача →
сессия → слот» записывается пультом в момент старта — из неё же строится
дерево. Слот протух или упёрся в лимит — парковка, подзадача возвращается в
очередь и уходит на следующий свободный слот, а не висит на мёртвом.

- **Механика пульта:** пул слотов со статусами и смоуком фактом; сопоставление
  «готовая подзадача × свободный слот»; потолок одновременных стартов из
  плана и `max_parallel_waves` конфига; парковка при лимите и возврат
  подзадачи в очередь; запись привязки при старте. До самотянущей очереди
  (шаг 4 стройки) переходный режим: чипы кликает человек, но состав и
  порядок диктует план — ручной остаётся только клик, не выбор.
- **Правило канона:** приоритет между эпиками и задачами, когда готового
  больше, чем слотов, — суждение диспетчера/постановщика (пометка приоритета
  в трекере, очередь её читает); закрепление слота за особой ролью (аккаунт
  OpenAI — только кросс-ревью) — ключ конфига; «этой подзадаче нужна такая-то
  модель» — строка плана исполнения.

### 8.2. Роль goal-чипов: от тикета к запущенной сессии

Ответ: **чип — транспорт запуска, а не носитель смысла, и его собирает пульт,
а не человек.** Смысл живёт в трекере (бриф-коммент, DoD, связи); чип — это
`/goal` с ключом подзадачи, ссылкой на бриф и правилами. Сегодня чип пишет
диспетчер и кликает человек; в целевой модели пульт генерирует его из данных
трекера шаблоном и сам подаёт в сессию при старте — «чип» перестаёт быть
ручной операцией и становится внутренним форматом запуска.

Что обязано быть проверено ДО старта — все проверки по данным, значит гейты
механики:

1. паспорт проекта зелёный (`passportQuick` — уже есть);
2. подзадача готова: связи «блокируется» закрыты, отметка второго гриля
   стоит;
3. бриф-коммент в тикете существует (проверяется факт наличия, не качество);
4. на подзадаче нет другой живой сессии (гейт «волна = одна подзадача»);
5. слот жив (смоук фактом);
6. текст `/goal` короче лимита 4000 — иначе сессия молча остаётся без цели
   (известный отказ, пульт обязан отклонить, а не запустить).

- **Механика пульта:** все шесть гейтов плюс автогенерация чипа шаблоном из
  трекера; отказ в запуске с внятной причиной вместо молчаливого старта
  пустой сессии.
- **Правило канона:** содержание брифа и DoD; выбор модели под тип работы
  (канон «волна-оркестратор — Opus»); решение запустить вне плана —
  исключение, которое фиксируется пометкой в трекере, и тогда гейты снова
  проверяют уже её.

### 8.3. Воркфлоу в пульте — наравне с субагентами

Факт: пульт читает каталог `subagents/` рядом с транскриптом и показывает
всех агентов, включая фоновых (`sessionAgents`, fleet.js:611 — починено
после инцидента 19.08 «аудитор поднял троих, в пульте — ни одного»).
Воркфлоу пульт не разбирает совсем: конвейер стадий человеку не показан,
его агенты в лучшем случае видны общей кучей без структуры «стадия →
агенты», и 45 минут ожидания конвейера выглядят как просто тихая сессия.

Ответ: **воркфлоу читается тем же приёмом, что субагенты, — по файлам рядом
с транскриптом.** Прогон воркфлоу пишет журнал (`journal.jsonl` с ходом
стадий и возвратами агентов + ленты `agent-*.jsonl`). Формат журнала — пока
**предпосылка, не факт** (челлендж Sol подтвердил: в коде пульта воркфлоу не
разбирается нигде, а пример конвейера пишет свои метрики в
`.nyron-hub/metrics.jsonl`): первый шаг реализации — факт-спайк, разобрать
артефакты реального прогона и зафиксировать схему; до него контракт не
кодировать. Пульту журнала достаточно, чтобы
показать: имя воркфлоу, стадии из его шапки (`meta.phases`), по каждой
стадии — агенты с состоянием «пишет прямо сейчас / закончил / упал» (та же
проверка свежести jsonl, что у субагентов), и строку прогресса «стадия 2 из
4, живых агентов 3».

- **Механика пульта:** разбор журнала воркфлоу и показ конвейера стадий в
  окне сессии наравне со списком агентов; активность воркфлоу входит в пульс
  сессии — но, как и фоновые товарищи, **не прикрывает тишину** главного
  потока: сессия, которая час «ждёт конвейер», не молчит для чек-ина
  раздела 6, а показывает, ЧЕГО ждёт; упавшая стадия — карточка, не тихий
  ноль.
- **Правило канона:** когда работу вести воркфлоу, а когда волной или
  субагентами — строка механизма в плане исполнения (суждение груминга и
  синьора); содержание и число стадий — автор воркфлоу; пульт конвейер
  показывает и меряет, но не сочиняет и не перестраивает.

## 9. Список работ механики пульта (порядок исполнения, решение постановщика 21.08)

Порядок = зависимости; пункты 1–3 независимы и заведены тикетами, 4–12 ждут
своей очереди списком здесь (решение постановщика: тикетами не заводить,
пока не дошли).

1. **Чек-ин по лентам** — тишина по активности транскрипта + агентов +
   фоновых команд, живой tmux не держит «working» — **STOVP-60**.
2. **Гейт паспорта на все режимы** — проверка при любом старте волны,
   «паспорта нет» = красный — **STOVP-61**.
3. **Валидация запуска на сервере** — длина `/goal` < 4000, отказ с причиной —
   **STOVP-62**.
4. **Launch-профиль** — запись запуска получает роль, эпик/задачу/подзадачу,
   оценку; фундамент гейтов ниже.
5. **Запрет фоновых товарищей по роли** — enforcement по роли из
   launch-профиля, а не промтом.
6. **Адаптер трекера** — единый интерфейс единицы работы (id, родитель,
   зависимости, статус, отметка гриля, DoD); прямые вызовы Jira из пульта
   закрыты.
7. **Дерево эпик → задача → подзадача → сессии** — из адаптера; гадание по
   будке и именам выключается.
8. **Гейты старта по трекеру + автогенерация чипа** — зависимости закрыты,
   гриль подтверждён, бриф существует, «волна = одна подзадача».
9. **Лимит времени шага + контрольная точка** — карточка при ×2 от оценки;
   кнопка перезапуска только при валидном чекпоинте.
10. **Воркфлоу в пульте** — сначала факт-спайк артефактов прогона, затем
    конвейер стадий наравне с агентами.
11. **Самотянущая очередь** — «готовая подзадача × свободный слот», парковка
    слота при лимите с возвратом подзадачи.
12. **Очередь мержа как жёсткие ворота** — вместе с автомержем
    (merge_rights=wave); до этого — советующая.

## 10. Прогон и замер (DoD тикета)

На ближайшем живом эпике: план волн называет задачи, подзадачи и число
одновременных стартов; в пульте эпик раскрывается в задачи и подзадачи из
иерархии трекера; волны стартуют одновременно. Замер тем же расчётом, что
BASELINE-1210 (история статусов: календарный размах против суммы часов;
число одновременно открытых подзадач). Цель — параллельность выше 1,7×
(ориентир 3×) без роста возвратов на доработку. Дополнительно — новый
показатель из инцидента psylia: **доля тишины в календарном времени сессии**
(у psylia было ~43 %); после включения чек-ина порогом 15 минут она обязана
упасть.
