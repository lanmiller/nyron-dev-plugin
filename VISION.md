# STOVP — VISION

**STOVP** (Self-Tuning Orchestrator for Vendor Pools) — автономная система
разработки продуктов: машина выполняет наблюдение и исполнение, человек
принимает решения (ставки, вердикты, приёмка). Один рантайм на машину
обслуживает все проекты команды (ai-evolve, betzo, psylia, noproblem).

Документ-пара: [SYSTEM-MAP.md](SYSTEM-MAP.md) — карта функций «сейчас → будет».
Ресёрч-база: [research/](research/). Обновлено: 2026-07-27.

## Зачем

Сегодня системные функции (вотчеры, таймеры, очереди) исполняются внутри
ИИ-сессий — самых дорогих и самых смертных компонентов, а человек совмещает
четыре роли: глаза (мониторинг), руки (запуск и рестарты), голову (решения)
и кошелёк (лимиты). Диагностика 27.07.2026 показала цену: вотчеры, убиваемые
таймаутами каждые 10 минут; очередь мержа с записями-призраками пятидневной
давности; человек узнаёт о сбоях раньше системы.

STOVP выносит системные функции в постоянный рантайм и забирает у человека
глаза и руки. Голова остаётся человеку.

Система состоит из трёх частей (MECE): **исполнители** (кто делает работу),
**управление** (кто распределяет и контролирует), **знания** (что направляет
работу и проверяет результат).

## 1. Исполнители: флот из пяти ролей

Принцип: у каждой роли свой вендор и своя экономика — дорогая модель не
исполняет дешёвую работу.

| Роль | Модель | Оплата | Нагрузка |
|---|---|---|---|
| Разработка (диспетчер, волны, код) | Claude — 4 подписки | подписки | пиковая, окнами |
| Кросс-ревью кода и планов | GPT (Sol/Terra) через codex CLI | подписка | по конвейеру |
| Третий голос: консилиум на сложных планах/ревью + механический рефакторинг | GLM | подписка (общая с QA) | по запросу |
| QA: UJM-прогоны, Playwright, регрессия | GLM (пилот); Kimi — картридж на пересмотр (п. 3.4) | подписка | фоновая, 24/7 |
| Спец-задачи (генерация картинок и пр.) | API точечно (Replicate и др.) | pay-per-use | эпизодическая |

**Консилиум модельных семей**: у семей разные слепые пятна. Обычный тикет —
пара «Claude пишет — GPT проверяет»; сложное решение (архитектура, спорное
ревью) — плюс третья семья (GLM/Kimi) третьим голосом.

**Экономика**: основа — подписки (фиксированная цена); API — только
переливной клапан и спец-задачи, постоянный поток работы на API запрещён.
Подписки Claude насыщены (4 штук хватает впритык), поэтому лимит-менеджмент
(учёт окон, каскад запусков, парковка) — условие выживания фабрики, а не
оптимизация.

**Форм-фактор**: сегодня — клоны Claude Desktop через Parall.app (у каждого
свой bundle ID, хранилище и логин; машина и IP общие). Целевой — headless
CLI-процессы с профилями `CLAUDE_CONFIG_DIR` на аккаунт, запускаемые демоном
локально: та же степень изоляции, что у клонов. Desktop-клоны остаются
рабочим местом человека и запасным контуром. VM — опция усиления изоляции
на будущее (ферма, рост fingerprint-риска).

## 2. Управление: дирижёр STOVP

Компоненты: демон **`stovpd`** (Python/FastAPI; портируемое ядро +
OS-адаптеры: launchd/служба, файловые события, изоляция), веб-морда
**Stovp** («вышка»; SvelteKit + shadcn, localhost, удалёнка через Tailscale),
CLI **`stovp`**. Один экземпляр на машину; переезд на выделенную ферму
(Mac mini) — изменением конфига, не перестройкой. Слаги github/npm/PyPI
`stovp`/`stovpd` и домены stovp.dev/.app свободны (проверено 27.07) —
застолбить до первой строки кода.

### 2.1 Вышка — наблюдение

Доска волн/job'ов (пульс, тикеты, ожидание вердикта), лента будки, очередь
и брони, квоты и расход по аккаунтам, реестр техдолга. **Контракт
наблюдения**: каждый объект имеет состояние `running/stalled/idle/unknown`
с меткой последнего доказательства прогресса, источником и порогом;
`unknown` алертится отдельно — тишина сенсора не выдаётся за здоровье.
Окно-транскрипт исполнителя: на этапе 1 — строго read-only; поле ввода
(control-job-продолжение через `--resume`) появляется только с демоном
(этап 3+), UI не обещает невозможного. Алерты в Telegram: тишина будки,
тикет без вердикта, протухший lease/heartbeat, недоступный сенсор. Кнопки
решений: вердикт, мерж пачки. Результат: человек перестаёт быть системой
мониторинга.

Фазировка (решение панелей 27.07): на этапе 1 вышки-UI НЕТ — только алерты
и готовые сенсоры («Сигнал»); полный UI строится один раз поверх схемы
stovpd на этапе 3+, чтобы не писать одноразовые адаптеры к умирающему
переходному контуру.

**Карманный интерфейс — Telegram Mini App** (решение 27.07): та же
SvelteKit-морда упаковывается мини-аппом в бота — пуш-алерты и пульт
решений в одном месте, с телефона отовсюду. Auth из коробки: подпись
initData + allowlist telegram-аккаунтов в конфиге ролей (каждый видит свой
вид). Транспорт — локальный туннель (tuna.am) с публичным HTTPS.
Границы каналов: в мини-аппе — доска, статусы, кнопки решений, алерты
(чувствительного контента нет); полные транскрипты и сырые логи — только
через Tailscale, через публичный туннель не гоняются (SECURITY-канон).

**Мета-метрики фабрики** (меряем систему, не только продукты; сенсоры —
Jira changelog, журнал вмешательств в будке, ccusage/OTel, ticket-id в
контексте job'а): (1) cycle time тикета по стадиям, отдельно ожидание
вердикта; (2) доля автономных прохождений без `human_intervention`;
(3) стоимость тикета в окнах и токенах; (4) first-pass yield (без возврата
в rework); (5) утилизация флота и «голодание» очереди. Baseline снимается
на этапе 0 — иначе окупаемость STOVP недоказуема. Alert precision: доля
алертов, приведших к действию; <50% две недели → сенсор чинится или
выключается.

### 2.2 Демон — инфраструктура

`stovpd` владеет будкой и очередью работ: таблицы jobs/attempts/leases/events
(outbox, идемпотентность), heartbeat исполнителей, TTL и чистка очередей и
броней, supervision (зависшие процессы, CPU-жор, протухшие lease), фоновые
job'ы (git-уборщик, линт CLAUDE.md, переиндексация кодового графа,
Confluence-синк). Результат: класс багов «сервис умер вместе с сессией»
устранён архитектурно.

### 2.3 Запуск флота — исполнение

Демон поднимает исполнителей headless-процессами: модель — параметром, резюм
после лимита — автоматический, распределение — по остатку квот подписок
(живые квоты из vendor API + ccusage; ротация только по типизированным
limit-сигналам, никогда по сетевым ошибкам). Чипы, пикер модели и ручные
подтверждения исчезают из механики; решения остаются у человека.
Исполнительный слой — пилот Claudexor как зависимость (профили, квоты,
ротация; интеграция через его стабильный CLI/API; форк — только по триггеру:
проект умер или PR-путь заглох).

**Job-модель** — единица исполнения для любого типа работы (код, ресёрч,
аналитика, контент): работа лежит в очереди; исполнитель — конечный процесс
(взял lease → сделал шаг → записал чекпойнт → завершился); контекст
продолжается через `--resume`; протухший lease подбирает следующий процесс.
Вотчеры, пробуждения и парковки исчезают как класс. Тип работы определяет
адаптеры и способ проверки, не механику.

**Не строим осознанно**: замену Jira и будки новой шиной (дорабатываем
существующие), GUI-автоматизацию Desktop-окон, свой мерж-механизм (источник
истины — GitLab MR/merge trains; в будке только локальные брони), свой стек
метрик (сенсоры готовые: OTel-телеметрия Claude Code, ccusage).

## 3. Знания

### 3.1 Канон ролей — плагин

Плагин — операционная система команды, не инструмент одного диспетчера:
каждый участник (человек или ИИ-сотрудник) работает в своей зоне через общий
канон — одни стандарты задач, документов и статусов на всех.

**Дистрибуция пакетами по ролям** (одна миграция вместе с переименованием
под STOVP): `stovp-core` (всем: стандарты задач, конфиг проекта, будка,
стиль) + `stovp-product` (гипотезы, фич-интейк, аналитика) + `stovp-qa`
(UJM, приёмка, баг-репорты) + `stovp-dispatch` (волны, кросс-ревью,
диспетчерство). Роль режется по функции; проект задаётся конфигом
(`.claude/<плагин>.md`) — один QA-пакет обслуживает и evolve, и лотереи.
Пакеты одинаково служат людям (Юра — core+product; Агиль — core+qa; Марина —
core+product) и ИИ-сотрудникам (QA-дежурный — core+qa).

**Внешние скилл-паки — используем, не форкаем.** Superpowers (процесс-канон:
brainstorming, TDD, systematic-debugging, writing-plans, verification) и
дизайн-скиллы (frontend-design, dataviz, shadcn) ставятся соседними
плагинами; наши скиллы в нужных шагах ссылаются на них («если доступен —
обязателен»), пакеты ролей объявляют их рекомендованными зависимостями
(dev → superpowers TDD/debugging; product → brainstorming; UI-работа →
дизайн-скиллы), `init-repo` проверяет установленность. Обновления приходят
от авторов, наш канон не дублирует их содержимое.

**Кодовый канон** (сохраняется при любом переезде): лестница до кода +
quality_floor, TDD с физической изоляцией тестов от имплементации, Context7
перед генерацией кода, кодовый граф (RAG) как инструмент каждого job'а.

**Дизайн-система — обязательная часть канона каждого продукта**: агенты
строят UI только из её компонентов; она же — входной язык постановки
(мокапы для фич-реквестов). Состояние: psylia — есть; evolve — построена,
улучшается; betzo — «казиношная», кандидат на выделение; noproblem —
завести.

### 3.2 Библиотека UJM — исполняемые пути пользователя

UJM (User Journey Map) — карта пути пользователя + Playwright-код,
прогоняющий этот путь по стенду. Путь каталога — per-project в конфиге
(evolve: `ai-evolve-docs-test/tests/e2e/journeys/`; этап 2 — пилот на
evolve). Стек: playwright-bdd (`.feature`-каталог — человеко- и
ИИ-читаемый) + официальные Playwright Test Agents (Planner/Generator/Healer;
Healer чинит в MR, канон не трогает) + playwright-reports-server (флаки,
тренды) + мультиюзер-фикстуры (2–3 контекста, уникальная доска на тест,
poll-утверждения сходимости CRDT).

Потребители: волна в разработке (вместо самодельного смоука), диспетчер на
приёмке (смоук после мержа), QA-роль в фоне (ночная регрессия), люди
(каталог = живая карта продукта; Confluence-слой генерится из шапок).
Владелец каталога — роль в фреймворке (человек или ИИ); опасность — не
отсутствие человека, а отсутствие правил пополнения и гейтов качества.
Пополнение: карта флоу из live-прогонов; фича, меняющая путь пользователя,
обновляет UJM тем же тикетом.

### 3.3 Продуктовая петля

Гипотеза — родительская карточка: при утверждении в неё линкуются dev- и
design-таски, прогресс и замер трекаются сквозь неё. Телеметрия (PostHog,
Langfuse, UJM-прогоны) автоматически становится замером; система готовит
проект вердикта — утверждает человек (авто-вердикт только по заранее
заданным в карточке порогам). Мини-аппы продакта — легитимный способ
проверки гипотезы (прототип → замер), каждому — карточка в знание-слое.

### 3.4 QA-модель

Пилот — GLM Coding Plan Lite (помесячно): единственная доступная сегодня
дешёвая флэт-подписка, официально работающая внутри Claude Code (наш
харнесс и MCP без миграции), vision во всех планах. Сценарии пилота:
скриншот стенда → UJM-тест; сломанный селектор → починка по trace;
ночной цикл; замер сжигания квоты (промпты за 5-часовое окно — главный
риск). Тариф пилота выбран окончательно: Lite (рекомендация «сразу Pro» из
раунда-1 отклонена — дешевле проверить и апгрейдиться по цифрам).
Exit-критерии пилота, фиксируются ДО покупки: ≥N успешных UJM-прогонов,
расход промптов за 5-часовое окно ниже квоты тарифа, доля успешных починок
селекторов; не выполнены — Pro или смена картриджа. Роль = слот,
модель = картридж: Kimi пересматриваем, когда откроют продажи Kimi Code
(на 27.07 подписки приостановлены).

### 3.5 Документация: три слоя

**Репо — как устроено; vault — что мы думаем и почему; Confluence — что мы
показываем.** Источник правды — репо/vault (Obsidian: пакет-папки гипотез,
канон-файлы с хозяином-ролью и сроком годности фактов, тип заметки в имени
файла, Bases-доски по фронтматтеру). Confluence — витрина, рендерится из
источника инструментом md2conf: папка → родительская страница, файл →
дочерняя, привязка по page-id (без дублей), точечный режим на один файл,
баннер «generated», правки витрины руками запрещены. Каноническое поле
привязки одно — `confluence-page-id` (нативное md2conf); vault-поле
`публикация:` мигрирует в него, два имени одновременно запрещены. Единственный
публикатор — пайплайн (CI или фоновый job демона); Obsidian в Confluence
не пишет. Документирует та роль, что произвела изменение, — правкой
источника. Для betzo сначала аудит-уборка vault (знание / рабочие папки /
мини-аппы / архив), затем белый список синка, затем зеркало.

### 3.6 Трекер-канон

Основа — модель psylia: 6-ступенчатая лестница статусов через маппинг в
конфиге (`backlog/in_progress/review/rework/testing/done`; имена на доске
любые, скиллы ходят по ключам), категория Jira-статуса — часть канона;
маршруты `dev` + `product` (product-тикет — родитель/гейт dev-тикетов);
слой STATUS-журнала и ROADMAP-потоков над трекером («в Jira только
приоритизированное, будущее — в роадмапе до приоритизации»); каждый переход
статуса — с комментом; техдолг-журнал конвертируется в тикеты грумингом.

## Дорожная карта

Граф зависимостей: **0 → (1 ‖ 2) → 3 → 4а → 4б → 5**. Каждый этап имеет
самостоятельную ценность и критерий готовности; зависимый этап не начинается
до критерия предшественника.

**Принцип непрерывности (высший приоритет)**: текущий плагин nyron-dev —
боевой инструмент ежедневной работы по основным проектам и обязан работать
всё время стройки STOVP. Этап 0 — это фиксы ЖИВОГО плагина (он продолжает
обслуживать волны), STOVP строится рядом, не вместо; миграция на пакеты и
новые механизмы — постепенная, по-ролям и по-проектам, с откатом; big-bang
запрещён. Конфликт «стройка vs боевые задачи проектов» решается в пользу
боевых задач.

**Переходный контракт (до этапа 3)**: волны работают по текущему протоколу
Desktop-сессий с вотчерами, подлатанными этапом 0; это временный режим, в
него не инвестируем сверх гигиены; мосты выключаются при переезде на
job-модель, каждому мосту — тикет на снос с триггером. **Сам этап 0
выполняется синхронными сессиями под наблюдением человека, не волнами**:
чинить механизм пробуждения волнами, которые он будит, — цикл (вердикт
панелей 27.07).

**Календарь и мощность**: реалистичный горизонт — конец этапа 2 через
2.5–3.5 месяца, этап 4а — к концу года (при приоритете боевых задач).
Стройке выделяется явная квота: одно 5-часовое окно одного аккаунта в день;
без квоты стройка голодает неограниченно. Этапы 1 и 2 параллельны по коду,
но последовательны по человеку — WIP-лимит: одна вертикаль за раз.
