# VISION: автономная система разработки продуктов

Дата: 2026-07-27. Статус: рамка, согласована с постановщиком. Не спека.
Перед любой стройкой — план-челлендж второй моделью (`plan-challenge.sh`).

## Главный тезис

Переходим от ручной оркестрации ИИ-сессий к автономной фабрике разработки:
машина забирает наблюдение и исполнение, человек оставляет за собой решения
(ставки, вердикты, приёмку). Система универсальна: один рантайм на машину,
обслуживает все проекты (ai-evolve, betzo, psylia, noproblem).

Обоснование перехода: сегодня системные функции (вотчеры, таймеры, очереди)
живут внутри ИИ-сессий — дорогих и смертных. Диагноз 27.07: вотчеры умирают
от таймаутов каждые 10 минут, очередь мержа держит записи-призраки 5 дней,
человек узнаёт о сбоях раньше диспетчера. Вывод: системные функции надо
вынести из сессий в постоянный рантайм.

Система состоит из трёх частей (MECE): **исполнители** (кто делает работу),
**управление** (кто распределяет и контролирует), **знания** (что направляет
работу и проверяет результат).

## 1. Исполнители: флот из четырёх ролей

Принцип: у каждой роли — свой вендор и своя экономика. Дорогая модель не
исполняет дешёвую работу.

Экономическая рамка (позиция постановщика, 27.07):
- деньги вторичны — профит от системы больше её стоимости; на копейках не
  оптимизируемся;
- но **чисто API — запрещено**: при объёмах фабрики API-биллинг разорителен;
  основа — подписки (фикс-кост), API — только переливной клапан и спец-задачи;
- подписки Claude уже насыщены: 4 штук едва хватает на неделю. Следствия:
  масштаб = добавление подписок + вынос всей несложной работы на дешёвые
  роли (QA-модель, Sol); лимит-менеджмент дирижёра (учёт окон, каскад,
  парковка) — не оптимизация, а условие выживания фабрики.

| Роль | Модель | Оплата | Нагрузка |
|---|---|---|---|
| Разработка (диспетчер, волны, код) | Claude — 4 подписки | подписки | пиковая, окнами |
| Кросс-ревью кода и планов | GPT (Sol) через codex CLI | подписка | по конвейеру |
| QA: сценарии, Playwright, регрессия | Kimi K3 или GLM — выбрать (п. 3.4) | подписка/дёшево | фоновая, 24/7 |
| Спец-задачи (генерация картинок и пр.) | API точечно (Replicate и др.) | pay-per-use | эпизодическая |

Документацию (техническую и человекочитаемую в Confluence) ведёт та роль,
которая произвела изменение; отдельного исполнителя не заводим.

Форм-фактор исполнителей: сегодня — окна Claude Desktop (Parallels, по
подписке на копию); целевой — headless CLI-процессы под управлением дирижёра.
Окна остаются только человеку (груминг, live-прогоны). Гипотеза «4 подписки =
4 CLI-профиля на одной машине без Parallels» проверяется прогоном до
вывода виртуалок.

## 2. Управление: дирижёр из трёх компонентов

Дирижёр — приложение на Mac (Apple Silicon), один на машину. Три компонента,
разделение по функции (MECE): видеть / обеспечивать / запускать.

### 2.1 Вышка — наблюдение

Локальный дашборд + алерты в Telegram. Показывает: доску волн (пульс, тикеты,
вотчер, ожидание вердикта), ленту будки, очередь мержа и брони, расход
токенов по моделям. Алертит: тишина будки, тикет без вердикта, мёртвый вотчер.
Результат: человек перестаёт быть системой мониторинга.

### 2.2 Демон — инфраструктура

`nyron-hubd`, launchd-сервис. Владеет будкой: вотчеры, таймеры, реаниматор,
TTL и чистка очередей/броней, детект мёртвых волн. Сессии ждут события через
тонкий клиент, решение о пробуждении — у демона. Результат: класс багов
«сервис умер вместе с сессией» устранён архитектурно.

### 2.3 Запуск флота — исполнение

Дирижёр сам поднимает исполнителей headless-процессами: модель — параметром,
резюм после лимита — автоматический, распределение — по остатку лимитов
подписок. Чипы, пикер модели и ручные подтверждения исчезают. Результат:
эпик закрывается без единого клика.

Не входит в управление (осознанно): замена Jira и будки новой шиной
(дорабатываем существующие), GUI-автоматизация Desktop-окон (хрупко).

## 3. Знания: канон, сценарии, петля

### 3.1 Канон ролей — плагин nyron-dev

Скиллы, правила волн, конвейер, конфиг проекта. Остаётся переносимым слоем:
дирижёр читает канон, а не заменяет его.

**Дизайн-система — обязательная часть канона каждого продукта** (агенты
строят UI только из её компонентов — quality_floor это уже энфорсит; плюс
она же — сырьё для быстрых мокапов продактам). Состояние по проектам:
psylia — есть; evolve/nyron — только что построена, улучшается;
betzo — есть «казиношная», кандидат на выделение в переиспользуемую
(бэклог, не сейчас); noproblem — прояснить и завести.

### 3.2 Библиотека UJM (User Journey Map) — исполняемые пути пользователя

Каталог канонических пользовательских путей в
`ai-evolve-docs-test/tests/e2e/journeys/`: «логин → создание плейбука →
прохождение оркестратора», «создание компании → роли → несколько юзеров на
доске». Каждый UJM: человекочитаемая карта пути (шапка: что за путь, роли,
данные) + Playwright-код, исполняющий этот путь + фикстуры (тест-юзеры,
тест-компания) + теги окружений. Термин в команде — UJM; «сценарий» —
синоним в тексте.

Потребители (MECE по моменту использования):
- **в разработке** — волна дёргает сценарий вместо самодельной проверки;
- **на приёмке** — диспетчер: смоук после мержа = прогон затронутых сценариев;
- **в фоне** — QA-модель гоняет регрессию в простое; падение → алерт и тикет;
- **для людей** — Агиль владеет каталогом и ревьюит канон; Confluence-слой
  генерится из шапок.

Пополнение: карта флоу из live-epic-testing конвертируется в сценарии; правило
конвейера — фича, меняющая пользовательский путь, обновляет сценарий тем же
тикетом.

### 3.3 Продуктовая петля

Вход и производство уже есть скиллами: intake-groom → product-flow →
jira-task-standard / nyron-waves → qa-handoff. Замыкание: телеметрия
(Langfuse, метрики стенда, сценарии) автоматически становится замером гипотезы
→ вердикт → следующая гипотеза.

### 3.4 Выбор QA-модели — решение экспериментом

Кандидаты: **Kimi K3** (последний), **GLM** (актуальная версия). Критерии
отбора, по убыванию веса:

| Критерий | Что проверяем |
|---|---|
| Скорость | латентность цикла «прочитал страницу → написал/поправил тест» |
| Подписка | наличие безлимитного/дешёвого тарифа под фон 24/7 |
| Browser vision | понимание скриншотов и DOM реального стенда |
| Инструментальность | полноценная работа с Playwright, CLI-агентный режим |
| Качество кода тестов | читаемость и стабильность (не флаки) |

Метод: один и тот же пилот на обоих — написать и стабилизировать 2–3 сценария
на predprod, сравнить по критериям. Решение фиксируется в конфиге плагина.

## Дорожная карта

Последовательность: каждый этап имеет самостоятельную ценность и критерий
готовности; следующий не начинается до выполнения критерия.

| # | Этап | Содержание | Критерий готовности |
|---|---|---|---|
| 0 | Гигиена | синк wave-rules v2.1; запрет timeout на вотчерах/Sol; фиксы hub-watch (замена вместо дубля, busy-флаппинг реаниматора); чистка очереди мержа; чек-аут-лист финала волны | сутки прогона без глухих сессий и ручных пинков |
| 1 | Вышка | дашборд + алерты | о любом застревании узнаём из алерта |
| 2 | Сценарии | каталог + пилот QA-модели (п. 3.4) + согласование с Агилем | волна дёргает сценарий вместо самодельного смоука; ночная регрессия идёт |
| 3 | Демон | nyron-hubd, вынос сервисов из сессий | ноль shell-вотчеров в сессиях; смерть сессии не теряет события |
| 4 | Флот | headless-запуск, мультиподписка | эпик без кликов; лимит одной подписки не останавливает фабрику |
| 5 | Петля | телеметрия → замеры гипотез | вердикт гипотезы формируется из данных без ручного сбора |

Этапы 1 и 2 можно вести параллельно: у них нет общих компонентов.

## Риски

| Риск | Митигация |
|---|---|
| Мультиаккаунт headless не взлетит (авторизация, ToS) | проверка прогоном до вывода Parallels; виртуалки остаются фолбэком |
| Desktop-сессии нельзя будить извне | не строить мосты-костыли; полный ответ — этап 4 |
| Сценарии без владельца-человека выродятся | каталог взлетает только с Агилем как владельцем; согласовать до старта этапа 2 |
| Решения ломают универсальность | каждое решение проверять на betzo/psylia/noproblem; дирижёр обязан уважать project-config |
| Сползание на API-биллинг («улетим в трубу») | API только как переливной клапан и спец-задачи; любой постоянный поток работы обязан жить на подписке; вышка показывает API-расход отдельной строкой |
| Насыщение подписок Claude (4 еле хватает на неделю) | лимит-менеджмент дирижёра с этапа 4; до него — модельная экономика ролей (Opus/Sonnet/Haiku, QA-модель на фоне) и парковка по канону |
