# STOVP — VISION

**STOVP** (Self-Tuning Orchestrator for Vendor Pools) — автономная система
разработки продуктов: машина выполняет наблюдение и исполнение, человек
принимает решения (ставки, вердикты, приёмка). Один рантайм на машину
обслуживает все проекты команды (ai-evolve, betzo, psylia, noproblem) и
всех участников — людей и ИИ-сотрудников.

Пара к документу: [SYSTEM-MAP.md](SYSTEM-MAP.md) — 25 функций «сейчас →
будет». Обоснования и первоисточники: [research/](research/).
Обновлено: 2026-07-28. Прошло: 2 раунда ресёрча (9 прогонов), финальное
ревью Terra, 5 ролевых панелей (~85 находок учтено).

## Зачем

Сегодня системные функции (вотчеры, таймеры, очереди) исполняются внутри
ИИ-сессий — самых дорогих и смертных компонентов, а человек совмещает
четыре роли: глаза (мониторинг), руки (запуск и рестарты), голову (решения)
и кошелёк (лимиты). Диагностика 27.07.2026 показала цену: вотчеры, убиваемые
таймаутами каждые 10 минут; очередь мержа с призраками пятидневной давности;
человек узнаёт о сбоях раньше системы.

STOVP выносит системные функции в постоянный рантайм и забирает у человека
глаза и руки. Голова остаётся человеку.

## Принципы (сквозные, применяются к каждому решению)

1. **Непрерывность — высший приоритет.** Плагин nyron-dev — боевой
   инструмент всю стройку; STOVP строится рядом, не вместо; big-bang
   запрещён; конфликт «стройка vs боевые задачи» решается в пользу боевых.
2. **Решения — человеку, механика — машине.** Вердикты, приёмка, мерж,
   ставки — кнопки человека; запуск, распределение, восстановление — демон.
3. **Подписки — основа, API — переливной клапан.** Постоянный поток работы
   на API запрещён; лимит-менеджмент — условие выживания, не оптимизация.
4. **Job-модель.** Исполнитель — конечный процесс (lease → шаг → чекпойнт →
   выход); контекст бессмертен (resume внутри аккаунта, handoff-чекпойнт —
   между); вотчеры и пробуждения исчезают как класс.
5. **Готовое вместо своего.** Своё — только тонкий слой, которого нет ни у
   кого (политика, будка, связка Jira↔MR↔UJM); всё остальное — зрелые
   инструменты как зависимости, форк — только по триггеру.
6. **Универсальность.** Роль = пакет плагина, проект = конфиг; ядро STOVP
   не содержит проектных фактов (граница публичного/приватного).
7. **Машина — скот, не питомец.** Фабрика воспроизводится на любой ОС из
   трёх переносимых вещей: git (конфиги+манифест), секрет-реестр (токены
   перевыпускаются, не копируются), шифрованный бэкап БД.
8. **Правило без механизма = пожелание.** Каноны энфорсятся хуками, CI и
   doctor-проверками, не памятью людей и агентов.
9. **Измеримость с первого дня.** Baseline до стройки, журнал вмешательств,
   фальсифицируемые критерии готовности; недоказуемая окупаемость =
   несуществующая.
10. **Безопасность как канон, не как спохват.** Стор секретов, границы
    данных per-вендор, разделение каналов по чувствительности — до того,
    как токены и транскрипты поедут по проводам.

## 1. Исполнители: флот из пяти ролей

У каждой роли свой вендор и своя экономика — дорогая модель не исполняет
дешёвую работу.

| Роль | Модель | Оплата | Нагрузка |
|---|---|---|---|
| Разработка: диспетчер, волны, код | Claude — 4 подписки | подписки | пиковая, окнами |
| Кросс-ревью кода и планов | GPT (Sol/Terra) через codex CLI | подписка | по конвейеру |
| Третий голос консилиума + механический рефакторинг | GLM | подписка (общая с QA) | по запросу |
| QA: UJM-прогоны, Playwright, регрессия | GLM (пилот п. 3.4); Kimi — картридж на пересмотр | подписка | фоновая, 24/7 |
| Спец-задачи (генерация картинок и пр.) | API точечно (Replicate и др.) | pay-per-use | эпизодическая |

**Консилиум семей**: обычный тикет — пара «Claude пишет — GPT проверяет»;
сложное решение — плюс третья семья (GLM/Kimi): слепые пятна семей не
совпадают по построению.

**Лимит-планировщик двух уровней**: размещение работы учитывает 5-часовое
окно И недельную квоту аккаунта; долгие задачи — только на аккаунты с
недельным запасом (`--resume` прикован к аккаунту). Переезд задачи между
аккаунтами — через handoff-чекпойнт, не resume. Ротация — только по
типизированным limit-сигналам вендора, никогда по сетевым ошибкам.

**Форм-фактор**: сегодня — клоны Claude Desktop через Parall.app (свой
bundle ID, хранилище и логин у каждого; машина и IP общие). Целевой —
headless CLI-процессы с профилями `CLAUDE_CONFIG_DIR`: та же степень
изоляции, риск не растёт. Desktop-клоны остаются рабочим местом человека и
запасным контуром. VM — опция усиления изоляции на будущее.

## 2. Управление: дирижёр STOVP

Компоненты: демон **`stovpd`** (Python/FastAPI; портируемое ядро +
OS-адаптеры), веб-морда **Stovp** («вышка»; SvelteKit + shadcn), CLI
**`stovp`**. Один экземпляр на машину; переезд на ферму (Mac mini) —
конфигом. Слаги github/npm/PyPI `stovp`/`stovpd` и домены stovp.dev/.app
свободны (проверено 27.07) — застолбить до первой строки кода.

### 2.1 Наблюдение — вышка и карманный контур

**Контракт наблюдения**: каждый объект — `running/stalled/idle/unknown` с
меткой последнего доказательства прогресса, источником и порогом; `unknown`
алертится отдельно — тишина сенсора не выдаётся за здоровье. Постоянный
synthetic-canary: намеренный тестовый сбой обязан рождать алерт; его
отсутствие — само алерт.

**Вышка** (этап 3+, поверх схемы демона): доска волн/job'ов, лента будки,
очередь решений человека (первоклассный объект с SLA), квоты по аккаунтам,
реестры техдолга и внешних зависимостей, экран «Подключения» (манифест
расширений, health MCP). Окно-транскрипт исполнителя: read-only просмотр;
сообщение из поля ввода = control-job-продолжение через `--resume`.

**Карманный контур — Telegram-бот + Mini App**: алерты и пульт решений в
одном месте, с телефона. Та же SvelteKit-морда упаковывается мини-аппом;
auth из коробки — подпись initData + allowlist аккаунтов из конфига ролей;
транспорт — tuna-туннель со статическим адресом (поддомен-кандидат stovp) —
вебхук и URL настраиваются один раз. **Границы каналов**: в мини-аппе —
доска, статусы, кнопки, алерты (без чувствительного контента); полные
транскрипты и сырые логи — только через Tailscale.

**Алерт-политика**: severity (critical будит всегда; routine — утренний
дайджест), quiet hours, дедупликация и сводка каскадов (сон Мака = один
сводный алерт, не пятнадцать); учёт precision — доля алертов, приведших к
действию; ниже 50% две недели → сенсор чинится или выключается.

### 2.2 Инфраструктура — демон

`stovpd` владеет будкой и очередью работ: таблицы jobs/attempts/leases/
events (outbox, идемпотентность, fencing-token против двойников после сна),
heartbeat, TTL и чистка очередей и броней, supervision (зависшие процессы,
CPU-жор, протухшие lease), фоновые job'ы: git-уборщик, линт CLAUDE.md,
переиндексация кодового графа, Confluence-синк, doctor. Эксплуатационный
контур: hot-backup с restore-тестом, dead-man's switch вне машины,
retention артефактов и алерт диска, политика сна/обновлений macOS,
break-glass диагностика без STOVP, runbook холодного старта.

### 2.3 Исполнение — запуск флота

Демон поднимает исполнителей headless-процессами: модель — параметром,
резюм после лимита — автоматический, размещение — по лимит-планировщику
(п. 1). Чипы и пикер модели исчезают из механики; «волна предлагает
работу» = job-заявка в очередь на утверждение, не чип. Исполнительный
слой — пилот Claudexor как зависимость (профили, квоты, ротация; интеграция
через его стабильный CLI/API).

**Не строим осознанно**: замену Jira и будки; GUI-автоматизацию
Desktop-окон; свой мерж (истина — GitLab MR/merge trains, в будке только
локальные брони); свой стек метрик (OTel Claude Code, ccusage — готовые);
форк Claudexor без триггера.

## 3. Знания

### 3.1 Канон ролей — плагин

Плагин — операционная система команды: каждый участник (человек или
ИИ-сотрудник) работает в своей зоне через общий канон.

- **Пакеты по ролям** (одна миграция с переименованием под STOVP, алиасы
  старых имён ≥2 релиза): `stovp-core` (всем) + `stovp-product`
  (Юра, Марина) + `stovp-qa` (Агиль, QA-дежурный) + `stovp-dispatch`
  (диспетчер). Роль = пакет, проект = конфиг. Приёмка разбивки: член
  команды поставил сам по гайду «первый день» и прошёл сценарий в песочнице.
- **Внешние скилл-паки** — соседними плагинами, не форкаем: superpowers
  (процессы), дизайн-скиллы (UI), Context7 (доки библиотек); наши скиллы
  ссылаются «если доступен — обязателен», пакеты объявляют зависимости,
  doctor проверяет. Паттерны чужих ролевых скиллов заимствуем
  (CI-линт скиллов, /compound «что выучили», журнал допущений замера,
  агент-критик артефактов); чужие фреймы — только через ручную проверку
  владельцем.
- **Кастомные агенты** — «скелет + оверрайд»: плагин даёт скелет роли,
  конфиг проекта — стек/зоны/запреты, init-repo собирает проектного агента.
- **Кодовый канон**: лестница до кода + quality_floor, TDD с физической
  изоляцией тестов, Context7 перед кодом, кодовый граф (RAG).
- **Дизайн-система обязательна в каноне продукта** — и как ограничение UI,
  и как язык мокапов постановки (per-project: дизайн-система в коде —
  evolve/psylia, Figma — betzo).
- **Git-канон**: конвенции коммитов/веток/MR + жизненный цикл ветки +
  механический энфорсмент (хуки, protected branches, CI-линт) + уборка
  через карантин-bundle с TTL.

### 3.2 Библиотека UJM — исполняемые пути пользователя

UJM (User Journey Map) — карта пути пользователя + Playwright-код,
прогоняющий путь по стенду. Путь каталога — per-project в конфиге; этап 2 —
пилот на evolve. Стек: playwright-bdd (человеко- и ИИ-читаемый
`.feature`-каталог) + официальные Playwright Test Agents (Healer чинит
ТОЛЬКО в MR и только локаторы — дифф assertions отклоняется автоматически)
+ reports-server (флаки, тренды) + мультиюзер-фикстуры (CRDT-сходимость).
Периодический mutation-чек: намеренно сломанная фича обязана уронить UJM.

Потребители: волна (вместо самодельного смоука), диспетчер (смоук после
мержа), QA-роль (ночная регрессия с определённым контуром: стенд,
синтетический seed, секреты, владелец флаков), люди (живая карта продукта →
Confluence из шапок). Владелец каталога — роль в фреймворке (человек или
ИИ): формат, гейты качества, ревью пополнений. Пополнение: карта флоу
live-прогонов; фича, меняющая путь, обновляет UJM тем же тикетом.

### 3.3 Продуктовая петля

Два входа постановки: **мандат** (решённая фича → feature-intake) и
**ставка** (гипотеза → product-flow). Гипотеза формируется первой как
карточка-родитель; при утверждении из неё встают и линкуются dev/design-
таски — прогресс и замер трекаются сквозь карточку. Телеметрия (PostHog,
Langfuse, UJM-прогоны) автоматически становится замером; система готовит
проект вердикта — утверждает человек (авто-вердикт только по заранее
заданным порогам). Замер сопровождается журналом допущений и peer-review-
чеклистом. События аналитики — часть DoD фичи (иначе к этапу 5 мерить
нечем). Мини-аппы продакта — легитимный способ проверки гипотезы; каждому —
карточка в знание-слое.

### 3.4 QA-модель

Пилот — GLM Coding Plan Lite помесячно (Kimi недоступен: продажи
приостановлены; MiniMax/Qwen/DeepSeek отсеяны ресёрчем). Exit-критерии
фиксируются до покупки: ≥N успешных UJM-прогонов, расход промптов за
5-часовое окно в пределах квоты, доля успешных починок. Сценарии пилота:
скриншот→тест, починка селектора по trace, ночной цикл, замер квоты.
Роль = слот, модель = картридж (строка в конфиге). Данные — по политике
границ per-вендор (см. Риски): GLM получает только e2e-код, тестовый стенд
и синтетический seed.

### 3.5 Документация: три слоя

**Репо — как устроено; vault — что мы думаем и почему; Confluence — что мы
показываем.** Источник правды — репо/vault (Obsidian-канон по betzo-модели:
пакет-папки гипотез, канон-файлы с хозяином и сроком годности фактов, тип
заметки в имени файла, Bases-доски). Confluence — витрина: рендер md2conf
(папка → родительская страница, привязка по `confluence-page-id` — единое
поле, точечный режим на файл, баннер generated, ручные правки запрещены);
единственный публикатор — пайплайн. Документирует та роль, что меняла, —
правкой источника. Для betzo: сначала аудит-уборка vault (знание / рабочие
папки / мини-аппы / архив), затем белый список, затем зеркало.

### 3.6 Трекер-канон

Основа — обкатанная модель psylia: 6-ступенчатая лестница статусов через
маппинг в конфиге (`backlog/in_progress/review/rework/testing/done`; имена
на доске любые); категория Jira-статуса — часть канона; маршруты `dev` +
`product` (product-тикет — родитель/гейт dev-тикетов); слой STATUS-журнала
и ROADMAP-потоков над трекером («в Jira только приоритизированное»);
каждый переход — с комментом; техдолг-журнал конвертируется в тикеты
грумингом. Ручной ввод для людей — только Jira, остальные представления
генерятся.

## Дорожная карта

Граф: **0 → (1 ‖ 2) → 3 → 4а → 4б → 5**. Каждый этап имеет
самостоятельную ценность и фальсифицируемый критерий готовности.

**Переходный контракт (до этапа 3)**: волны работают по текущему протоколу
с вотчерами, подлатанными этапом 0; сверх гигиены в него не инвестируем;
каждому мосту — тикет на снос с триггером. **Этап 0 выполняется синхронными
сессиями под наблюдением человека** — чинить механизм пробуждения волнами,
которые он будит, — цикл.

**Календарь и мощность**: конец этапа 2 — 2.5–3.5 месяца, этап 4а — к
концу года (при приоритете боевых задач). Квота стройки — одно 5-часовое
окно одного аккаунта в день; WIP — одна вертикаль за раз. Ключевые ставки
стройки (job-модель, headless-экономика подписок, Claudexor) оформляются
карточками гипотез с порогами — по собственной дисциплине системы.

| 4а | Флот: вертикаль | headless-запуск по одному профилю; job-конвейер одного типа задачи на одном проекте (пилот Claudexor) | N тикетов подряд разных типов проходят Jira → MR → CI → UJM, ≥K% без записей в журнале вмешательств; каждое вмешательство классифицировано |
| 4б | Флот: мультипрофиль | ≥2 профилей, лимит-планировщик двух уровней, ротация, парковка/каскад | лимит одной подписки не останавливает фабрику (проверено намеренным дожиганием окна) |
| 5 | Петля | телеметрия → замеры гипотез; авто-подготовка вердиктов | проект вердикта гипотезы формируется из данных без ручного сбора; человек утверждает |

## Метрики фабрики

Сенсоры: Jira changelog, журнал вмешательств в будке, ccusage/OTel,
ticket-id в контексте job'а (закладывается в job-модель — задним числом не
восстановить). Baseline снимается на этапе 0.

1. Cycle time тикета по стадиям (отдельно — ожидание вердикта).
2. Доля автономных прохождений (без `human_intervention`).
3. Стоимость тикета в окнах и токенах.
4. First-pass yield (без возврата в rework; % отклонённых healer-MR).
5. Утилизация флота и «голодание» очереди.

## Риски

| Риск | Митигация |
|---|---|
| Разморозка «Agent SDK credit»: headless на подписках переоценят по API-ценам (анонс приостановлен) | риск №1 флота: fallback-профиль на API-ключ/интерактив; Desktop-контур сохраняется; unit-экономика тикета считается до этапа 3; определён минимальный выживающий режим (алерты + UJM-регрессия на GLM) |
