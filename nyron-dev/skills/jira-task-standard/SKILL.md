# Стандарт Jira-задачи AI Evolve / Nyron

Скилл — единый канон «как писать таски» для людей и агентов. Им пользуются:
человек, заводящий тикет; диспетчер волн на груминге (`nyron-waves`);
live-тестирование при оформлении находок (`live-epic-testing`); сборка
QA-приёмки (`qa-handoff`).

## Конвенции трекера — из конфига проекта

Имена типов, лейблов и статусов у каждого продукта свои. Брать их из конфига
(скилл `project-config`): `jira.site`, `jira.project_key`, `jira.issue_types`,
`jira.labels`, `jira.statuses`, `jira.routes`. **Поля нет → дефолты ai-evolve**
(таблица ниже) — старые конфиги продолжают работать без правок.

| Что | Ключ конфига | Дефолт (ai-evolve) |
|---|---|---|
| Трекер и проект | `jira.site` / `jira.project_key` | nyron.atlassian.net, DEV |
| Типы | `jira.issue_types` | «Задание» (НЕ «Задача»), «Баг», «Subtask», «Эпик» |
| Лейблы зоны | `jira.labels` | `front` / `back` / `agent` / `infra` / `catalog` |
| Маршрут отдела | `jira.routes` | один проект = `jira.project_key` |
| Папка эпика | `epic_folder` | `ai-evolve-docs-test/waves/{key}-{slug}` |

Общее для всех проектов:

- `qa`-лейбл — только для явных задач QA-инженеру.
- Эпики — через parent. Assignee следует за статусом (канон маршрута —
  `docs/SYSTEM.md` плагина): в Ревью — постановщик, в Доработке —
  исполнитель, в «Готово к
  тестированию»/Тестировании — QA; «Готово» ставит только QA.
- Create ведёт в «Дизайн - проектирование» (продуктовая проработка):
  заведённый ГРУМЛЕННЫЙ тикет сразу переводить в Бэклог или К выполнению;
  в «Дизайн - проектирование» остаётся только сырьё, которое ещё штормится.
- Дубли не плодить: перед созданием сверить с эпиком (JQL `parent = <эпик>`).
  Статус «Отменено» — только у дублей, с done-кредитом комментом в живом тикете.
- Имена статусов различаются между досками («Бэклог» vs «К выполнению») —
  ориентироваться на категорию (new / indeterminate / done), transition id
  получать `getTransitionsForJiraIssue` по месту.
- `storage: files` → тикета нет: задача = файл в `files.tasks_dir` с тем же
  содержимым, статусы двигаются правкой фронтматтера.
- **Постановка человеку вне флота — без инструментов плагина.** Assignee без
  плагина nyron-dev (работает в своём Клоде/чате) не имеет будки, `hub_post`,
  скиллов и MCP — тикет и промт для него их не требуют. Канал отчёта такого
  исполнителя — коммент тикета, чат или коммит; в постановке явно написать,
  чем он пользуется (урок 21.08: отчёт, заложенный в будку человеку без
  плагина, не мог состояться). Кто оснащён, а кто нет — сверять по реестру
  внешних участников: записи `roles.<slug>` конфига с `plugin: false` и
  `report_channel` (скилл `project-config`).

## Обязательная структура тикета — форма задачи (7 разделов)

Утверждена CTO 08.08.2026. Шаблон с примером «плохо → хорошо» —
`assets/task-template.md`. Разделы 1–6 — гейт готовности (DoR): **без них
тикет не проходит в «К выполнению»**, кем бы ни был заведён. Раздел 7
дотягивает разработка на груминге.

1. **Что делаем** — заголовок глагольной фразой результата + суть; JTBD:
   «когда <ситуация>, я хочу <действие>, чтобы <ценность>».
2. **Зачем** — ценность по JTBD или связь с эпиком; контекст с пруфами,
   без сленга.
3. **Как работает** — ожидаемое поведение по шагам; путь пользователя
   (UJM) и шаг из каталога `ujm/` docs-репо, либо честное «вне UJM:
   инфраструктура/тесты/рефакторинг» — по этому полю собирается пакет QA.
4. **Дизайн** (обязателен для UI-задач, отдельным блоком) — скриншоты
   именно того куска/состояния, который делает тикет (живут в
   `requirements/<слаг>/` docs-репо), + строка «что актуальное / что
   строим». UI не трогается → явная строка «UI не трогается».
5. **DoD** — список наблюдаемых поведений без пересечений и без дыр с пруфами.
6. **Как тестировать** — сценарий по шагам, каждый шаг размечен
   **[AI-прогон]** / **[руками]**; **где лежат тесты** (папка задачи в
   тест-репо, юниты и E2E поимённо); чекпойнты «протестировано: …».
   ДВА раздельных слоя, смешивать запрещено:
   - **Приёмка руками** — только то, что видно на экране: предусловия в
     терминах данных стенда (аккаунт, роль, тариф, компания — и они обязаны
     существовать), шаги, наблюдаемый пользователем результат. Прогоняется
     без чтения кода. Эффект виден только внутри системы → пишем прямо:
     «руками не принимается, приёмка автотестом X» + наружный инвариант
     («право отзывается не позже N секунд»).
   - **Проверки разработчика** — логи, внутренние запросы, тесты. Живут в
     Техконтексте, в ручную приёмку не входят.
   При сдаче тикета в «Готово к тестированию» исполнитель ОБНОВЛЯЕТ этот
   блок фактом — QA-блок в комменте-пруфе (канон перехода — скилл
   nyron-waves): автотестами покрыто (пути) / руками-чекпоинты / техническое
   отсмотреть. Постановочный сценарий — план; QA-блок — факт сдачи.
   Техника выбирается по `references/test-design.md` (Equivalence
   Partitioning / State Transition / Decision Table / сценарий). Для фич с
   нечётким критерием («релевантно», «похоже») обязательны 3-5 эталонных
   пар «вход → ожидаемый результат», иначе критерий — вкус, а не проверка.
   Кейсы блока трижды переиспользуются: имена dev-тестов → чек-лист
   QA-приёмки → регресс.
   Опционально: **Вне скоупа** — что сознательно не делаем.
7. **Техконтекст** (заполняет разработка на груминге) — файлы и зоны,
   декомпозиция, план реализации комментом на чекпойнте; пути, логи,
   гипотезы о корне; единственное место, где допустим сленг.

## Форма эпика (8 разделов, все обязательны)

1. **Что делаем** — суть фичи одним абзацем.
2. **Зачем** — JTBD.
3. **Как работает** — сценарий пользователя по шагам.
4. **Дизайн** — макеты и материалы отдельным блоком; UI не трогается →
   так и пишется явно.
5. **DoD эпика.**
6. **Сквозной сценарий тестирования** — приёмка эпика ЦЕЛИКОМ, по
   галочкам; **прогоняется ДО закрытия последнего дочернего тикета**
   (иначе провал сквозного прогона нечем возвращать — дети уже в Готово).
7. **Нарезка** — дочерние тикеты (появляется после груминга).
8. **Техконтекст** — зоны, репы, риски; каждый флаг — с тикетом на снос.

Разделы 1–6 эпика — тот же DoR: без них эпик не грумится в задачи.

**Гейт статуса**: тикет не переводится в «Тестирование» без блока «Приёмка
руками» (или явной пометки «руками не принимается»). Пустое описание в
статусе тестирования — дефект процесса.

## Стиль (McKinsey)

- **Пирамида**: вывод/результат первым — заголовок и первая строка отвечают
  «что получим».
- **Кратко и однозначно**: одно предложение — одна мысль; двоякое чтение —
  переписать; без воды и «и т.д.».
- **Без сленга в человеческом слое**: текст читается методологом, продактом,
  CEO с первого раза. Сугубо техническая задача (рефакторинг, инфра) всё равно
  получает человеческий верх в 1-2 строки: зачем это бизнесу/команде.
- **Без пересечений и без дыр**: пункты DoD не пересекаются и покрывают всю готовность; задачи
  внутри эпика не пересекаются по скоупу и покрывают всё ТЗ без дыр (нашли
  дыру — новая задача, а не раздувание существующей).

## Приём бизнес-задачи (наштормленной)

> Пришла **решённая фича / бизнес-требование** («надо добавить X»), а не готовое
> ТЗ на тикет → сначала скилл **`feature-intake`**: требование как артефакт
> (файл) → согласование → эпик. Сюда возвращаемся, когда пора оформлять тикеты.

Задачи от методолога, продакта, CEO (часто перенос из Weeek: целое ТЗ с
мокапами и правками-поверх-правок в описании) — НЕ отбрасывать, а доводить:

1. **Решить форму** (декомпозиция):
   - **эпик + задачи** — работа шире одного участка кода/одной итерации
     (несколько репо, ролей, недель);
   - **задача + подзадачи** — один участок, много шагов;
   - **одиночная задача** — влезает в тикет.
2. **ТЗ целиком** (мокапы, сценарии) — файлом в папку эпика
   (`epic_folder` конфига; дефолт
   `ai-evolve-docs-test/waves/<DEV-эпик>-<слаг>/spec-….md`), в тикетах — ссылка
   и JTBD/DoD-выжимка. Задвоения в исходном описании вычищаются, канон = файл.
3. **Довести каждый тикет** до структуры выше. Смысл меняется или неоднозначен —
   вопрос автору КОММЕНТОМ в тикет, не гадать; до ответа тикет в работу не берётся.

## Суперповеры в флоу (если установлен плагин superpowers)

Встраивать по ситуации, с мягкой деградацией (нет плагина — пропустить шаг):

- Требования мутные, «хочется вот такого» → **superpowers:brainstorming**
  ДО декомпозиции: расшторм с постановщиком, итог — согласованные требования.
- Большая фича, нужна спека/план → **superpowers:writing-plans**: спека файлом
  в папку эпика, в тикеты — ссылка.
- Готовая спека в Confluence → скилл **atlassian:spec-to-backlog** как черновик
  декомпозиции, затем довести тикеты до этого стандарта (он создаёт сырые).
- Тикет-баг → в DoD строкой: «корень назван в отчёте» —
  **superpowers:systematic-debugging** (нет фикса без корня); детали
  встраивания — nyron-waves «Багфикс-тикет — только через корень».
- Перед заявлением «готово» в любом отчёте — свежий прогон с пруфом, не
  память о прошлом прогоне: **superpowers:verification-before-completion**
  (наш канон «каждый шаг фактом» — то же правило; скилл — развёрнутый
  протокол для спорных случаев).

## Чек перед сохранением тикета

- [ ] заголовок = результат; JTBD есть; DoD без пересечений и без дыр, проверяем;
- [ ] DoD и «Как тестировать» написаны так, что груминг соберёт из них
      «Паспорт конвейера» (nyron-waves) без переписывания: DoD — плоский
      список наблюдаемых поведений, кейсы — конкретные шаги;
- [ ] человеческий слой без сленга; технарское — в Техконтексте;
- [ ] «Как тестировать» есть (для багов/фич с поведением);
- [ ] parent/лейблы/assignee выставлены; дубль проверен по эпику;
- [ ] батч тикетов эпика: нарезка прошла челлендж постановок (Fable-штурм +
      Sol plan-challenge, канон `cross-review` §«Второй контур») ДО выдачи
      брифов — тикеты по непроверенной постановке не заводятся;
- [ ] длинное — файлом в папку эпика, не в описании.
