# feature-intake — требование как артефакт

У продукта есть вход, которого не покрывает ни один другой скилл плагина:
**решённая фича**. Стейкхолдер (продакт, CEO, комплаенс, сам разработчик) хочет
добавить функционал. Это **мандат** — его не проверяют ставкой, его доставляют.

Плагин силён справа (доставка: `nyron-waves`) и в форме тикета
(`jira-task-standard`). Слева не хватало **формы самого требования** и **гида
разворачивания**. Этот скилл — только про них, тонкий: всё остальное делают
смежные скиллы, он на них ссылается и не копирует.

**Развилка на входе, одна строка:** не уверены, что взлетит, и хотите проверить
замером — это **ставка**, ей занимается скилл `product-flow`, не этот. Уверены и
решили делать — **мандат**, работаем здесь.

## Два раздельных шага

Требование и эпик — разные события, между ними живёт обсуждение и согласование
(созвон, комменты, правки). Скилл НЕ склеивает их в одну кнопку.

| | Р1 «Собрать требование» | Р2 «Развернуть в эпик» |
|---|---|---|
| Когда | принесли хотелку | требование согласовано (`status: согласовано`) |
| Кто запускает | автор требования | тот, кто берёт в работу (продакт/диспетчер) |
| Выход | файл-требование + открытые вопросы | эпик в трекере + папка эпика + нарезка задач списком |
| Тикеты задач | не заводит | не заводит (это груминг) |

## Р1 — собрать требование

1. **Конфиг**: прочитать конфиг проекта (скилл `project-config`) —
   `storage`, `files.requirements_dir`, `routes`, `models.*`.
2. **Принять сырьё**: текст, голос-расшифровка, скрин, ссылка, пересылка.
   Сырьё — каша (правки поверх правок, несколько хотелок) → сначала
   `intake-groom` дешёвой моделью, дальше работать с его выжимкой.
   Сырьё сохраняется дословно (секция «СЫРЬЁ» в файле) — ничего не теряем.
3. **Довести диалогом — два режима** (гриль-механика; паттерн
   grilling/grill-me М. Покока, решение 03.08):
   - **«Покрутить»** — сначала свободная раскрутка: варианты, аналоги в
     продукте, прототип собирается и переделывается без протокола. Идею
     не допрашивают, пока она не оформилась.
   - **Гриль** — идея оформилась: вопросы ПО ОДНОМУ, к каждому —
     рекомендованный ответ (автор соглашается или правит, а не сочиняет
     с нуля). **Факты и решения разделены жёстко**: что можно узнать из
     репо (это уже есть в продукте? какие пути каталога UJM задеты?) —
     Claude ищет сам и спрашивать не имеет права; автору достаются только
     решения. Финал — не раньше общего понимания.
   Обязательный минимум: зачем это бизнесу; кто пользователь; что считаем
   готовым. Дыра в требовании — **открытый вопрос**, не фантазия скилла.
4. **Прототип** (для фичи с интерфейсом — обязателен):
   - **форма для многошагового флоу — сквозной живой прогон** (канон с
     пилота 04.08): одна страница, где автор проходит путь фичи САМ —
     вводит реальный запрос, кликает настоящие кнопки, идёт по этапам
     (прогресс-шаги сверху: например «Лендинг → Подбор → Регистрация →
     Запуск»), с кнопкой сброса и подсказками для всех веток. Табы
     статичных состояний — только для одноэкранных фич;
   - **сборка — переиспользованием, не перерисовкой**: экран/секция уже
     существует в бою → импортировать боевой компонент/секцию в прогон;
     рисовать самодельную копию существующего экрана ЗАПРЕЩЕНО
     (лестница: «уже есть у нас» — используй; копия разъедется с боем и
     соврёт автору). От себя рисуются только TODO-куски, которых в бою
     нет;
   - только из компонентов дизайн-системы проекта (правила — CLAUDE.md в
     папке дизайн-системы; голый HTML запрещён quality_floor);
   - страница — ПОЛНЫЙ путь `/design-system/proto/<слаг>` (внутри витрины
     дизайн-системы: этот роут публичный — вне auth-гейта и редиректов
     неизвестных путей; страница на «своём» роуте вне витрины уводит
     неавторизованного на корень — проверено пилотом 04.08), ветка
     `proto/<слаг>` фронт-репо (сборку кода делает front-dev-агент,
     не сессия гриля);
   - **показ — во встроенном браузере сессии**: Claude поднимает dev-сервер
     (конфигурация в `.claude/launch.json`, отдельный порт под прототип)
     и открывает страницу в предпросмотре — автор кликает и крутит дизайн,
     не выходя из чата; «ссылка в терминале» показом не считается;
     вьюпорт сразу выставить десктопным (ширина ~1440–1620, resize окна
     предпросмотра) — узкая панель показывает мобильную вёрстку и врёт
     о дизайне; мобильный вид — вторым шагом по запросу автора;
   - **страница не реагирует на клики → перезагрузить вкладку
     предпросмотра**: протухший кэш dev-сервера «омертвляет» страницу
     (не гидратируется), HMR к прото-серверу не коннектится (грабля
     пилота 04.08). Сказать автору об этом ДО показа — мёртвый клик не
     должен его пугать; перезапуск сервера не нужен;
   - **самопроверка ДО показа**: прежде чем звать автора, сессия сама
     проверяет визуал — скриншот каждого состояния, клики живые (страница
     гидратировалась), консоль без ошибок, вёрстка из компонентов
     дизайн-системы; автору отдаётся проверенная картинка — его глаза
     нужны для решений о дизайне, а не для отлова кривой вёрстки;
   - разметка блоков: «актуальное» (уже есть; заявлено «есть», а в коде
     нет → это вопрос автору, гриль сверяет сам) / «TODO» (строим);
   - **переключатель «чистый вид»** прямо на странице прототипа: одна
     кнопка (уголок экрана) скрывает ВСЕ служебные пометки — бейджи
     актуальное/TODO, подписи, отладочные тосты; автор смотрит интерфейс
     глазами пользователя, потом включает пометки обратно для разбора
     скоупа;
   - **прототип мержится в main** после согласования требования (MR автора,
     обычное ревью): раздел «Прототипы» витрины индексируется обходом
     `proto/*`, и только из main прототип виден исполнителю тикета, QA и
     дизайнеру без чекаута чужой ветки. Утечки в прод нет — витрина
     закрыта флагом (`VITE_DESIGN_SYSTEM_ENABLED`, в проде 404). Ветка
     `proto/<слаг>` — место сборки и ревью, не вечный дом;
   - в шапке страницы прототипа — ключ эпика/тикета, к которому он
     относится (иначе через месяц не опознать, чей это прототип);
   - прототип смертен: удаление страницы (и ветки) — пункт DoD эпика;
   - **общая польза из прото-ветки не умирает вместе с прототипом**: если
     по ходу сборки исправлено что-то общее (витрина, компонент
     дизайн-системы, конфиг), это выносится ОТДЕЛЬНЫМ коммитом/MR в main
     сразу — не ждёт закрытия эпика и не уезжает в утиль (грабля пилота
     04.08: улучшение сайдбара витрины застряло в прото-ветке);
   - **прото-ветка живёт в свежести**: перед показом автору — подтянуть
     main (rebase/merge). Прототип на устаревшей базе врёт о продукте
     ровно так же, как самодельная копия.
5. **Файл-требование создаётся РАНО и дописывается по ходу** (урок пилота
   03.08: обрыв сессии — сбой, лимит — в любой точке должен терять минуты,
   а не наработку интервью). Завести файл по `assets/requirement-template.md`
   в `files.requirements_dir` (`<слаг>.md`) сразу после «покрутить» (сырьё +
   JTBD + первые решения), дальше дополнять после каждого блока ответов.
   Фронтматтер:
   `status: draft` · `owner` · `epic: ""` · `tickets: []` · `departments`.
   Тест-кейсы — черновиками путей каталога UJM (текст «что, как, куда»,
   формат `ujm/` docs-репо), не вольной прозой: на нарезке они станут
   полем «путь UJM» тикетов, а после доставки — автотестами каталога.
6. **Самодостаточность файла — требование читает не тот, кто грилил**
   (груминг, разработчик, QA). Обязательно:
   - **скриншоты выбранного дизайна в файле**: каждое состояние экрана
     (чистый вид, без служебных пометок) — картинкой в
     `requirements/<слаг>/` со вставкой в текст. Прототип смертен —
     скриншоты вечны: дизайн обязан пережить смерть ветки прототипа;
   - **раздел «Дизайн»**: какой вариант выбран и почему; список состояний
     экрана; что в каждом «актуальное», что «TODO» — словами;
   - **смоук свежим читателем**: перед сменой статуса файл читает
     субагент БЕЗ контекста гриля с вопросом «что тебе непонятно, чтобы
     это сделать?»; непонятки чинятся в файле или уезжают в «Открытые
     вопросы». Не прошёл читателя — статус не меняется.
7. **Вернуть человеку**: ссылка на файл и прототип + открытые вопросы
   списком + сигнал размера (эпик / задача / мелочь) одной строкой.

### Якорь в каталоге путей (сразу после конфига, ДО вопросов)

Открыть каталог UJM проекта (`ujm/` docs-репо), сопоставить фичу с путями
и сообщить исход автору ВСЛУХ — один из трёх:

- **путь есть** → «фича меняет путь X, шаги Y»; кейсы требования пишутся
  дельтой к его карте;
- **пути нет** → сначала заводится скелет пути (карта «что, как, куда»,
  3–5 строк, формат-эталон каталога) прямо в гриле — фича становится его
  изменением; каталог пополняется фичами, а не отдельным геройством;
- **фича вне путей** (инфраструктура, внутренности) → честное «вне UJM»
  в требовании.

Без якоря вся цепочка ниже работает на фикции: поле «путь UJM» тикетов
нечем заполнять, разбор находок («ломает путь?») не имеет линейки,
QA-пакет ссылается в пустоту.

### Дома общего элемента (вместе с якорем, ДО вопросов)

Для каждого элемента/компонента, который фича меняет, найти ВСЕ его
места использования — механически, по коду (кодовый граф: call-sites /
использования компонента; нет графа — grep по имени), а не по памяти.
Элемент живёт больше чем в одном месте → исход автору ВСЛУХ:
«этот блок общий для X и Y — меняем оба, только X (Y нужен фолбэк) или
разъезжаемся осознанно?» Решение фиксируется в требовании (скоуп /
вне скоупа). Менять общий элемент, зная только один его дом, —
источник регрессий в соседних режимах (грабля пилота 04.08: блок
выдачи общий для лендинга и маркетплейса, гриль видел только лендинг).

### Живой пруф для «уже работает»

Заявления «уже в бою / уже работает» и метка «актуальное», от которых
зависит скоуп фичи, требуют живого пруфа со стенда: прогон руками или
скриншот. Git-лог и наличие кода пруфом НЕ считаются: коммит ≠
задеплоено ≠ включено флагом (грабля пилота 04.08: «авто-активация в
бою» по коммитам DEV-693 — живьём поведение отличалось). Дешёвое
правило: одна минута живой проверки снимает спор, который археология
по коммитам только разжигает.

Наблюдение браузер-автоматизации — тоже НЕ пруф: синтетический ввод
браузер-тулов даёт артефакты (автозаполнение, негидратированная страница),
и «0 found» при живом ответе API уже случался (грабля пилота 04.08).
Спорное наблюдение перепроверяется руками или реальным юзер-вводом —
и только потом становится фактом скоупа или бага.

### Вариативность дизайна (ключевой экран — всегда варианты)

Для ключевого экрана фичи прототип собирается НЕ в одном варианте:

1. **Внутренний полу-гриль дизайна**: сессия с ролевыми линзами генерит
   2–3 принципиально РАЗНЫХ подхода (разные концепции подачи, не оттенки
   одного) и спорит сама с собой — адвокат каждого варианта, слабые
   топятся до сборки.
2. **Параллельная сборка**: выжившие варианты собирают front-dev
   субагенты одновременно, на одной прото-странице с переключателем
   «Вариант A / B / C» (компоненты — только из дизайн-системы).
   Именно обычные субагенты с возвратом отчёта вызовом: фоновые «товарищи
   по команде» результат родителю не возвращают, и сессия встаёт навсегда
   в ожидании (урок 21.08).
3. **Выбор автора**: показ со сравнением — абзац «за/против» на вариант +
   рекомендация. Автор кликает все и выбирает; выбранный остаётся,
   проигравшие удаляются из прототипа сразу.
4. **Ограничитель**: вариативность — только для ключевого экрана и только
   при содержательной развилке дизайна; мелкая фича или однозначный
   дизайн → один вариант (лестница: не строить лишнего).

### Ролевые линзы (на «покрутить» и перед финалом)

Идею и прототип сессия обязана прогнать через две линзы (ролевые карточки —
скилл `team-roles`; внешние дизайн-скиллы — по канону «если доступен —
обязателен»):

- **Линза продакта**: какую ценность видит пользователь в первые секунды;
  что он должен сделать и почему сделает; не размыт ли оффер.
- **Линза продуктового UX/UI-дизайнера**: иерархия экрана, состояния,
  где пользователь заблудится (скилл `design-critique` — структурная
  критика прототипа).
- **Проверка посылов — отдельным проходом** (скилл `ux-copy`): каждый
  видимый текст прототипа (заголовки, кнопки, пустые состояния, тосты) —
  однозначен и понятен целевому пользователю без контекста команды;
  двусмысленные формулировки выносятся автору списком «как поймёт
  пользователь / что мы имели в виду», а не молча переписываются.

Находки линз показываются автору ДО финала — это часть гриля, не ревью
после.

### Предохранители гриля (от вырождения в «да-да-да»)

- **Дорогое/необратимое решение — без готовой рекомендации**: только
  варианты с ценой каждого. Рекомендация — якорь; давать её можно там,
  где ошибка дёшево чинится.
- **Следить за долей согласий**: подряд >80% ответов «да, как ты
  предложил» — интервью выродилось; остановиться и переключиться на показ
  прототипа («что здесь не так?») — согласие глазами надёжнее усталого «да».
- **Финал — словами автора**: автор пересказывает требование своими
  словами в одну-две фразы; резюме машиной финалом не считается.
- **Тайм-бокс**: сессия ограничена по времени; не уложились — вторая
  сессия, не марафон.
- **Свежесть сессии (защита от выгорания контекста)**: длинная
  гриль-сессия деградирует — начинает отвечать из памяти разговора вместо
  кода. Признаки: третья+ пересборка прототипа; утверждения о коде/дизайне
  без свежего пруфа путь:строка; автор говорит «ты галлюцинируешь».
  Любой признак → СТОП и честное предложение: «передаю в свежую сессию» —
  файл-требование самодостаточен (для этого он и есть), новая сессия
  продолжает от него с чистым контекстом и обязана перечитать код, а не
  верить файлу на слово. Тянуть выгоревшую сессию дальше запрещено.
- **Скоуп-стоп (защита от расползания)**: идея автора меняет уже принятые
  в этом гриле решения или уводит за рамку цели → НЕ крутить молча, а
  вслух дать развилку: (а) **паркуем** — записать в раздел «Идеи на
  потом» требования (кандидат в гипотезу/отдельную фичу) и финалить
  текущий скоуп — это дефолт; (б) **пересобираем скоуп осознанно** —
  только по явному слову автора, с ценой вслух («сбрасываем решения X,
  Y»). Одно требование — одна цель; щедрый на идеи автор — благо, но
  каждая идея получает свой дом, а не растягивает текущий.

**Требования по отделам строятся из `routes` конфига, а не из зашитой
четвёрки.** Включаются ТОЛЬКО вовлечённые отделы: у одного продукта
разработка+дизайн+CRM, у другого один общий скоуп «промо-разработка» —
это нормально, полнота считается по тем блокам, что есть.

Статус `draft → согласовано` снимает **человек**, не скилл. Несогласованное
требование в Р2 не идёт.

## Р2 — развернуть в эпик

Запускается отдельной командой по требованию со `status: согласовано`.

1. **Эпик-контейнер**: создать эпик в трекере — маршрут по `routes` (отдел,
   который ведёт работу), тип эпика и лейблы из конфига трекера. Заголовок =
   глагольная фраза результата; описание — ГЕНЕРАТ из файла-требования
   (JTBD + скоуп + DoD + затронутые пути UJM + ссылка на прототип), руками
   не переписывается: истина — файл в docs, эпик — её проекция.
   Под каждый затронутый путь UJM в нарезке гарантирован тикет/подтикет —
   груминг это проверяет. Каждый UI-тикет несёт блок «Дизайн»: ссылка на
   скриншот СВОЕГО куска из `requirements/<слаг>/` — дизайн доезжает до
   исполнителя тикетом, а не остаётся в требовании.
   `storage: files` → эпика-тикета нет, контейнер = файл-эпик в папке эпика.
2. **Папка эпика** по шаблону `epic_folder` конфига (подстановка `{key}` —
   ключ эпика, `{slug}` — слаг требования). Файл-требование переезжает туда
   (или лежит в `requirements_dir` со ссылкой — как задано в конфиге проекта).
3. **Сшить ссылки в обе стороны**: во фронтматтер требования — `epic: <ключ>`;
   в эпик — ссылка на файл-требование. Тикет без файла и файл без ключа —
   потеря контекста.
4. **Нарезка задач — списком в файле, не тикетами**: разбиение без пересечений и без дыр по
   `routes`/участкам, у каждой строки — результат и отдел. Это черновик для
   груминга.
5. **Челлендж постановки — ДО груминга тикетов и брифов** (урок пилота
   07.08, DEV-1129: без этого шага эпик уезжает в тикеты непроверенным, и
   ошибка постановки всплывает перезапусками имплементации). Для эпика —
   ОБЯЗАТЕЛЕН, двумя головами по канону `cross-review` §«Второй контур»:
   Fable-штурм (узкие места мышлением: развилки, скрытая сложность,
   «а надо ли так») + Sol `plan-challenge.sh` по требованию+нарезке
   (сверка с реальным кодом: ложные предпосылки, пересечения нарезки,
   дыры DoD). Риски правят требование и нарезку НА БУМАГЕ — до выдачи.
   Мелочи (одиночная задача, одна файл-зона) — можно пропустить, решение
   вслух.
6. **Передать в доставку**: сказать человеку, что дальше — груминг по
   `jira-task-standard` (форма тикетов) и `nyron-waves` (волны). Скилл
   останавливается здесь.

## Правила

- **Мандат, не ставка.** Никаких HADI-петель, замеров и вердиктов: требование
  считается принятым по DoD, а не по метрике эксперимента.
- **Не выдумывать.** Всё мутное — в «Открытые вопросы» с адресатом. До ответа
  требование остаётся `draft`.
- **Человеческий слой без сленга** (McKinsey: пирамида, кратко, однозначно;
  критерии приёмки без пересечений и без дыр) — канон стиля в `jira-task-standard`, не дублируем.
- **Один артефакт — одна цель.** Две несвязанные хотелки → два требования.
- **Тикеты задач скилл не заводит** никогда: сырые тикеты потом всё равно
  переписывать на груминге.

## Смежные скиллы

- `project-config` — куда писать, какие отделы и типы у трекера.
- `intake-groom` — причесать кашу до Р1 (дёшево, sonnet/haiku).
- `jira-task-standard` — форма тикетов после Р2 и канон стиля.
- `nyron-waves` — доставка эпика волнами.
- `product-flow` — второй продуктовый вход: ставка (гипотеза → замер → вердикт);
  шаг разворачивания в эпик у нас общий.
- `superpowers:brainstorming` — если требование мутное и «хочется вот такого»:
  расшторм с автором ДО записи файла (мягкая деградация: нет плагина — просто
  диалог по шагу 3).
