# Подключение плагина к проекту — одноразовые шаги

Читать, когда конфига проекта ещё нет или его надо поднять на новой машине.
В повседневной работе этот файл не нужен: скиллам хватает тела `SKILL.md`.

## 1. Создание конфига

1. Скопировать структуру из `assets/config-template.md`.
2. Спросить у пользователя минимум (не растягивать интервью): тип проекта,
   хранилище задач (есть ли Jira и какой ключ проекта), чем занимаются рабочие
   (код или данные), какие роли включить.
3. Заполнить `roles.*.context` реальными путями проекта («куда смотреть»
   каждой роли: папки доков, дашборды, канон-файлы) — это главная проектная
   ценность конфига; пустые списки не оставлять, лучше спросить.
4. Записать `.claude/nyron-dev.md`, добавить в `.gitignore` проекта
   `.claude/nyron-dev.local.md` и `.nyron-hub/` (состояние будки).
5. Показать пользователю итоговый конфиг одним сообщением.

## 2. Чек-лист переноса на новый кодовый проект

1. Плагин + конфиг по шагам выше: `models.*`, `quality_floor`, `flows`, роли.
2. **Граф кода**: бинарь codebase-memory-mcp (релиз под платформу, сверить
   чексуммы) → запись в `.mcp.json` проекта (gitignored) → `index_repository`
   каждого репо (секунды). Реиндекс при мерже уже прописан в каноне волн.
3. Репо или каталог тестов с реестром: у каждого теста шапка-описание.
4. `.env.example` в каждом репо; секреты только из окружения, дефолтов-секретов
   в коде нет; целевое хранилище — переменные CI.
5. Правила волн собрать в проект: `python3 <plugin>/hub/wave-rules-sync.py
   --apply` и заполнить `<docs_dir>/shared/wave-rules.project.md`.
6. Политика кода приезжает сама SessionStart-хуком плагина — в CLAUDE.md
   проекта её не дублировать.

## 3. Jira MCP проекта (для `storage: jira`)

Канон доступа для ВСЕХ проектов — **локальный project-MCP в `.mcp.json` корня
проекта** (докерный `mcp-atlassian` по API-токену: работает в headless-сессиях,
без капризов OAuth). Плагинный или облачный Atlassian-коннектор — только
интерактивная альтернатива.

1. Проверить `.mcp.json` корня: есть ли сервер с именем из `jira.mcp_server`.
2. Нет — создать запись из `assets/jira-mcp-template.json`: подставить сайт и
   корпоративную почту; **API-токен спросить у пользователя** (id.atlassian.com
   → Security → API tokens) — в чужих секретницах его не искать. Нужен
   запущенный Docker.
3. Убедиться, что `.mcp.json` в `.gitignore` проекта — там токен.
4. Смоук: `jira_get_user_profile` отвечает.

## 4. Каноны проекта для codex (AGENTS.md)

Codex (кросс-ревью, челлендж плана, codex-тул) НЕ читает CLAUDE.md — его
конвенция `AGENTS.md` (та же иерархия: `~/.codex/AGENTS.md` → корень git →
подпапки, лимит ~32KiB на файл).

**Канон (codex ≥ 0.144)** — одна строка в `~/.codex/config.toml`, глобально для
всех проектов, в репо ничего не коммитится:

```toml
project_doc_fallback_filenames = ["CLAUDE.md"]
```

**Фолбэк (codex < 0.144)** — локальный симлинк `ln -s CLAUDE.md AGENTS.md` в
корне и в каждом код-репо с `CLAUDE.md` (не коммитить, если пуш триггерит CI).

## 5. Проектные MCP для codex (`.codex/config.toml`)

Проектный конфиг codex читается ТОЛЬКО для доверенных проектов. Рецепт обкатан
18.07.2026 (codex 0.131):

1. Доверие проекту — в `~/.codex/config.toml`:
   `[projects."<абсолютный-путь>"]` → `trust_level = "trusted"`.
2. `<проект>/.codex/config.toml` — секции `[mcp_servers.<имя>]`
   (command/args/env) + **обязательно** `default_tools_approval_mode =
   "approve"` в каждой: значение именно `approve`, потому что `auto` молча
   игнорируется, и в headless-прогоне вызовы умирают с «user cancelled MCP tool
   call».
3. **Грабля болтливых серверов**: сервер, пишущий служебный текст в stdout
   вперемешку с JSON-RPC, ломает строгий парсер codex. Лечение — обёртка
   `... | grep --line-buffered '^{'` плюс `startup_timeout_sec = 60`, если
   сервер долго стартует.
4. `.codex/` — в `.gitignore` проекта (внутри ключи).
5. Смоук: `codex mcp list` из каталога проекта показывает серверы.

## 6. MCP будки (nyron-hub)

**Грабля инсталлера маркетплейса: дотфайлы плагина (`.mcp.json`) могут не
копироваться в кэш установки** — тогда тулов `hub_*` нет ни в одной сессии, и
все молча работают CLI-фолбэком (вскрыто 22.07: так жили все прогоны). Канон
надёжной установки — user-scope MCP на путь marketplace-клона (клон обновляется
`git pull`, инсталлер ни при чём):

```bash
claude mcp add --scope user nyron-hub -- sh ~/.claude/plugins/marketplaces/nyron-dev-marketplace-v2/nyron-dev/hub/run-hub.sh
```

Проверка в сессии: `hub_status` отвечает MCP-тулом. Якорь будки резолвится
сервером по рабочему каталогу — одна user-scope запись обслуживает ВСЕ проекты
машины, у каждого своя `.nyron-hub/hub.db`. Плагинный `.mcp.json` остаётся для
запусков через `--plugin-dir`; дубль имён безвреден — будка одна и та же.
