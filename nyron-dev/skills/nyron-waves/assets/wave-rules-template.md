# Общие правила волны — {{project}}

Эти правила обязательны для каждой сессии-волны. Чип ссылается на этот файл;
волна читает его первым, вместе с бриф-комментами диспетчера в своих тикетах.

Файл **собирается** плагином: универсальные правила — в шаблоне
`skills/nyron-waves/assets/wave-rules-template.md`, значения — в
`.claude/nyron-dev.md`, проектные уроки — в
`{{docs_dir}}/shared/wave-rules.project.md`. Правка руками пропадёт при
следующей сборке.

## Роль и модели

- Сессия-волна — оркестратор своей волны: координирует, сама код НЕ пишет.
- **Механика → Workflow, решения → сессия.** Workflow обязателен для ДВУХ
  форм механики: (а) пачка независимых кусков (веером: N тестов/файлов/
  тикетов — параллель из коробки); (б) **стадийный конвейер тикета** — даже
  одного: `impl(TDD) → критика находок → фиксы → cross-review → доработки →
  пуш` как pipeline-стадии (цикл доработок — loop с лимитом 2-3 итераций,
  дальше стадия возвращает «блокер»). Выгода конвейера: чекпойнт на каждой
  границе — упал на ревью → тест и код из кэша (`resumeFromRunId`), не с нуля;
  стадию «забыть» невозможно. Скелет — `examples/ticket-conveyor-workflow.md`
  скилла nyron-waves. Сессии-волне остаются РЕШЕНИЯ: вердикты, блокеры,
  шина тикетов, «что дальше» — их в скрипт не зашивать.
- **Масштаб конвейера — по размеру тикета.** Полный конвейер (тестген
  red-тестов чужой моделью, WF-импл, циклы кросс-ревью, полный сьют) — для
  тикетов с поведенческим кодом. Тривиальный тикет — снос ветки/папки/файла,
  переименование, конфиг, где проверка механическая («удалить и убедиться,
  что ничего никуда не пропало»), — гоняется ЛАЙТ-режимом: одна прямая правка
  (агент или сессия по политике кода), механическая проверка (grep
  потребителей + точечный прогон затронутого) и не больше ОДНОГО круга
  кросс-ревью; тестген и полный сьют не разворачиваются, если дифф не трогает
  поведение. Режим задаёт диспетчер в брифе строкой «конвейер: лайт» (волна
  вправе предложить лайт в план-комменте, если бриф молчит) — разворачивать
  полный конвейер по инерции на тривиальном тикете запрещено: это сжигает
  часы и токены без прибавки к качеству.
- Имплементация — субагенты `model:'{{models.code}}'` через проектных агентов
  по зоне (карта зон — в правилах проекта ниже). Ревью кода — `code-reviewer`.
- **Задание субагенту несёт пять вещей, иначе он допишет своё.** Субагент не
  видит ни тикета, ни брифа, ни этого файла — у него только текст вызова.
  Пересказ своими словами теряет ровно то, что потом называют отсебятиной:

  | Что вложить | Как | Почему без этого ломается |
  |---|---|---|
  | DoD тикета | дословно, пунктами | пересказ теряет условия, работа уходит мимо |
  | Зона файлов | список путей + «за пределы не выходить, нашёл проблему рядом — верни строкой, не чинь» | тикет расползается по соседним слоям |
  | Материал, который надо ПЕРЕИСПОЛЬЗОВАТЬ | пути к прототипу, компонентам, существующему механизму | иначе он честно напишет своё с нуля |
  | Политика кода | блок ниже дословно | лестница и три проверки до автора не доходят |
  | Форма ответа | что вернуть: изменённые файлы, ответы на лестницу, что НЕ сделано | без формы отчёт приходит прозой, и волна не может его проверить |

  **Политика кода** — он её не получает сам: хук отдаёт политику сессии, а код
  пишет субагент. В каждый кодовый вызов дословно:

  > Перед кодом ответь на лестницу: (1) нужен ли этот код вообще; (2) нет ли
  > уже в базе — с пруфом путь:строка; (3) нельзя ли параметризацией
  > существующего. Три проверки при написании: не дублируй механизм (покажи,
  > почему не подошёл существующий); не заводи слой без второго потребителя;
  > правка требует трогать три места — скажи об этом, а не размазывай молча.
  > Минимизации не подлежит `quality_floor` проекта. Ответы на лестницу — в
  > отчёт.

  Без этого хвоста автор кода работает без политики, и ревьюер ловит уже
  написанное — вдвое дороже.
- **Помощник, чей результат нужен, — обычный субагент, не «товарищ».**
  Нельзя поднимать фоновых «товарищей по команде» (teammates) для работы,
  результат которой сессия должна получить: товарищ отчитывается «я свободен»,
  результат родителю НЕ возвращает — сессия встаёт навсегда в ожидании ответа
  (боевой случай 21.08: 45 минут простоя при живом спиннере). Нужно: такую
  работу отдавать обычному субагенту, который возвращает отчёт значением
  вызова; фоновый товарищ допустим только там, где его результат сессии
  не нужен.
- Обработка данных, поиск, ресёрч — `model:'{{models.search}}'` (рутина —
  effort low). Массовые однотипные операции — `model:'{{models.mass}}'`.
- Модель ЯВНО в каждом вызове — наследование запрещено; модель-оркестратор
  (`models.dispatcher`) субагентам не назначается.
- Перед генерацией кода — актуальная документация через Context7.

## Каталог и изоляция

- Рабочий каталог — корень проекта на этой машине, как у диспетчера (в брифе
  указан абсолютный путь); пути в брифах — репо-относительные. Изоляция —
  только git worktree от origin/main:
  `git -C <корень-проекта>/<repo> worktree add <путь> origin/main -b <ветка>`
- **Имя и место worktree — конвенция**: `<корень-проекта>/.wt-<тикет>-<репо>`
  (например `.wt-{{jira.project_key}}-968-front`); чужие `.wt-*` не трогать.
  Создание worktree и его удаление — парные шаги: worktree живёт до мержа
  ветки, после мержа пачки его вместе с веткой убирает диспетчер прогоном
  `<plugin>/hub/wave-cleanup.sh --apply` (только `branch -d`). Волна обязана
  не оставлять в своём worktree незакоммиченного: нужное — коммитом в ветку,
  ненужное — снести самой. Иначе уборка встанет, а хвост уедет строкой с
  причиной в отчёт волны.
- Рабочие деревья репо НЕ трогать и НЕ переключать: там могут жить живой
  стенд пользователя и параллельные сессии.
- Мульти-репо волна — одно имя ветки во всех репо (имя — из бриф-коммента).
- **Бронь файлов (будка nyron-hub)**: перед правками по тикету —
  `hub_lock {agent: "wave-N", paths: [<файлы/каталоги от корня проекта>]}`.
  Отказ с конфликтом → в эти файлы НЕ лезть: `hub_post` диспетчеру и работать
  над другим своим тикетом. После пуша ветки — `hub_unlock`.
- **Чекпойнты `hub_post` — ОБЯЗАТЕЛЬНЫ** (не опция): «взял <тикет>» при старте
  тикета, «сдал <тикет>» при сдаче, «волна сдана» финалом, «блокер: …»
  немедленно — это пульс для будка-вотчера диспетчера. Содержательные
  брифы/отчёты/вердикты — по-прежнему ТОЛЬКО комменты тикетов (будка = сигнал
  «читай тикет», не замена шины).
- **Долгий прогон (WF/критика находок/сьют >30 мин) — heartbeat ДО старта**:
  пост `hub_post` «ушёл в долгий прогон <что> до ~<оценка времени>» перед
  запуском, и пост по выходу. Сессия в долгом WF не отвечает на пинги
  (просыпается только по своим нотификациям) и выглядит мёртвой — боевой
  случай 09.08: takeover подняли по волне, которая 4.5 часа честно работала
  молча.
- **Адресация `to:` — только РЕАЛЬНЫЕ имена сессий из будки** (какие есть в
  `hub_status`/брифе), НЕ роль. Пост на несуществующее имя
  (`to: "dispatcher"`) уходит в никуда без ошибки — боевой случай 09.08: пять
  постов волны потерялись. Не уверена в имени — пиши `to: all` с обращением в
  тексте. И слушай шину штатным `hub-watch.sh watch <имя>` — голый
  `hub_read(agent=…)`-курсор терял адресные посты (баг 09.08).

## Git- и Jira-дисциплина

- **Кто сливает в main — решает конфиг проекта** (`merge_rights`), это
  лестница режимов, а не одно правило:
  - `wave` — волна после зелёного финала мержит и пушит в main сама
    (одиночная разработка, маленький проект без живого стенда на main);
  - `dispatcher` (дефолт) — волны пушат СВОИ ветки и отдают MR-ссылки,
    сливает диспетчер по очереди мержа;
  - `lead` / `cto` — волны пушат ветки, диспетчер сводит и готовит пачку,
    право слить — только у названного человека: он садится и сводит MR-ы.
  Режим один на проект и известен волне из этого файла — самовольное
  повышение своих прав (слить при `dispatcher+`) остаётся нарушением.
- При любом режиме, кроме `wave`: **нужно** пушить СВОЮ ветку тикета и
  отдавать MR-ссылку — пуш своей ветки разрешён и является обязательным
  финалом (без этой парной формулировки волна однажды оставила шесть готовых
  веток лежать локально).
- **Мерж пачки делается НЕ в главном рабочем дереве.** Запрет «рабочие
  деревья не трогать» без пары «а где тогда мержить» приводит ровно к тому, что
  диспетчер берёт главное дерево: боевой случай 12.08 — фронт остался на
  временной ветке `merge-1224`, отстав от main на пять коммитов, и локальный
  стенд тихо показывал не то. **Нужно:** отдельный worktree под мерж
  (`.wt-merge-<репо>`) либо мерж без переключения дерева; главное дерево
  остаётся на main. Переключил — верни тем же ходом и скажи об этом в отчёте.
- Финал по тикету = ветка запушена + в отчёт-комменте:
  `git log main..<ветка> --oneline` и MR-ссылка из вывода пуша («To create a
  merge request… visit: …»). Токены не нужны — git по SSH.
- Длинные артефакты (спека, ресёрч, дамп) — файлом в папку эпика
  `{{epic_folder}}` (+пуш док-репо), в тикет — ссылку.
- Док-репо `{{docs_dir}}` пушится напрямую (деплоя нет).
- Каждый значимый шаг — комментом в тикет; статусы двигать по машине:
  взял тикет → «{{jira.statuses.in_progress}}» (+план), готово →
  **«{{jira.statuses.review}}»** (+отчёт, assignee → постановщик); после
  вердикта «ДОРАБОТКА» тикет в «{{jira.statuses.rework}}» — исправить и
  вернуть в «{{jira.statuses.review}}». Дальше волна тикет не двигает:
  «{{jira.statuses.qa_ready}}» ставит диспетчер после мержа и смоука,
  «{{jira.statuses.done}}» — только QA.
- **Маркировка тестирования в отчёте обязательна**: секция «Чем проверено»
  несёт явный маркер `[AI-ПРОГОН]` — какие авто-тесты (unit/integration/e2e)
  прогнаны ИИ, цифрами и с red-фактом; e2e у пользовательских флоу должен
  быть, его отсутствие называется явно с причиной. Что машина проверить не
  смогла — маркер `[РУЧНОЕ QA]` с готовым тест-кейсом: диспетчер перенесёт эти
  пункты в QA-блок при сдаче.
- **Коммит-конвенция**: заголовок коммита начинается с ключа тикета —
  `{{jira.project_key}}-XXX: <что сделано, по-человечески>`; коммит/пуш
  закрывает несколько тикетов — ВСЕ ключи списком. Те же ключи в
  отчёт-комменте и MR.
- **Трекер — через project-MCP из `.mcp.json` корня проекта** (здесь — сервер
  `{{jira.mcp_server}}`, тулзы `mcp__{{jira.mcp_server}}__jira_*`; API-токен,
  headless-надёжен). Первым ходом — смоук `jira_get_user_profile` или JQL по
  проекту. Fallback (Docker/сервер лежит): плагинный Atlassian MCP с грантом
  на {{jira.site}} — грант проверить через `getAccessibleAtlassianResources`;
  чужие коннекторы без гранта не годятся.
- Коммиты и комменты — на русском.

## Границы работы: что чинить, а что нет

Цель волны — закрыть DoD тикета, а не достичь идеала. Покрывать всё найденное
и посыпать голову пеплом — нарушение, а не усердие.

- **Разбор любой находки, три корзины** (без пересечений и без дыр):
  1. **Ломает путь пользователя из каталога** → дефект: тикет сразу.
  2. **Трогает поведение, которого в каталоге путей нет** → это не дефект, а
     вопрос о замысле продукта: одна строка постановщику в очередь решений.
     Тикет заводится только после его ответа.
  3. **Ничего не ломает («можно лучше», стиль, дубль-кандидат)** → запись в
     перечень технического долга `{{debts_file}}`, НЕ тикет. Перечень
     конвертируется в тикеты грумингом пачкой, когда доходят руки.
- **Безопасность — отдельная узкая полоса** (каталог путей её не ловит):
  находка вида «кто-то получает то, что не должен» всегда доходит до
  постановщика, но в четырёх строках: кто → что получает → пруф
  воспроизведения → вопрос замысла. Развёрнутый разбор — по его запросу.
- **Потолок кругов ревью: 2 по умолчанию, 3 для сложного тикета.** Дальше —
  не следующий круг, а решение человека: принять с остатками или отбить.
  Ревьюер по построению всегда что-то находит, а каждый фикс рождает новую
  поверхность — бесконечная сходимость невозможна. Остатки уходят в перечень
  долга (`{{debts_file}}`), круг закрывается.
- **Оценка своей работы — по DoD**, не по количеству найденного. Отчёт «нашёл
  и починил 40 замечаний» без закрытого DoD — провал, а не успех.

**Границы тикета расширяет постановщик.** Согласие ревьюера, волны и диспетчера
между собой границей не является: цепочка «ревьюер нашёл → волна согласилась →
диспетчер подтвердил» замыкается без человека и на каждом шаге выглядит
разумно, а тикет тем временем растёт часами. Но правило не тупое — смежную
дыру, из-за которой функция не заработает, тянуть можно и нужно:

| Находка | Что делаем |
|---|---|
| Мешает функции работать И уже разобрана — понятно, что и где чинить | дотянуть в том же заходе, чтобы функция отработала и не искать это повторно |
| Не мешает функции (стиль, «можно лучше», чужая зона) | отдельный тикет с пометкой «рефакторинг» в бэклог; в текущий круг НЕ берётся |
| Мешает, но не разобрана — надо копать | тикет плюс строка постановщику: функция без этого неполна, решение за ним |

- **Потолок дотягивания:** правка укладывается в небольшой заход внутри
  текущего круга. Вышла за него — это отдельная работа, уезжает второй строкой
  таблицы. Часами упарываться запрещено: цель — рабочая функция, а не идеальный
  код вокруг неё.
- Действует всегда: регресс собственной работы тикета чинится сразу; находка по
  безопасности доходит до постановщика четырьмя строками.
- Отчёт волны показывает отдельной строкой: «дотянуто по ходу: N, отправлено
  отдельными тикетами: N» — видно и то, и другое.

## Качество: инженерный минимум

- TDD: тесты из тикета/брифа — ПЕРВЫМИ (red → green). Если в тикете есть блок
  «Как тестировать» — его кейсы (классы эквивалентности, переходы состояний,
  столбцы decision table, негативные) становятся именами тестов один-в-один.
- **Два сорта тестов — две точки во времени.** Unit и интеграционные — красными
  ДО кода: они и есть спека. E2e по пути клиента — ПОСЛЕ имплементации, как
  приёмка: до кода их писать не с чего. Смешение сортов путает исполнителей.
- **Тесты принимает НЕ их автор — гейт ревью тестов.** До старта имплементации
  диспетчер (или вторая модель) сверяет red-тесты с DoD: покрывают ли каждый
  пункт, нет ли теста без пункта DoD, который он доказывает, нет ли бреда.
  Самопроверка волны гейтом не считается: плохие тесты пропускают плохой код,
  и весь TDD-контур обесценивается.
- **Режим прогона тестов:** в цикле разработки — точечно по затронутому;
  полный набор — ОДИН раз на финале тикета перед сдачей. Полный прогон на
  каждую итерацию запрещён: жжёт время без прироста качества, финальный гейт
  всё равно ловит. Красный финальный прогон → чинить и повторить его целиком.
- Новые тесты: шапка-описание (что и зачем покрывает) + регистрация в каталоге
  тестов проекта — без этого тикет не принимается.
- **Снос функций/полей = grep потребителей + ПОЛНЫЙ сьют.** Боевой случай:
  снос версионности потерял импорт и дал ошибку в рантайме — целевые тесты
  зелёные, полный прогон красный. Проверка синтаксиса ленивые вызовы не ловит.
- **Мок без `spec=` не проверяет сигнатуру** (боевой случай: два вызова с
  несуществующим аргументом, тесты зелёные, потому что патчили голым моком).
  Сервисы патчить только `autospec`/`spec=`. Парное: **базлайн линтера — не
  стена шума**: сверка сальдо «база↔ветка» слепа к дефектам, лежащим В
  базлайне; раз в несколько кругов грепать базлайн по классам, не являющимся
  шумом окружения.
- **git stash в волнах ЗАПРЕЩЁН**: stash — ОБЩИЙ стек на репозиторий, worktree
  его НЕ изолирует. Чужой `stash pop` вытащит ваш WIP, ваш — чужой (инцидент:
  pop притащил конфликт-маркеры и пять посторонних файлов в чистое дерево).
  Сравнение с базой — `git show <ref>:<путь>` или временный worktree. Цифры
  прогонов, снятые с загрязнённого дерева, недействительны — перезапускать.
- **Новая флоу-фича — за флагом, багфикс — БЕЗ флага** (чинится поведение, а
  не вводится новое; багфикс за флагом получает ДОРАБОТКУ). Новый флаг
  заводится вместе с тикетом на свой снос: после ручного теста дефолтом
  становится новое поведение, флаг и легаси-ветка сносятся хвостом.
- **UI-правки сверяются с макетом дизайн-системы.** Если у поверхности есть
  утверждённый живой макет в витрине — КАЖДАЯ правка этой поверхности перед
  сдачей сверяется с ним состояние-в-состояние; расхождение = блокер сдачи.
  Точечный фикс «по тикету», уводящий прод от макета (снятый текст, другой
  статус, другая композиция), — дефект, даже если тикет формально закрыт.
  Витрина права, пока постановщик не изменил её решением.
- **Обход дизайн-системы ловится машинально, до сдачи.** UI-тикет перед
  отчётом прогоняется через `python3 <plugin>/hub/ds-check.py --repo <worktree>`:
  голый `<button>`/`<input>` рядом с импортом классов компонента
  (`*Variants`) — блокер сдачи, потому что классы взяты, а сам компонент
  обойдён. Недостающее добавляется В САМУ дизайн-систему, потом используется.
  Боевой случай DEV-1274: чип паспорта уехал голым `<button>` с
  `badgeVariants`, поймал человек глазами — теперь ловит проверка.
- **Есть прототип — переносить, а не перерисовывать.** Компоненты прототипа
  импортируются боевым кодом; волна добавляет к ним данные, состояния и
  обработку ошибок. Компонент прототипа не подходит → написать постановщику,
  почему, и получить решение. Молча нарисовать заново — нарушение: согласование
  теряет смысл, а работа делается дважды.
- **Ревизия договорённостей перед сдачей.** Если постановщик работал с волной
  живьём (дизайн-такт, live-фидбек в сессии) — перед сдачей ОБЯЗАТЕЛЬНА
  ревизия: поднять всю сессию, выписать КАЖДОЕ его пожелание (включая
  мимоходом сказанные мелочи) и свести таблицей «сказано → сделано /
  оформлено тикетом / отложено с его явного согласия (пруф)» комментом в
  головной тикет. Договорённость, не превращённая в тикет или строку фиксации
  ДО сдачи, — потеряна по определению.

## Парковка по лимиту (без участия человека)

- **Limit-сигнал** (предупреждение «approaching limit» или первая
  limit/429-ошибка субагента) = команда ПАРКОВАТЬСЯ, не пахать дальше:
  окно дожигать на полу-работе запрещено.
- Парковка: (1) чекпойнт — закоммитить WIP в свою ветку как есть
  (`<тикет>: WIP чекпойнт парковки`); (2) `hub_post` «ПАРКУЮСЬ <тикет>:
  <что сделано, что осталось, с чего продолжать>»; (3) перевзвести
  watch-вотчер; (4) завершить ход. Дальше сессия спит на будке (ноль
  токенов) — RESUME-пинг реаниматора разбудит после отката окна, продолжать
  строго с чекпойнта.
- Увидела в будке «ПАРКОВКА ВСЕМ» от диспетчера → та же процедура немедленно.
- Лимит — это ПАУЗА, не смерть: не эскалировать, не бросать тикет, не
  завершаться «насовсем».
- **Handoff-файл (переезд на другой аккаунт)**: `--resume` прикован к
  аккаунту подписки — если окно/неделя аккаунта на исходе, а работа длинная,
  вместо ожидания отката: (1) чекпойнт как при парковке; (2) handoff-файл в
  папку эпика `handoff-<тикет>-<дата>.md`: что сделано (коммиты/ветки), что
  осталось (по пунктам), с чего начать, грабли; (3) в конце файла — готовая
  строка `/goal Продолжи работу по <тикет>: прочитай <путь к handoff> и
  бриф-коммент тикета, работай по wave-rules` — постановщик копирует её в
  любой свободный клон одной вставкой; (4) `hub_post` «HANDOFF <тикет>:
  <путь>» и завершиться.

## Ожидание

- **Долгие процессы (CI, кросс-ревью, docker-сьюты) запускать
  `run_in_background: true`** и заниматься другим — завершение будит сессию
  task-notification'ом. Синхронные sleep/until-циклы в форграунде — только
  когда фоновый запуск недоступен; слепые sleep-поллы «проверю через N минут»
  — нарушение. НЕ завершаться со словами «жду уведомления» без взведённого
  вотчера — сессия уснёт.
- **Ушла в долгий фон — нельзя молчать, нужно сказать человеку в том же
  ходе**: что запущено, сколько примерно ждать и что сессия ждёт уведомления
  о завершении; уведомление пришло — сообщить результат. Молчание при живом
  фоне снаружи неотличимо от смерти сессии (боевой случай 21.08:
  двадцатиминутный скан шёл молча — человек считал сессию мёртвой).
- **Параметр `timeout` на фоновых вотчерах и на кросс-ревью НЕ ставить
  НИКОГДА**: таймаут убивает фоновый процесс (диагноз 27.07: вотчеры с
  timeout=600000 умирали каждые 10 минут — сессия жила в вечном будильнике,
  будка глохла). Вотчер обязан жить до события; долгому скрипту таймаут не
  назначается, его завершение и так придёт нотификацией.
- Зависимая волна (guard в чипе): первым шагом проверить, что ветки
  предшественников ВЛИТЫ в main (пуш ветки ≠ готовность). Не готово — коммент
  в тикет и стоп; поллинг раз в 20–30 минут.

## Финал и шина ревью

**Сколько проверок гонять — по размеру тикета.** Слоёв ровно столько, сколько
называют СВОЙ класс ошибок; остальное — сожжённые часы. Основной независимый
взгляд один — кросс-ревью другой моделью: код пишет Opus, проверяет чужая
семья, и слепые пятна не совпадают по построению.

| | S — правка в одной зоне, поведение не меняется | M — поведенческий код | L или метка СЛОЖНЫЙ — архитектура, миграция, больше одного репо |
|---|---|---|---|
| Челлендж плана | нет | один прогон | два прогона |
| Red-тесты чужой моделью | нет | да | да |
| Критика находок своей моделью | нет | **нет** | да |
| Кросс-ревью | один круг, `-s S` | r1 полный, r2 по диффу фиксов | r1 + r2, `-s L` |
| Тесты | точечные | точечные в цикле + полный набор один раз | то же |
| Сверх того | — | — | разбор конструкции на дорогой модели |

- **Субагент `code-reviewer` в обычном тикете НЕ зовётся** — он дублирует
  кросс-ревью той же семьёй моделей, что писала код. Только когда проверяющая
  модель недоступна, и это пишется в отчёт.
- **Критика находок своей моделью — только на СЛОЖНОМ.** По двум пилотам: на
  простом тикете она дала ноль уникальных находок, всё дубли кросс-ревью; на
  сложном сквозном — двенадцать, и слои дополнили друг друга.
- Раунд ревью без НОВЫХ находок — стоп, следующего круга нет.

- Финал тикета: фиксы по своим тестам → **кросс-ревью другой
  моделью** (скилл `cross-review` плагина: описание тикета во временный файл →
  `scripts/cross-review.sh -C <worktree> -b main -t <файл> -s <размер тикета>` —
  запускать ФОНОВЫМ Bash (`run_in_background`, вывод в файл), пока проверяющая
  модель думает 2–5 мин — пилить следующий тикет, вердикт забрать по
  нотификации; блокеры в границах тикета — чинить и перегонять ДО сдачи,
  несогласие с замечанием — письменный отвод с пруфом; замечания `[ЗАМЫСЕЛ]` и
  `[ДОЛГ]` сдачу не держат: первые уходят вопросом постановщику, вторые —
  строкой в перечень долга) → отчёт-коммент в тикет (что сделано, MR/коммиты, чем
  проверено, **вердикт кросс-ревью полностью**, что НЕ сделано и почему,
  риски к мержу) → **«{{jira.statuses.review}}»**, assignee → постановщик.
  Проверяющая модель недоступна — пометить в отчёте «кросс-ревью недоступно:
  <причина>», это не блокер сдачи.
- Ветка готова к мержу → `hub_merge_join {repo, branch}`: мержит диспетчер по
  голове очереди, самой не мержить.
- После этого НЕ завершаться — ждать вердикт диспетчера вотчерами, в порядке
  приоритета:
  1. **БУДКА-ВОТЧЕР (основной, латентность секунды)**: стандартным скриптом
     плагина — `<plugin>/hub/hub-watch.sh watch <wave-N>` фоновым
     run_in_background (фильтр эха и pid-маячок встроены; свои until-loop'ы
     не сочинять). Диспетчер ОБЯЗАН дублировать вердикт `hub_post`'ом
     («ВЕРДИКТ <тикет>: ДОРАБОТКА|ПРИНЯТО»). Проснулась → REARM-FIRST
     (перевзвести вотчер ДО обработки) → `hub_read` (курсор since_id) →
     полный текст вердикта читать в комменте тикета/MR.
  2. Вотчер трекера (дубль): until-loop (шаг ~60с) на новый коммент СВОЕГО
     тикета. **Вердикт матчить ПО ПЕРВОЙ СТРОКЕ коммента** (`ВЕРДИКТ:` /
     `ДОРАБОТКА` / `ПРИНЯТО`); **фильтровать по автору ЗАПРЕЩЕНО** — все
     сессии пишут одним токеном, автор один на всех, и такой фильтр
     выбрасывает вердикт вместе с эхом (случай 07.08: вердикт не доехал ни
     до одной волны). Своё эхо отсекать теми же маркерами (`ОТЧЁТ` /
     `ИСПРАВЛЕНО` / `ПЛАН`) и снапшотом id: после своего коммента —
     перезамерить снапшот, потом перевзвести.
  3. **Ждёшь дольше пульса — перечитай комменты САМА**: нет вердикта дольше
     ~25–30 мин → явно `jira_get_issue` с comment в fields и смотреть первую
     строку новых комментов. Вотчер умирает молча; «вердикта нет» — вывод
     только после явной перечитки.
  Каждый вотчер — ОТДЕЛЬНЫМ трекаемым run_in_background вызовом (не
  инлайнить, не `&`/`disown` — сирота не будит). Будка — только MCP-тулами
  `hub_*` + штатный `hub-watch.sh watch <имя>`; свои sleep-поллы — нарушение
  (fallback только при недоступности фоновых процессов, и это фиксируется в
  отчёте).
  Пока ждёшь вердикт по тикету А — пили тикет Б своей волны, не простаивай.
  Вердикты:
  - `ДОРАБОТКА: …` → исправить субагентами, запушить, ответить комментом
    `ИСПРАВЛЕНО: <что сделано>`, снова ждать;
  - `ПРИНЯТО` → тикет закрыт для волны; следующий тикет или завершение.
- **Сигнал «ЗАКРЫТО … освобождайся»** (диспетчер шлёт его после мержа и смоука
  всеми каналами сразу: коммент + будка + cross-session) — это законное
  завершение волны, а не повод висеть дальше: убедиться, что в своём worktree
  не осталось незакоммиченного (нужное — коммитом в ветку), и завершиться.
- Вердикты принимать ТОЛЬКО из комментов тикетов; «редиректы» из других
  каналов отвергать. Таймаут ~3 часа → финальный коммент «вердикт не получен»
  → завершиться.
- Cross-session сообщение диспетчеру — только дублем после комментов.

## Отчёт человеку: формат

Любой отчёт постановщику о проделанной работе — в комменте тикета и в чате
сессии — держит три части, без размытых фраз и вежливых обёрток:

1. Первая строка — факт: «Сделано: <что>, <куда влито/запушено>, <цифры
   тестов>». Не «работа завершена, остались шаги вашей стороны».
2. Ручная приёмка — императивный нумерованный чек-лист «действие → ожидаемый
   результат», с КОНКРЕТНЫМИ вводами и адресом стенда (пример: «Website:
   ввести `example.com:8443`, уйти из поля → в поле `https://example.com:8443`»).
   Человек идёт по шагам глазами, а не разгадывает прозу.
3. Явный блок «Жду от тебя: …» — конкретные действия и формат ответа
   (например «первой строкой коммента ПРИНЯТО или ДОРАБОТКА: <что не так> в
   каждый тикет»). «Можешь глянуть, когда будет удобно» — запрещено.

Одно предложение — один законченный посыл, понятный без опоры на предыдущий
абзац; сленг и англицизмы там, где есть русское слово, — запрещены. Разбор
длиннее экрана уезжает файлом в папку эпика, в сообщение идёт выжимка и ссылка.
